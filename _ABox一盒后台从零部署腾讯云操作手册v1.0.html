第 0 步 · 开工前：先定三件事

这三件不定就动手，后面大概率返工。每件都只要一个答案。

0.1这次部署是给谁用的？你决定
内部联调
只让你自己和测试人员访问 → 可以暂不装 HTTPS，先用 http://IP:8080，第 8 步以后再做
对外服务
团长 / 供应商要访问 → 必须走 HTTPS，且必须有已备案域名（微信侧强制要求）

本手册默认按对外服务写（完整路径）。若只做内部联调，跳过第 8 步即可，其余完全相同。

为什么内部联调也建议早做 HTTPS

后台是高权限面（能看到金额、佣金、供应商结算）。HTTP 明文传输 = 同一 WiFi 下任何人都可能截获登录凭据。内部联调只是"可以缓"，不是"不需要"。

0.2域名有没有、备了没你去查

只有你能查（在你的域名注册商 / 备案系统里）。查两件事：

域名的当前接入商是谁（阿里云？腾讯云？其他？）
备案是否仍然有效（不是"曾经备过"）
这条是唯一不可加急的一段

备案绑定实际接入商。若域名当前接入商不是腾讯云，换过来必须办接入备案，管局终审 1–20 个工作日；若原备案已失效，会被注销、需重新备案。

没有已备案域名 = 第 8 步的证书装不了、小程序也配不了服务器域名。所以：如果答案是"没域名"或"接入商不是腾讯云"，今天就先把备案提交掉，让它和部署并行跑 —— 这是整个上线周期里唯一不能靠加班压缩的一段。

0.3命令谁来敲我可以代劳

这台电脑上实测已装 OpenSSH 10.3p1 + scp + git。所以有两条路：

你敲
照本手册逐条复制粘贴（第 3 步起每步都有现成命令）

你在服务器上配一次免密登录，把 IP 给我 —— 第 3 步之后全部我来跑，报错我自己查自己修

第 1 步 · 买服务器

腾讯云控制台 → 轻量应用服务器 → 新建。只有这一页要填，按下面抄。

1.1配置照抄你 · 付款
选项选什么为什么是这个
地域中国境内（如 北京 / 上海）境外节点无法备案
镜像Ubuntu 22.04 纯系统镜像不要选"应用镜像"（Docker 版/宝塔版）—— 它们预装的东西会和我们自己的编排抢端口
套餐4 核 8G见下方"为什么不能省"
计费包年包月，时长 ≥ 3 个月按量/试用/竞价不支持备案，买了也不给备
带宽≥ 3 Mbps（不能为 0）带宽 0 不支持备案，也访问不了
系统盘默认 SSD 即可（80G 量级）MySQL + Redis + 两个镜像，够用
不要为了省几百块选 2C4G

这台机器上要同时跑 MySQL 8 + Redis 7 + API + nginx，而且还要在它上面构建两个 Node 镜像 —— 构建阶段的内存峰值才是真正的压力点，不是运行时。实测经验：4G 内存跑 pnpm install + nest build 会被 OOM 掉，而 OOM 的表现是构建进程被静默杀掉、报错信息完全看不出是内存问题，能卡很久。

差价是一次性的（新用户首单 4C8G 约 ¥450/年，日常价约 ¥1,500–2,500/年）。选 4C8G。

买完你会拿到三样东西

公网 IP（形如 1.2.3.4）—— 本手册后面用 <IP> 代指
root 密码（控制台设置或短信下发）
实例状态 = 运行中
1.2顺手别买的东西防顺手加购
不买原因
云数据库 MySQL / 云 Redis编排里已经自托管了这两个，再买是双份钱
负载均衡 CLB项目硬约束：一期只允许一个 API 实例（时间线是进程级单例）。CLB 会引入未验证的多实例形态，症状是"同一分钟下单，一台过一台不过，两边都不报错"，极难排查
COS 对象存储现在 STORAGE_DRIVER=local 就能跑，nginx 已配好 /static/。等图片量真上来了再迁，配置项都是现成的
CDN / 云监控单楼灰度体量用不上；项目已有自建巡检脚本

第 2 步 · 开防火墙

腾讯云控制台 → 轻量应用服务器 → 你的实例 → 防火墙。这一步最容易犯错，错了后面全乱。

2.1只开这三个端口你 · 控制台
端口协议用途来源
22TCPSSH 登录（或控制台 WebShell）建议限制为你的 IP
80TCPHTTP（证书签发校验要用，之后跳转 443）全部
443TCPHTTPS —— 后台真正对外的人口全部
绝对不要把 8080 放到公网

项目的后台容器对宿主暴露的是 8080 端口，那是给宿主机 nginx 内部反代用的，不是给公网用的。直接开 8080 等于：
① 绕过了 HTTPS，明文传输管理员凭据；
② 绕过了第 8 步要装的证书与安全头；
③ 一旦 PROVIDER_MODE 配错（见第 5 步），任何人可免密登录任意身份。

正确形态：公网 443 → 宿主机 nginx → 127.0.0.1:8080。8080 只在服务器内部可见。

如果你的 22 端口不想对全网开

腾讯云控制台提供「一键登录（WebShell）」功能，走网页直连，不需要开 22 端口、不需要配密钥。第 3 步用它最省事。等你要让我代劳时再开 22 并限制来源 IP。

第 3 步 · 登录服务器 + 装 Docker

从这里开始是命令行。每条命令都可直接复制。

3.1登录（两种方式选一）你
方式 A · 控制台 WebShell（最简单，推荐第一次用）

腾讯云控制台 → 实例 → 一键登录 → 弹出黑框即可直接敲命令，不用装任何东西。

方式 B · 本机 SSH（Windows 10/11 自带，打开 PowerShell 或 CMD 即可）
ssh root@<IP>

首次连接会问 Are you sure you want to continue connecting (yes/no)? —— 输入 yes 回车，再输密码（输入时屏幕不显示，正常的，敲完直接回车）。

判据

出现 root@<主机名>:~# 提示符即登录成功。若提示 Connection timed out → 回第 2 步确认 22 端口；若 Permission denied → 密码不对，去控制台重置。

3.2固定时区（别跳，它影响钱）关键
timedatectl set-timezone Asia/Shanghai && timedatectl | grep "Time zone"
为什么要单独做这一步

项目的 MySQL 容器启用了 --default-time-zone=+08:00，应用侧连接也写死 timezone='+08:00'。若宿主机是 UTC，日切跑批（T-1 24:00 截单、次日 02:00 结算）会算错日子 —— 表现为"订单明明在截单前下的却被判超时"这类极难归因的问题，而且不报错。

判据：输出应含 Time zone: Asia/Shanghai (CST, +0800)。

3.3加 2G 交换空间（防构建 OOM）强烈建议
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile && echo '/swapfile none swap sw 0 0' >> /etc/fstab && free -h | grep -i swap

判据：Swap: 一行显示约 2.0Gi。

4C8G 跑两个 Node 镜像的构建，加 swap 是保险。代价是磁盘换内存，构建慢一点，但不会莫名其妙被杀进程。

3.4装 Docker或我
curl -fsSL https://get.docker.com | sh
装完验证（两条都要过）
docker --version
docker compose version
判据必须是两条都出版本号

docker compose version 必须输出形如 Docker Compose version v2.x.x。只装到 Docker 引擎、没有 Compose V2 插件是常见情况 —— 此时 docker compose 会报"command not found"，而 deploy.sh 会在"1/7 预检"那一步直接中止（脚本带 set -euo pipefail，不会静默）。

若第二条失败：apt-get update && apt-get install -y docker-compose-plugin

把 Docker 设为开机自启
systemctl enable --now docker

第 4 步 · 把代码弄到服务器上

推荐用 git 直接拉，最省事也最不容易出错。

4.1克隆仓库或我
cd /opt && git clone <你的仓库地址> abox-onebox && cd abox-onebox
先确认远端是最新的

已核实：origin/main 已与本地 HEAD 对齐（commit 1a0710e，含注销功能、通知矩阵、口味评价、资金闸门、28 道门禁、部署前置）。所以直接从远端拉即可，不用从你本机传。

如果仓库是私有的、服务器上没配 SSH key，就退回方案 B：在你本机执行 scp -r abox-onebox root@<IP>:/opt/（较慢，但不用配权限）。

判据

ls docker-compose.prod.yml scripts/deploy.sh .env.example

三个文件名都列出来（不报 No such file）才算到位。注意 docker-compose.prod.yml 必须在仓库根目录 —— 所有脚本都是按"在根目录执行"写的。

4.2确认脚本有执行权限易漏
chmod +x scripts/*.sh

git 通常会保留权限位，但 Windows 上打过包的仓库有时会丢。若后面执行 ./scripts/deploy.sh 报 Permission denied，就是这一步没做。

第 5 步 · 写 .env.prod

整个部署里唯一"配错了不报错、但后果最严重"的一步。请逐条核对。

5.1先复制样例或我
cp .env.example .env.prod && chmod 600 .env.prod
照抄样例上线 = 裸奔

样例文件是为本地开发写的，里面有三个必须改掉的值。直接拿去部署，服务照常起来、不报任何错，但后果如下。

5.2三个必须改的（缺一不可）你填值
变量必须改成不改的后果
PROVIDER_MODE 显式写 real（对外服务时） 最危险 留 mock 的后果是：任意 code 可免密登录任意身份 + 支付自动置为已支付，且服务照常起、无任何报错
JWT_SECRET 真随机长串 留 change_me_before_go_live → 任何人可以自签一个超管 token
MYSQL_ROOT_PASSWORD
DB_PASSWORD		 强口令 DB_PASSWORD 生产无内置兜底，漏配即连不上库
关于 PROVIDER_MODE 的两道保险

项目在 main.ts 里有 REQUIRED_IN_PROD 检查：生产环境漏配该项会直接启动中止。这是第二道保险 —— 但它的作用是"防漏配"，防不了"配成了 mock"。所以仍需你显式写 real。

若这次只是内部联调、暂时没有微信账号：可以留 mock，但务必不要开 8080 到公网（回到第 2 步）。

5.3在服务器上生成强密钥（推荐这样）或我
生成两个随机串，打印出来
openssl rand -base64 32
openssl rand -base64 32
用编辑器改（把上面两条输出分别贴进对应位置）
nano /opt/abox-onebox/.env.prod

改完按 Ctrl+O 回车保存，Ctrl+X 退出。

为什么推荐在服务器上生成，而不是让我给你一个

① 密钥不经过聊天记录，减少留痕面；② 手打的密码几乎都是弱密码；③ 生成完请顺手抄进你的密码管理器 —— 丢了它只能重来一遍，数据库里的密码哈希是用它签的。

如果你希望我来做这一步：我会在服务器本地生成并直接写入文件，不把密钥内容打进对话，只告诉你已写入。

5.4核对清单逐条勾
PROVIDER_MODE 已按你的场景显式写 real（或确认只做内部联调）
JWT_SECRET 已换成随机串（不是 change_me_before_go_live）
MYSQL_ROOT_PASSWORD 和 DB_PASSWORD 已改（两者都用同一个新密码最省事）
MYSQL_ROOT_PASSWORD 已填 —— 这是编排里的硬失败项，缺了 compose 直接拒绝启动
DB_DRIVER=mysql、QUEUE_DRIVER=redis（不是 sqlite / memory）
文件权限已是 600（ls -l .env.prod 看到 -rw-------）
关于 MYSQL_ROOT_PASSWORD 的一个坑

编排里写的是 ${MYSQL_ROOT_PASSWORD:?缺少 MYSQL_ROOT_PASSWORD} —— 带 :? 的写法表示变量缺失时 compose 直接拒绝启动，不会用默认值悄悄起来。这是好事（防裸奔），但代价是：如果你漏填，报错信息会很明确，看到"缺少 MYSQL_ROOT_PASSWORD"就知道是第 5 步没做完。

其它变量多是 ${VAR:-默认值} 形式（有兜底），所以只有这一个会硬拦你。但"能启动"不等于"配对了" —— 所以 5.4 的清单要逐条勾。

第 6 步 · 跑部署脚本

项目自带 deploy.sh，7 个阶段全自动。先空跑一遍看它会做什么，再真跑。

6.1先空跑（不真的动任何东西）强烈建议
./scripts/deploy.sh --dry-run

会打印出它打算执行的每一条命令，不实际执行。看一遍，确认没有意外（比如路径不对、tag 不对）。

6.2真跑或我
./scripts/deploy.sh

首次部署约 8–15 分钟（主要是拉基础镜像 + 构建两个 Node 镜像）。你会看到 7 个阶段依次推进：

阶段做什么这一步卡住意味着
1/7 预检检查 docker / compose / 编排文件 / .env.prod，确定镜像 tagDocker 没装好，或不在仓库根目录
2/7 备份备份数据库首次部署时报"备份失败"是正常的（库还是空的），脚本会警告后继续
3/7 起依赖启动 MySQL + Redis，等 MySQL 就绪MySQL 起不来（多半是密码或内存）
4/7 构建构建 api + admin 两个镜像最耗时也最容易 OOM 的一步；报 Killed 基本就是内存不够（回第 3.3 步）
5/7 迁移执行数据库迁移（建表）见第 7 步的专门判据，这里显示"已执行"不代表表真的建好了
6/7 起应用启动 api + admin 容器—
7/7 健康验证轮询健康检查，最多 90 秒API 没起来，看下一步的排查命令
失败时脚本不会自动回滚，这是故意的

脚本在失败时会打印出明确的回滚命令然后停下，把决定权交给人。原因是：迁移可能已经执行了，此时自动把代码退回旧版、而表结构停在新版，会形成半新半旧状态 —— 那往往比"新版本 + 已知故障"更难判断。这与项目"不做静默降级"的一贯取舍一致。

第 7 步 · 验收三条判据

脚本打印"部署成功"不代表可以收工。这三条要亲眼看到。

7.1容器都在跑或我
docker compose -f docker-compose.prod.yml --env-file .env.prod ps
判据

四个服务（mysql / redis / api / admin）状态都要是 Up 或 Up (healthy)。
注意 api 没有配 healthcheck（编排里刻意没加，避免依赖故障引发重启风暴），所以它只显示 Up 是正常的，不能用"是不是 healthy"判断 API 好坏 —— 要靠 7.3。

7.2迁移真的建表了最容易蒙混过关
docker compose -f docker-compose.prod.yml --env-file .env.prod run --rm --no-deps --entrypoint sh api -c \
  'node node_modules/typeorm/cli.js migration:show -d apps/api-server/dist/database/data-source.js'
唯一有效判据：两支都要是 [X]

输出必须同时列出 Init1700000000000 和 ParityFix1700000000001，且两个后面都是 [X]。少一支，或者任何一支是 [ ]，都等于表没建全。

为什么不能只看部署脚本"5/7 迁移已执行"那行 OK：TypeORM 在找不到任何迁移文件时不报错，只输出一行 No migrations are found 就正常退出 0。于是部署流水线显示全绿，而所有建表语句从未执行 —— 等到第一个写请求打进来，才会炸在"列不存在"上，而那时已经是线上故障了。

已核实的现状（避免你白担心）

迁移的 glob 配置实测为 migrations/*.{ts,js} —— 已同时包含 .js，所以在 dist/ 下能匹配到编译产物，配置本身没问题。
但这不等于可以跳过这条判据：最终有没有 .js 落在 dist/database/migrations/ 里，取决于构建时的编译范围 —— 这属于"只有真机跑一遍才知道"的事。所以第 7.2 步必须真跑一次、亲眼看两支都是 [X]。

7.3探针能通或我
curl -s http://127.0.0.1:8080/api/v1/health/ready; echo
curl -s http://127.0.0.1:8080/api/v1/health; echo
判据

两条都返回 JSON。/health/ready 会额外检查 MySQL / Redis 连通性；/health 是存活性探针（不检依赖）。
如果 /health/ready 返回非 200，说明应用起来了但连不上库 —— 90% 是 .env.prod 里数据库密码和 MYSQL_ROOT_PASSWORD 不一致。

另外：/health 的返回里带 version 字段，用它可确认"现在跑的到底是哪一版"（镜像构建时注入的 git sha）。

顺手确认后台页面能打开
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/

返回 200 即可。此时你在浏览器里访问 http://<IP>:8080 也应该能看到后台登录页 —— 但请先确认你已经把 8080 关在公网外（第 2 步），否则就用控制台 WebShell 里的 curl 测。

第 8 步 · 装 HTTPS 证书

前置条件：已有域名、且已解析到这台服务器的 IP。没有域名就先回第 0.2 步。

8.1解析先生效你 · 控制台

在域名解析商处加一条 A 记录：@（或你要的子域名，如 admin）→ <IP>。

在服务器上确认解析已生效（看到你的 IP 才行）
ping -c 1 <你的域名>
不要跳过这条

解析没生效就去申请证书，certbot 会失败，而失败信息是"DNS 解析不到"这类容易误判成别的问题。先确认这一步，省很多事。

8.2装宿主机 nginx或我
apt-get update && apt-get install -y nginx certbot python3-certbot-nginx
8.3写站点配置（反代 8080）或我
cat > /etc/nginx/sites-available/abox-admin <<'EOF'
server {
    listen 80;
    server_name <你的域名>;

    client_max_body_size 20m;

    location / {
        proxy_pass         http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 微信支付 V3 回调要拿原始报文验签，不能缓冲
        proxy_request_buffering off;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
    }
}
EOF
ln -sf /etc/nginx/sites-available/abox-admin /etc/nginx/sites-enabled/
rm -f /etc/nginx/sites-enabled/default
nginx -t && systemctl reload nginx
两个必须保留的细节

① client_max_body_size 20m —— 后台要传商品图 / 凭证图，nginx 默认 1m 会直接 413，且报错只在上传时出现。
② proxy_request_buffering off —— 微信支付 V3 回调要拿原始报文验签（应用侧开了 rawBody）。缓冲会引入时序/大小差异，导致签名校验失败，而症状是"支付成功了但回调验签不过"，很难往 nginx 上想。

8.4申请证书填邮箱
certbot --nginx -d <你的域名> -m <你的邮箱> --agree-tos -n

certbot 会自动改配置、装证书、并配好自动续期。它还会问是否把 HTTP 重定向到 HTTPS —— 选重定向（2）。

验证
certbot renew --dry-run
为什么一定要跑一次 dry-run

免费证书 90 天过期。certbot 装完会注册自动续期任务，但那个任务从未被验证过。renew --dry-run 不消耗申请额度、却能证明续期链路是通的 —— 不验的话，三个月后你会在一个毫无征兆的早上发现全站证书过期。

最终判据

curl -s -o /dev/null -w "%{http_code}\n" https://<你的域名>/

返回 200，且浏览器地址栏是锁头图标。到此，后台可以用 HTTPS 正常访问了。

第 9 步 · 备份 · 回滚演练 · 定时任务

这三件事决定"出事之后有没有退路"。建议第一次就做，别等出事。

9.1备份或我
./scripts/backup-db.sh && ls -lh backups/ | tail -5
备份文件在容器所在机器上是"假备份"

机器挂了 / 被误删，备份也一起没。第一台机器上线后，请务必把 backups/ 同步到别处（哪怕是你本机硬盘，或者腾讯云 COS 的一个低频存储桶）。这件事不做的后果是"有备份，但和数据库一起丢了"。

9.2回滚演练必须做一次
./scripts/rollback.sh
为什么"没出事也要演练一次"

回滚脚本和备份脚本一样，从未在真机执行过。真出事的那天，如果你第一次跑它就发现有问题（比如路径不对、tag 取不到），那就是"明知有退路却走不了"的最坏局面。在没有压力的时候跑通一次，是唯一能确认退路可用的办法。

硬禁忌 生产机上永远不要执行 docker image prune -a —— 它会把上一版镜像一起删掉，等于亲手销毁回滚能力。

9.3注册定时任务或我
./scripts/install-cron.sh --dry-run
./scripts/install-cron.sh

先 --dry-run 看它会写什么，再真装。项目的时间线是运行时注册 + 热重载（不是 @Cron 装饰器），所以定时任务装好之后，日切、结算、巡检才会真的跑。

一个前提约束

项目的时间线是进程级单例，因此一期只允许一个 API 实例。定时任务装在这台机器上即可；不要为了"高可用"再起第二个实例，那会引入双份跑批（同一笔结算跑两次）。
