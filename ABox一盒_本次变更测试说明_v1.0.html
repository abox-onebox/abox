零、先看这三条（避免把设计当缺陷）

  1. 报错一律是 HTTP 200，靠响应体里的 code 判断成败， 不要看 HTTP 状态码。校验失败是 code:10001，不是 400。
  2. 只卖一个套餐，用户不点菜：下单表单只有「份数」一项， 没有口味、没有备注、没有选券控件。今天的菜是只读展示，不是让你选。
  3. 团长点「送达」不会立刻到账：佣金是三段式——送达 → 当日 14:00 生成待结算 → 次日 02:00 入账。当天查不到佣金是正常的。

三、必测项

3.1 一键停售（新增 · 重点）

后台新增「系统 → 一键停售」页。运营填写停售原因后全局拦新单，落独立表 ab_sales_pause。

  1. 后台进入 系统 → 一键停售，填原因（例如「今日备货不足」）并提交
  2. 打开小程序首页：应看到停售提示，且带有刚填的那句原因
  3. 尝试下单：应被拦下，提示语里同样带原因
  4. 后台执行「恢复接单」
  5. 小程序首页与下单应恢复正常
预期
停售期间下单报 60009，提示形如「今日暂停接单：备货不足」。
若运营没填原因，回落为「当前已暂停接单」——两种都算正确。
恢复后不应残留拦截。

3.2 楼宇停用闸门（新增）

后台停用办公楼或楼群时，会检查该楼 / 楼群是否还有未完结订单。

  1. 先造一个有未完结订单的办公楼，后台执行停用 → 应被拦下
  2. 让未完结订单数超过阈值后强制停用 → 应提示需提交运营审批
  3. 在已有订单进入履约阶段后尝试撤回停用 → 应提示无法撤回
  4. 把某个办公楼挂到已停用的楼群下 → 应被拒绝
预期（文案见第五节速查表）
第 1 步：60006（楼）/ 60007（楼群）
第 2 步：60012　　第 3 步：60013　　第 4 步：60008

3.3 X 盲盒（新增）

  1. 正常下一单
  2. 打开订单详情：应看到盲盒一行，状态为「待揭晓」，看不到内容
  3. 团长点「送达」后再看：应显示具体盲盒名，状态变「已揭晓」
  4. 首页对应位置也应显示该盲盒格位
预期
送达前不得泄露盲盒内容——这是它全部的意义所在。
同时：没有集盒、勋章、弹层这些额外东西。这是个轻量小功能， 只出现在首页一格和订单详情一行，别处出现即为异常。

3.4 代金券（新增 · 重点）

独立的券系统。券有三个来源：推荐返券、客服补偿、后台手动发放。

  1. 后台 财务 → 代金券：建一个券种，并手动发一张给某个测试用户
  2. 该用户登录小程序，我的 → 我的券：应能看到这张券
  3. 用该用户下单：应自动抵扣，订单详情里能看到优惠金额
  4. 取消这笔订单：券应退回，回到「我的券」里可用
  5. 再走一次退款流程，且退款被驳回：券不应退回
预期
下单时系统自动选抵扣最多的那张，用户端不做选券控件（守「表单只有份数」的规矩）。
三种取消路径都必须退券：用户自助取消、截单兜底自动取消、退款审批通过。
第 5 步是关键的反向用例：退款驳回时券不能退——退了就是白送钱。

3.5 去餐化（改版）

  1. 确认小程序内已不存在「供应商列表」「溯源」入口
  2. 后台 供应商 → 门店实拍照片：上传照片、整组替换
  3. 首页查看今日菜品：能打开看到今天吃什么
预期
菜品是只读信息展示，让用户知道今天吃什么，不是点菜、不能选。 若出现口味选择、备注输入框，即为缺陷（违背单一套餐的设计）。

3.6 首页 / 招募页 / 推荐中心（改版）

  1. 逐屏检查首页布局与文案
  2. 进入招募页：CTA「成为团长」一屏内只出现一次
  3. 从招募页进入推荐中心：非团长身份也应能推荐并看到记录
预期（文案红线）
招募与分享文案中不得出现：「自提」「自行领取」「躺赚」「轻松赚」「零花钱」 「管一栋楼」「全楼」「先到先得」。
这些是提审红线或已纠正过的错误设定，命中即为缺陷。
交付口径统一是「团长送到你工位」。

四、回归项（三步重构，无功能变化）

后台楼宇模块被拆成了三个文件（停用块、派生计算层、读侧服务），主文件从 1611 行降到 726 行。 纯代码搬家、行为不应有任何变化，但涉及面广，以下必须回归：

  • 后台楼宇：列表、详情、总览、配送图（这四个视图被整体搬到新文件）
  • 后台楼群：增删改查、成员替换
  • 停用流程：停用、恢复、停用通知
  • 下单全链路：下单 → 支付 → 送达 → 佣金入账
判据
与改动前表现完全一致即为通过。若发现任何差异——哪怕是文案多一个字——都要报， 因为重构的契约就是「零行为变化」。

  • 佣金不是即时到账：见第零节第 3 条
