# ABox 一盒 · 路线 B（整体迁入 WorkBuddy）迁移成本评估

> 评估时间：2026-10-17  
> 评估对象：将 ABox 一盒小程序整体迁入 WorkBuddy 小程序应用空间开发 + 托管发布，后端切换至 cloud-service  
> 数据来源：本工作区 `abox-onebox/` 源码实拉 + cloud-service / sites 官方能力说明

---

## 零、一句话结论

**路线 B 现阶段不推荐，且以现有 cloud-service 能力属于「架构级不可行」**——它不是迁移，而是放弃整套 NestJS 后端、用 BaaS 重做；而 BaaS 恰恰托不住 ABox 的核心商业逻辑（订单状态机 / 结算 / 分账 / 真实微信支付 / 定时截单时间闸）。即便强行做，最终仍需自建运行时承载业务逻辑，等于「还是自己管服务器」，cloud-service 的价值归零。

## 二、cloud-service 能力边界（真实）

| 模块       | 提供                       | 不提供                                                |
| -------- | ------------------------ | -------------------------------------------------- |
| Database | CRUD / 条件查询 / 分页         | 关系型事务 / 复杂 JOIN / TypeORM 迁移 / 原 schema 兼容         |
| Auth     | 端用户注册 / 登录 / 会话 / 身份隔离   | 自定义鉴权策略、JWT 自管、与微信商户号联动                            |
| Storage  | 文件上传下载 / 签名 URL          | —                                                  |
| LLM API  | 免密钥大模型调用                 | —                                                  |
| **运行时**  | 无                        | **无云函数 / 无自定义服务端逻辑 / 无 Redis / 无 cron 队列 / 无全局单例** |
| **支付**   | 仅 **xpay 虚拟支付**（虚拟商品/会员） | **无实体交易支付、无商户号托管、无分账、无回调**                         |

关键判定：**cloud-service 是 BaaS（后端即服务），不是「能跑任意 Node 服务」的容器**。NestJS 的全部 service 层在它里面没有运行位置。

## 三、能力逐项对照（缺口 = 迁移成本）

| ABox 现有能力                                              | cloud-service 能否承载   | 缺口严重度        | 后果                                                    |
| ------------------------------------------------------ | -------------------- | ------------ | ----------------------------------------------------- |
| 订单 11 态状态机 + 幂等（`Idempotency-Key`）                     | ❌ 无运行位置              | **致命**       | 放前端→金额/状态可被篡改；不放→业务崩                                  |
| 结算（佣金 8/9/10/12% 自动结算）                                 | ❌ 无运行位置              | **致命**       | 资金计算不可信、违反资金安全                                        |
| 团长分账 / 提现打款（`payout.service`）                          | ❌ 无运行位置              | **致命**       | 现金分账逻辑无处安放                                            |
| 真实微信支付 + 回调（`wxpay` / `wx-notify`）                     | ❌ 仅 xpay 虚拟支付        | **致命**       | 实体交易不适用 xpay，须自建且自建处无托管后端                             |
| 定时截单 / 09:30 收口 / 11:30 送达（`@nestjs/schedule` + 单例时间闸） | ❌ 无 cron / 无单例运行时    | **高**        | 时间唯一真相机制需完全重做；Serverless 天然不适合全局单例                    |
| Redis 幂等 / 缓存 / 队列                                     | ❌ 无 Redis / 无 BullMQ | **高**        | 并发安全、异步任务需另寻方案                                        |
| 28 表关系模型 + 5 支迁移                                       | ⚠️ 需重新建模             | **高**        | 数据模型重设计 + 迁移工具 + 历史数据导入                               |
| 42 个 service 的业务规则                                     | ❌ 无运行位置              | **致命**       | 全部重写，且重写后无载体                                          |
| 前端 27 页数据访问（现调 `api.xunlizhinian.cn`）                  | ⚠️ 改调 SDK            | **中-高**      | 改用 `@tencent-ai/workbuddy-cloud-sdk/miniprogram`，全量改造 |
| 后台 admin-web                                           | ⚠️ 改调 SDK + 重新部署     | **中**        | 后端没了，admin 也须改调 cloud-service                         |
| 微信商户号回调域名 / 小程序服务器域名                                   | ❌ 发布域由 WorkBuddy 管   | **中（有风险窗口）** | 备案、商户号配置、公众号配置要重走                                     |

## 四、五大结构性障碍

1. **业务逻辑层无承载物（致命）**  
   ABox 的核心不是「存数据」，而是「算钱 + 管状态」：订单状态机、结算、分账、退款、对账、佣金。这些是服务端信任边界，放前端 = 金额可被用户篡改，绝对不可行。BaaS 没有「写服务端函数」的位置，所以这 42 个 service 要么消失、要么挪到别处自建——后者等于没迁。
2. **真实支付 + 分账无法托管（致命）**  
   cloud-service 只有 xpay（虚拟商品）。ABox 是实体盒饭 + 团长现金分账，必须持有微信商户号、自己实现支付下单 / 回调验签 / 分账打款。这些逻辑本身就需要一个可信服务端，而 cloud-service 不提供。
3. **Redis + 定时任务无对等物（高）**  
   `currentTimeline()` 进程级单例、`@nestjs/schedule` 定时截单、BullMQ 异步任务——依赖有状态运行时 + Redis。cloud-service 是 Serverless、无状态、无单例，时间闸机制要彻底重做，且重做后仍存在并发一致性风险。
4. **数据层要重做（高）**  
   28 表关系模型 + 5 支 TypeORM 迁移 + seed，cloud-service Database 不兼容原 schema，需重新建模、写迁移与导入工具、校验历史数据。
5. **合规链路要重走（中，有窗口期风险）**  
   ICP / 小程序备案（86369）/ 域名实名 / 公安备案都绑定现有发布域名。迁入 WorkBuddy 后发布域与回调域变更，微信支付商户号回调地址、公众号/小程序服务器域名配置全部要改，存在审核窗口期，期间支付与登录可能中断。

## 五、工作量量级（仅作量级参考，非精确排期）

| 工作项                          | 量级       | 说明                     |
| ---------------------------- | -------- | ---------------------- |
| 数据模型重设计 + 迁移 + 历史导入          | 大（数周）    | 关系模型→BaaS 存储，需重写全部读写   |
| 业务逻辑重写（且无载体→须另寻方案）           | 极大       | 路线 B 本身不解决，需自建运行时，价值归零 |
| 支付 / 分账 / 回调自建               | 大        | 仍要商户号 + 自建可信服务端        |
| 前端 27 页数据访问层改造               | 中-大      | 全量改调 SDK               |
| 后台 admin-web 改造 + 部署         | 中        | —                      |
| 合规重走（备案/商户号/域名）              | 中（有风险窗口） | —                      |
| 全量回归（门禁 29 道 + e2e m1/m2/m3） | 大        | 现有门禁基线会全部失效需重建         |

**总判定**：路线 B ≈ 推倒重来，且重来后核心逻辑仍须自建服务端 → cloud-service 省下的服务器运维，被「无处安放的核心逻辑」反噬。

## 七、一句话给祝总

你这套的价值在「算得清钱、管得住状态」的服务端，而 cloud-service 是「存数据、免运维」的 BaaS，两件事错位。把 B 当迁移是亏的——**留着腾讯云那套后端，只把 WorkBuddy 当「补强新功能 + 发分享链接」的工具，才是这套模块对你最划算的打开方式**。
