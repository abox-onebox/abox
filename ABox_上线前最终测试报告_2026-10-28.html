一、阻断级问题（上线前必须处置）

阻断 18081 的 Cookie 闸门会把小程序整端挡死

现象：8081 端口所有路径（含 /api/）一律返回 401。实测：

/                      -> 401
/api/v1/health/ready   -> 401
/api/v1/auth/login     -> 401
/api/v1/pay/notify     -> 401

为什么它挡的是小程序：

  • 小程序接口地址写死 8081：apps/miniprogram/.env 与构建产物内均为 http://154.8.164.180:8081/api/v1（已 grep 产物确认）
  • 闸门是 server 级 if ($abox_gate_pass = 0) { return 401; }，覆盖静态页与 /api/ 反代，不是只挡页面
  • 小程序端 request.ts 不带 Cookie（已 grep 确认无 Cookie 相关代码），也无从通过 ?gate= 换取 —— 那条换 Cookie 的分支只在浏览器访问 / 时触发

闸门本身是对的：它修的正是我上次提的 P0（?devCode=任意 可免密切换任意身份 + 8081 对外开放）。注释里也写清了为何用 Cookie 而非 Basic 认证。问题只在于它把 API 一起挡了。

建议改法：闸门只作用于静态页面，放行 /api/ —— API 侧本来就有 JWT 鉴权（我实测无 token / 伪造 token 均被 10002 拦下）。或上线前直接撤掉闸门。

阻断 2支付回调在 8081 同样被挡 401

实测对照：

8080 /api/v1/pay/notify -> 201  （可达）
8081 /api/v1/pay/notify -> 401  （被闸门挡）

后果：微信支付回调走 8081，被挡 ⇒ 用户付了钱、系统不知道，订单停在待支付。这正是 P3「支付单边账」的触发路径。mock 模式下看不出来，一旦切真实支付立刻爆。

与阻断 1 同一个根因，放行 /api/ 即可一并解决。

昨天那个 P0 的现象确实消失了——同一订单三个端点各打 5 次，全部 code=0：
