P3 · 支付单边账（回调丢失） —— 确认是缺口

这条是四条里唯一「我的判断成立」的，也是四条里唯一真的要花钱修的。
核实结论：系统没有主动查单补偿机制。用户微信支付成功、但回调没打到服务器时，这笔钱在系统里不会被发现。
证据：
  • payment/wxpay.service.ts 对外方法只有四个：createPrepay（下单）、parseNotify（解析回调）、onPaid（回调处理钩子）、simulatePaid（模拟支付）。没有 queryOrder、没有 closeOrder。
  • 全仓 grep「主动查单 / 补单 / payQuery」：零命中。
  • 9 个定时任务名单里（cutoff / commission-settle / auto-confirm / delivery-generate / leader-expire / meal-publish / reconciliation / supplier-share / page-track-cleanup）没有任何查单对账类任务。
实际影响：用户扣了钱、订单停在「待支付」，超时后被自动关单。用户看到「订单已取消」但钱被扣了 —— 这类投诉只能靠用户主动发现，你无从知晓。上线后每发生一次都是一次信任损失。
建议：加一个定时查单任务。对「创建超过 N 分钟、状态仍为待支付」的订单，主动调微信查单接口：支付成功则补推进；确认未支付则关单。这是同类系统里的标准做法，工作量不大。

S3 · 提现并发超扣 —— 我判断错了，实际已防住

这条我原本标 P0，看完代码应当撤销。
核实结论：提现用了乐观锁 + 冻结机制，并发是安全的。
证据：
  • finance/withdraw.service.ts 提现申请在事务内：version: () => 'version + 1' 且 .where('id = :id AND version = :v')，更新行数为 0 时直接抛「余额已变动，请刷新后重试」——经典的乐观锁写法。
  • 申请阶段不是直接扣钱，而是 balance 减、frozen 加（余额冻结），到账后才真正出账。
  • 同样的乐观锁在其余写钱路径系统性覆盖：refund.service.ts（4 处）、reversal.service.ts（2 处）、commission.service.ts、balance-admin.service.ts、delivery.service.ts（配送状态推进也有）。
结论：这条从 P0 缺口改为「已实现」。我原先依据「grep 不到悲观锁」就推定有并发风险，是用不完整探针得出的错误结论，请勿据此去找技术团队问责。

T3 · 手动补跑结算双倍入账 —— 我判断错了，实际天然幂等

这条我原本标 P0，也应撤销。
核实结论：补跑端点是幂等的，重复点不会双倍入账。
证据：
  • commission.service.ts:720：入账扫描条件是 { status: 'pending' } —— 只捞待入账的行。
  • commission.service.ts:790-796：入账用 UPDATE ... SET status='settled' WHERE id=:id AND status='pending'，更新到 0 行就跳过（注释写明「并发下已被别处入账」）—— 这是行级原子的防重。
  • 跑批路径走 sched.run() 带锁，同一目标日期只跑一次；手动补跑端点确实不带锁，但因为上面的写法，不带锁也不会重复入账。源码注释自己也写了「本方法天然可重入」。
结论：「手动补跑不带锁」这行注释确实存在，但它是有意为之且安全的——幂等由 SQL 条件保证，不靠锁。我当时只看到「不带锁」三个字就下了结论，是断章取义。

Q2 · 团长自确认送达即计佣 —— 部分成立，降为 P1

不是我说的「纯自确认」，但也确实存在凭证缺口。
核实结论：佣金不由团长点「送达」直接触发。中间隔着三道，有天然缓冲。但「是否已送达」这个前置状态，确实只有单侧（团长/管理员）能推进。
实际链路（三道）：
环节谁推进代码位置
订单 → DELIVERED团长点，或管理员推进delivery.service.ts:922 advanceGroupOrdersToDelivered
T 日 14:00 计佣（status=pending）定时任务，只捞 DELIVERED 的单order.service.ts:964 autoConfirmByDate
T+1 02:00 入账到团长余额定时任务commission-settle.task.ts:94
为什么降级：
  • 计佣是定时任务按日期批量做，团长点送达不能直接换钱，中间有 14:00 到次日 02:00 的缓冲窗口，足够用户申诉。
  • order.service.ts:971-977 专门有一个「履约异常」分支：14:00 仍未送达的订单如实计数上报，绝不偷偷改状态。这说明团队考虑到这个问题了。
剩下的真实缺口：全仓没有取餐码 / 二维码核销（grep 零命中）。所以当用户投诉「我没收到」时，系统侧拿不出任何送达凭证，只能靠操作日志打官司。建议在保持「团员零走动」的前提下，加一条用户侧无需操作、超时自动确认 + 可申诉的凭证机制。
