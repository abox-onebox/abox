X5 · Redis 一抖动，幂等保护就永久静默失效（真缺口）

证据位置：apps/api-server/src/common/cache/kv.service.ts:112-130 · :27 / :47 / :127
代码事实：
  • :126 catch { —— 不区分异常类型，连接失败 / 超时 / 命令报错一律捕获
  • :127 this.degraded = true; —— 置位
  • :128 return this.setNx(key, value, ttlSec); —— 递归后走内存分支（不会栈溢出，此处实现是对的）
  • 反向验证：全文件 grep "degraded = true" 得 7 处；grep "degraded = false" 仅 1 处且是 :27 的字段声明 ⇒ 运行期零复位，单向、需重启才能恢复
为什么这次抖动「很容易发生」：Redis 客户端建连参数写的是 enableOfflineQueue: false + maxRetriesPerRequest: 1（kv.service.ts:38-45）。 这两项是刻意让故障立即暴露的正确写法，但副作用是：一次亚秒级网络抖动就会立刻抛错并触发降级，而不是等重连。 也就是说，这条降级路径不是「理论上的极端分支」，而是生产环境迟早会走到的路径。
最值得说的一点：它与本项目自己坚持的口径相反。
同一套代码里，队列明确选择了 fail-closed —— 项目文档原文： 「Redis 驱动连不上是 fail-closed 抛错，不静默降级」，理由是「丢一条『退款待重试』既无报错也无处可查」。
而幂等键这里恰恰是静默降级。问题在于：幂等键失效的后果比队列丢一条更直接 —— 它防的是「同一笔钱被扣两次、同一单被建两遍」，而失效时表面上一切正常（请求照常成功返回）。
建议修法（三选一，工作量都很小）：
  • 推荐 · 改成 fail-closed：Redis 驱动下 setNx 抛错直接向上抛，不降级 —— 与队列同口径。代价是 Redis 抖动期间下单会失败，但「明确失败」远好于「静默重复」
  • 次选 · 可自愈的降级：保留降级，但加一个后台探活（每隔 N 秒试一次 Redis，恢复后把 degraded 复位为 false）
  • 最小改法 · 至少让它吵起来：降级时打 ERROR（现在是 WARN）并接入告警 —— 目前只有一行日志，没有任何人会被通知
验收标准（可直接转技术）：
  • 让 Redis 不可达，调用下单接口两次 ⇒ 期望返回明确错误，而不是「第二次被判为重复提交」或「两次都成功建单」
  • 让 Redis 抖动一次后恢复 ⇒ 期望 degraded 能回到 false（若选次选方案）
  • 降级期间，日志级别为 ERROR 且能被监控系统捕获

I1 · 幂等主链路：设计正确，且有自动化测试守着（不用动）

证据位置：common/interceptors/idempotent.interceptor.ts · apps/miniprogram/src/api/request.ts:9

这条我原本怀疑会出问题，逐段追下来发现三段齐全，是同类实现里写得比较完整的：

环节实现为什么这样是对的
① 占位 :71 setNx(key, '__pending__', 600) Redis 分支用的是 SET key val EX ttl NX（:123）—— 单条命令原子，并发下只有一个请求能拿到锁
② 回填 :78 成功后把首次结果写回该键 重复命中时返回 10006 + data=首次结果，HTTP 仍是 200，端上按成功处理 ⇒ 用户不会看到「下单失败」但钱被扣了
③ 失败删键 :80-86 业务抛错时 del(key) 注释写得很清楚：不删的话键会一直停在占位态，用户改完再提交就永久卡死。删掉后「失败可重试、成功仍被缓存」
端上配合也是对的（这是最容易做错的一环）：
  • 下单页持有同一个键（order-create.vue:193 声明、:380 生成一次），不每次点击都换
  • 请求层 request.ts:9 明确：10006 且携带 data 时按成功解包 ⇒ 回放不会误触发「换键重试」，不会重复建单
  • 只在服务端已明确拒绝（code > 0 且不属回放）时才换键（:341）
而且它不是「看起来对」，是有断言守着：
  • scripts/e2e-m1.mjs:540 —— 断言同键重复下单 code === 10006 且回吐原 orderNo
  • e2e-m1.mjs:551 —— 断言回放走 HTTP 200
  • e2e-m1.mjs:582 —— 断言「一人一日可多单」：换键再下能成功建单，且不是幂等回放

最后这条尤其关键 —— 它把「防重复」和「允许多单」这对矛盾需求同时钉住，任何一侧改坏都会立刻报红。这是本项目少见的高质量断言。

两条次要观察（不建议现在动，记着即可）：
  • 18 处 @Idempotent 中 12 处是 required: false，包含提现审批四连、退款审批、强制退款等资金动作。目前靠管理后台的 axios 拦截器自动注入键才生效；若有人用脚本 / curl 直调接口，这些动作没有幂等保护
  • 管理后台自动键不含操作人身份（键 = 分钟桶 + 请求哈希）：两个管理员在同一分钟对同一动作各点一次，第二次会被判重复并回放首次结果。不会重复执行，但运营会看到「请勿重复提交」而困惑

I2 · 统计数字与订单同源，没有滞后（不用动）

证据位置：modules/stats/stats.service.ts:225（口径注释） · :229-234（判定实现）

你看到的报表数字会不会和订单真实数据对不上？核下来的结论是不会，原因是它没有走任何中间层：

  • 数据源是 dataSource.getRepository(Order).createQueryBuilder('o') —— 直接查订单表，不是快照表、不是汇总表
  • 反向验证：全文 grep cache / kv. / snapshot 零命中 ⇒ 没有缓存，不存在「数字滞后于真实订单」的窗口
  • 「什么算有效订单」只有一处判定（validOrderQb()），四个统计端点共用。源码注释原话：「不许多处实现」
这一条之所以值得单独说：统计口径最常见的坑不是算错，而是同一件事有多份实现（列表页一套、看板一套、导出一套）， 改了一个忘另两个，两边都不报错。这里主动收敛成一处，是预防性的正确写法。

X6 · 操作日志表没有任何清理策略（建议补，低优先级）

证据位置：apps/api-server/src/tasks/ 全目录 · 对比 modules/track/page-track-cleanup.task.ts

第三批我核实了「日志写失败只打 WARN」（X3），这次顺带查了它的上游 —— 这张表会不会一直涨：

表清理策略说明
ab_page_track（匿名埋点） 有 page-track-cleanup.task.ts 每日 03:30 清理，保留 180 天（与隐私条款声明一致）
ab_operation_log（操作审计） 无 全仓 tasks/ 目录与全量代码中零清理任务；且该表不只有后台操作 —— 跑批对账不平也会往里写（reconciliation.task.ts:54）
为什么值得记一笔（虽然不紧急）：审计日志的特殊性在于 —— 它既不能随便删，又不能一直涨。 匿名埋点可以「满 180 天就清」，操作日志往往有留存要求，但现在的状态是「没有任何策略」， 等真正出问题（表大到影响查询、或磁盘告警）时再临时决定，容易两头不讨好。
建议：
  • 先拍板留存期（建议 1–2 年，与财务对账周期对齐），再照 page-track-cleanup 的样子写一个归档任务
  • 更稳的做法是先归档再删（转存到对象存储），审计数据删了就真没了
  • 顺带给 X3 补上监控：日志表「每日新增条数」做一个心跳，条数骤降即说明写入在静默失败

核实方法与已排除的误判

  • 生产配置实查：docker-compose.prod.yml:109 明确 QUEUE_DRIVER: redis，redis.config.ts:17 默认也是 redis ⇒ 生产确实是分布式 KV，X5 只会在抖动后发生，不是常态
  • 本批排除的两条误判：
    • 一度怀疑「端上每次点击都换新键导致幂等形同虚设」—— 追到 order-create.vue:193/380 确认键是页面级持有，不是每次生成，判断不成立
    • 一度怀疑「管理后台自动键会串到别人的操作」—— 确认键含 method+url+body，不同目标单号键就不同，风险仅存在于同一分钟完全相同的重复点击，而那正是要拦的场景
  • 反向验证：degraded = true 7 处 / 运行期复位 0 处（支撑 X5「不可复位」）；grep cache|snapshot 在 stats 服务零命中（支撑 I2「无缓存」）
