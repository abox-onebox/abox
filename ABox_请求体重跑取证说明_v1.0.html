版本 v1.0　|　日期 2026-10-27　|　编写：严过关（测试）　|　对象：外部测试同学
一句话结论。你报的那条 10001，我们已经用「带体 / 不带体」两组对照在现网完整复现出来了： 同一个坏体打到订单列表上，一样报。所以它不是订单详情专有的 bug，而是「请求体不合法」时全站统一的表现。 现在只剩最后一环没闭合：到底是哪个调用方给这两个 GET 带上了体。这一环只有你的工具能给出答案 —— 所以请你按下面四步再跑一次。

一、请你帮四件事（按优先级）

  1. 贴出调用片段原文（python requests 代码 / curl 命令 / Postman 配置截图，任一即可）。
  2. 跑一条自查命令，确认你的工具给这两个 GET 到底带了多少字节的请求体（命令见第四节，三种工具各给了一条）。
  3. 用你原来的方式重跑一次，并告诉我们精确的本地时间戳（精确到秒）和你的出口公网 IP。
  4. 顺手回一句：你当时访问的是 8081 端口，还是某个域名？中间有没有走代理 / 网关 / 抓包工具？
为什么会需要你重跑。我们查了现网保留的 nginx 访问日志，里面没有你那批请求： 日志只保留了最近约一小时，而这一小时里所有 /api/ 请求都是我们自己的 curl（来源 172.18.0.1、User-Agent curl/7.81.0）；其余外部 IP 只有端口扫描噪声（RDP 探测、CONNECT 探测），没有任何一条打到订单接口。 也就是说：服务端目前根本留不下这条痕迹（原因见第七节「我们无条件认领的缺陷」）。这不是托词，是我们确实缺证据，所以需要你那一侧的原始数据。

还有一个能直接帮你定位的细节

同样是「把 token 塞进体里」，两种塞法报出来的文本不一样。你可以拿自己那条报错文本对一下，就知道自己属于哪种：

你发的体是什么形态 服务端返回的 message
带引号（JSON.stringify(token)）
即体是 "eyJhbGciO..."		 Unexpected token '"', ""eyJhbGciO"... is not valid JSON
← 与你报告里的文本完全一致
不带引号（裸 token）
即体是 eyJhbGciO...		 Unexpected token 'e', "eyJhbGciOi"... is not valid JSON
（与你报告的文本不同，可排除）
发了体，但没声明 Content-Type: application/json 根本不会走到这一步，会直接返回 10002 未登录或登录已过期
（也可排除）
由此可以确定的三件事。 你的工具在那两个 GET 上：(1) 带了 Content-Type: application/json； (2) 体是一个 被 JSON 引号包起来的字符串，不是裸 token； (3) 体的长度约等于「token 长度 + 2」字节（我们用现网 token 实测是 243 字节）。
在 python requests 里，这恰好就是 requests.get(url, headers=..., json=token) 的效果 —— json= 参数对一个字符串会做 json.dumps，于是体变成 "eyJ..."， 同时自动带上 Content-Type: application/json。这是目前头号嫌疑写法，麻烦你优先核对这一处。

三、请提供调用片段原文（第一优先）

以下任一形式都可以，越原始越好，不用整理：

  • python：那段发请求的原始代码（含 headers=、json= / data=、params= 的整行）。别删掉你写死 token 的那几行。
  • curl：整条命令行（可以把 token 打码成 eyJhbGciO...，保留前后各 8 位就够）。
  • Postman：请求配置截图（重点是 Body 标签页和 Headers 标签页）；或者更省事 —— 点右上角的 </> Code，把生成的 curl / python 片段整段贴过来。
  • 其它工具（JMeter / Apifox / 自研脚本 / 抓包文件）：把请求原始报文（Raw）贴过来即可，我们只看请求行 + 头 + 体。

如果那份脚本已经不在了也没关系 —— 直接做第四节的自查，同样能拿到结论。

四、一条你能自己执行的自查命令

目的很单纯：让你的工具自己说出「我给这个 GET 带了多少字节的体」。四条按你的工具挑一条，不用全跑。

4.1 通用办法（推荐，不挑工具）：本地起一个「原始请求回声」

把下面内容存成 echo_req.py，然后 python echo_req.py：

import socket

s = socket.socket()
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(('127.0.0.1', 8899))
s.listen(5)
print('正在监听 127.0.0.1:8899 ，请用你的工具打一次请求后按 Ctrl+C')

while True:
    c, _ = s.accept()
    raw = c.recv(65535)
    head, _, body = raw.partition(b'\r\n\r\n')
    lines = head.split(b'\r\n')
    print('--- 收到一个请求 ---')
    print('请求行        :', lines[0].decode('utf-8', 'replace'))
    for L in lines[1:]:
        low = L.lower()
        if low.startswith(b'content-length') or low.startswith(b'content-type'):
            print('请求头        :', L.decode('utf-8', 'replace'))
    print('请求体字节数  :', len(body))
    print('请求体前80字节:', body[:80])
    c.sendall(b'HTTP/1.1 200 OK\r\nContent-Length: 2\r\n\r\n{}')
    c.close()

然后只把那两个 GET 的 base URL 换成 http://127.0.0.1:8899，用你原来一模一样的写法打一次（token 请照常从真实环境登录后取，别把登录也指过来）。 看输出里的「请求体字节数」：

  • 是 0 → 你的工具没带体，那这个报错另有来源，请把这个结果发我们，我们立刻按第七节的判据自查。
  • 大于 0，且前 80 字节以 "eyJ 开头 → 就是它了，请把这段输出截给我们，并回看第三节对一下写法。

4.2 如果你用 python requests（最省事）

在你原来的那行请求后面加三行，别改请求本身：

r = requests.get(url, headers=headers, json=token)   # ← 你原来的写法，一字不改

print('method         :', r.request.method)
print('Content-Type   :', r.request.headers.get('Content-Type'))
print('body 字节数    :', len(r.request.body or b''))
print('body 前 80 字节:', (r.request.body or b'')[:80])

如果 body 字节数 不是 0，而你的本意是把 token 放进请求头 —— 把 json=token 换成 headers={'Authorization': 'Bearer ' + token} 即可。（顺带一提：params= 才是放查询参数的正确位置。）

4.3 如果你用 curl

curl -v -X GET "http://<host>:8081/api/v1/orders/<orderNo>" \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" 2>&1 | grep -E "^> (GET|POST|Content-Length|Content-Type)"

出现 > Content-Length: <非0> 就说明带了体。 注意：单靠 curl 的 -X GET 不会凭空产生体，只有写了 -d / --data / --data-raw 才会有 —— 我们也正是靠这一点确认「curl 复现不出来」。

4.4 如果你用 Postman

  • 打开 View → Show Postman Console，发一次请求，在 Console 里看该条请求的 Request Body 与 Size。
  • 或者直接在请求右上角点 </> Code，把生成的片段贴给我们 —— 这个最快。
  • 顺便看一眼 Body 标签页：GET 请求通常应该是 none，如果那里是 raw 且写着 token，就是它。

4.5 我们这边同步在做的事（$request_length）

运维正在 nginx 侧补 $request_length 字段（记录每个请求的入站总字节）。补完之后， 只要你告诉我们重跑的精确时间戳和出口 IP，我们就能在 nginx 日志里直接读出那条 GET 的体长， 不需要你做任何额外操作。这条是给「万一上面几条你都不方便跑」留的兜底路径。

五、为什么浏览器 / 客户端 App 复现不出来（不是推卸，是物理上发不出）

我们知道「你报了但我们复现不出来」这种对话最容易变成互相怀疑，所以这里把原因说透 —— 结论是：浏览器和我们的客户端在这个场景下，结构上就发不出这个体。

5.1 框架层面：uni-app 对 GET 硬编码不带体

我们 H5 走的是 uni-app，它内部的 uni.request 实现里，请求体是这样组装的：

// node_modules/@dcloudio/uni-h5/dist/uni-h5.cjs.js:12386-12387
let body = null;
if (method !== "GET") {            // ← 只有非 GET 才去组装 body
    ... body = JSON.stringify(data) ...
}

// node_modules/@dcloudio/uni-h5/dist/uni-h5.cjs.js:12453-12454
xhr.send(body);                    // ← GET 时这里就是 xhr.send(null)

也就是说：GET 的 body 从一开始就是 null，最后发的是 xhr.send(null)，一个字节都不会带。 这不是我们代码的选择，是框架写死的。所以你在手机浏览器里点、在微信开发者工具里点，都点不出这个体。

5.2 我们代码层面：又加了一道闸

// apps/miniprogram/src/api/request.ts:194
data: method === 'GET' || method === 'HEAD' || method === 'OPTIONS' ? undefined : data,

GET / HEAD / OPTIONS 一律把 data 抹成 undefined，双保险。 （顺带说清楚：这道闸是今天事故复盘时加的，还没进现网镜像，所以它不是「现网早就安全」的证据 —— 真正的证据是 5.1 那一条框架行为。）

5.3 一句话总结

能带体的只有「手写请求」这一族。浏览器、uni-app、curl（不写 -d）都属于「天然不带体」； 而 python requests 的 json=、Postman 里 Body 填了 raw、JMeter 里配了 Body Data， 都属于「会带体」。这两族的差别决定了谁能复现、谁不能 —— 所以这件事只能靠你那边的调用片段来定论。

六、我们要找的是「哪个调用方」，不是追究谁的错误

请把这一节当成我们这边的正式表态：我们找的是那个会带体的调用方，不是找人背锅。
  • 为什么非找不可。只要还有任何一个调用方在给 GET 带体，它就随时会再报一次 10001 —— 而这一次我们仍然查不到（服务端不打日志，见第七节）。留着这个盲区上线，下一次没人能定位。
  • 我们这边的账已经记在自己头上了。不管最后查出来是谁带的体，服务端有两条缺陷无条件认领（第七节），正在改，与你的结论无关。
  • 需要你提供的就一件事。哪个脚本 / 哪条 Postman 请求 / 哪个工具在给这两个 GET 带体。告诉我们就行，不需要解释为什么这么写。
  • 如果最后查出来是我们自己的脚本带的体（比如某个我们忘了的联调脚本 / 巡检脚本），那结论同样成立，我们照改，一样谢谢你把它逼出来。

七、什么情况下这确实是我们的问题（请你反过来验证我们）

我们不希望这份说明变成单方面结论。下面每条都是可证伪的判据：只要命中任意一条，那就是我们的问题，请直接把证据甩回来，我们按 P0 处理。

编号 判据（命中即为我们的缺陷） 你怎么验
C1 不带体也会报。你的请求 Content-Length: 0 或压根没体，仍返回 10001 4.1 回声脚本显示「请求体字节数: 0」
C2 标准客户端能复现。用手机浏览器或微信开发者工具（不手写任何请求）点到订单详情页就报 录屏 / F12 Network 截图
C3 POST 带合法对象体也报。POST 一个正常 JSON 对象仍返回这个报错文本 任意 POST 接口试一次
C4 报错文本不是这一句。你拿到的 message 不是 Unexpected token ... is not valid JSON，而是别的 10001 文案 贴原始响应
C5 nginx 侧体长为 0。补完 $request_length 后，你重跑那条 GET 的体长是 0（说明服务端把空体也判成了非法体） 给我们时间戳 + 出口 IP
C6 不带登录态也报这个。不带 Authorization 时，我们这边正常应该返回 10002 未登录（HTTP 401）；若返回的是 10001，说明鉴权链路上还有别的坑 去掉 Authorization 打一次

我们无条件认领的两条缺陷（与上面判据无关，正在改）

缺陷一：这个分支不打日志。实测现网 api 容器日志里 Unexpected token 出现 0 次、10001 出现 0 次 —— 而我们当天已经打过去几十次这样的请求。 也就是说：这类请求在服务端不留任何痕迹，出事只能靠调用方自述。这是本次最该改的一条，与谁带的体无关。
apps/api-server/src/common/filters/all-exceptions.filter.ts:70-71（HTTP 400 分支只映射成 10001，未打日志）
缺陷二：把框架英文原文原样下发给调用方。 Unexpected token '"', ""eyJhbGciO"... is not valid JSON 是 Node 框架的内部原文， 既没本地化，又把体内容回显了出去。无论调用方是谁，收到这句都只能猜。
链路：body-parser/lib/types/json.js:83-90,156-176（严格模式拒绝顶层非对象并二次拼装报文）→ @nestjs/core/router/routes-resolver.js:94-101（把任意 SyntaxError 统一映射成 400）→ all-exceptions.filter.ts:70-71（转 10001 并原样下发）
