三、必测项

3.1 一键停售（新增 · 重点）

后台新增「系统 → 一键停售」页。运营填写停售原因后全局拦新单，落独立表 ab_sales_pause。

v1.0 的坑：停售不是「即时开关」，是「按出餐日的区间」
创建时必须填 mealDateFrom / mealDateTo（两端含首尾，同一天＝只停一天）。
若停的是未来某天，当天仍然可以下单——这是正常的，别判成「停售无效」。 （真身：sales-pause.dto.ts:38-46）
  1. 后台 系统 → 一键停售，填起止日期（建议就填今天）+ 原因（例如「今日备货不足」）并提交
  2. 打开小程序首页：应看到停售提示，且带有刚填的那句原因
  3. 尝试下单：应被拦下，提示语里同样带原因
  4. 后台对这条记录执行「恢复接单」
  5. 小程序首页与下单应恢复正常
  6. 反向 A：起始日晚于截止日 → 应报错 10001，提示「停售起始日不能晚于截止日」，后台不应显示成功
  7. 反向 B：对已恢复的区间再点一次「恢复」→ 应提示「该停售区间已恢复，无需重复操作」，不应静默成功
  8. 权限：用 operator 账号调「创建停售」→ 应被拒（有意收窄，正向用例）
预期
停售期间下单报 60009，提示形如「今日暂停接单：备货不足」。 运营没填原因时回落「当前已暂停接单」——两种都算正确。
停售立即生效（该服务刻意零缓存）；不影响存量订单，见第六节。
（反向 B 真身：sales-pause.service.ts:96-98）

3.2 楼宇停用闸门（新增 · 本节四步已全部重写）

最重要的一条：判据不是「楼里有没有订单」，而是「订单处在哪个阶段」
闸门按固定优先级全序求值，顺序不能调换。把订单分成两组：
  • B 组（未截单，运营可撤回）：待支付、已支付、退款申请中、退款中
  • A 组（已履约，不可撤回）：已截单、已出餐、配送中、已送达
只要有一笔进了 A 组，就一票否决报 60013，勾「强制停用」也没用。 （真身：suspend-gate.ts:18-31 分组清单、:111-117 全序）
按此顺序做，每步先看清订单处于哪个组：
  1. 造 1~2 笔 B 组订单（待支付 / 已支付 / 退款中，都还没截单）→ 停用该楼 → 应报 60006（楼群则 60007）
  2. 造 1 笔 A 组订单（已截单及之后）→ 停用 → 应报 60013（最高优先，force 也无效）
  3. 后台把 building.suspend_force_max_count 临时调成 2（默认 20，后台配置页可改），再造 3 笔全部是 B 组的订单 → 停用 → 应报 60012（需走审批）
  4. 同第 1 步（1~2 笔 B 组订单）时勾选「强制停用」 → 应放行成功，且操作日志有记录
预期 · 四条各对应一种结果，别串
① → 60006　　② → 60013　　③ → 60012　　④ → 成功
第 3 步最容易做错：混进一笔 A 组订单就会被 60013 截走，拿不到 60012。 造数据前先确认每笔订单的状态。
（阈值默认 20 真身：biz-config.service.ts:183；forceSuspend 入参：building-admin.dto.ts:289 / :444）

3.3 X 盲盒（新增）

  1. 正常下一单
  2. 打开订单详情：应看到盲盒一行，状态为「待揭晓」，看不到内容
  3. 团长点「送达」后再看：应显示具体盲盒名，状态变「已揭晓」
  4. 首页对应位置也应显示该盲盒格位
  5. 抓包验证（v1.1 新增）：用任何抓包方式看订单详情的响应体——送达前 blindBoxName 应为 null
预期
送达前不得泄露盲盒内容——这是它全部的意义所在。
同时：没有集盒、勋章、弹层这些额外东西，只出现在首页一格和订单详情一行，别处出现即为异常。
第 5 步的判据（服务端已修，本步是回归验证）
首轮审阅发现：该字段此前无条件下发，「送达前不泄露」完全依赖小程序端不显示，抓包即得。
现已改为服务端遮蔽：送达（delivered / completed）之前 blindBoxName 一律为 null；是否含盲盒改由 blindBoxPending 下发（只有 true/false，不含内容）。
⇒ 第 5 步应看到 null。若送达前就抓到内容，即为缺陷，请照实报—— 不要因为「界面上确实没显示」就判通过。

3.4 代金券（新增 · 重点）

独立的券系统。券有三个来源：推荐返券、客服补偿、后台手动发放。

  1. 后台 财务 → 代金券：建一个券种，并手动发一张给某个测试用户
  2. 该用户登录小程序，我的 → 我的券：应能看到这张券
  3. 用该用户下单：应自动抵扣，订单详情里能看到优惠金额
  4. 取消这笔订单：券应退回，回到「我的券」里可用
  5. 再走一次退款流程，且退款被驳回：券不应退回
预期
下单时系统自动选抵扣最多的那张，用户端不做选券控件（守「表单只有份数」的规矩）。
三种取消路径都必须退券：用户自助取消、截单兜底自动取消、退款审批通过。
第 5 步是关键的反向用例：退款驳回时券不能退——退了就是白送钱。 （三处退券真身：order.service.ts:680 / :863 / refund.service.ts:798，最后一处的宿主是审批通过而非建单）

3.5 去餐化（改版）

  1. 确认小程序内已不存在「供应商列表」「溯源」入口
  2. 后台 供应商 → 门店实拍照片：上传照片、整组替换
  3. 首页查看今日菜品：能打开看到今天吃什么

  2. 进入招募页：CTA「成为团长」一屏内只出现一次
  3. 从招募页进入推荐中心：非团长身份也应能推荐并看到记录
预期（文案红线）

这些是提审红线或已纠正过的错误设定，命中即为缺陷。交付口径统一是「团长送到你工位」。

3.7 停用后能否下单（本次修复本体 · v1.0 遗漏，v1.1 补齐）

这是本次提交 6b37218 修的那个 bug，必须验

  1. 后台停用办公楼 A
  2. 用 A 楼的用户账号下单 → 应被拦，报 60010「该办公楼已停用时不可下单」

  4. 造一栋未配置楼群的楼，用其用户下单 → 应报 60011「该办公楼暂未开通服务，请联系运营」
