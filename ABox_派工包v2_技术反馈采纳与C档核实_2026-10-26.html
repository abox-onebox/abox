三、A2 验收脚本已重写为「验收模式」—— 11/11 全绿

修复前的脚本是复现缺陷用的（期待它红）；修复后它必须守住不回退（期待它绿）。 按技术提醒，我重写了它 —— 否则它会一直红着，让人误以为缺陷还在。 连跑 3 次 EXIT=0，稳定不抖动。
断言守什么
① Redis 不可达 ⇒ setNx 必须抛错fail-closed 的核心；静默返回 true 即等于放行重复扣款
② setNx 不得返回布尔值防止有人改成「返回 false 假装没抢到」，那同样会静默放行
③ 两实例至多一个拿到锁互斥本体（原缺陷的 ③ 就是这里）
④ setNx 体内不得递归调用自身静态守住：降级路径不许被加回来
⑤ 存在 driverIsRedis 显式隔离保证 redis 驱动下永不读内存
RV-b2 / RV-c（新增）回答技术问的「要不要重启」：断言故障后 degraded 无残留 + setNx 体内既不读 degraded 也不走 useMemory()。
⇒ 没有任何需要靠重启才能清除的状态，Redis 一恢复、下一次调用即生效
RV1 探针有效性（改用 memory 驱动）共享存储下同键第二次必须 false。改驱动是因为不再依赖网络行为，语义更精确且不会 flaky
过程中我自己踩的坑（已修，写出来免得重蹈）：
  • lazyConnect:true ⇒ 不发命令 ioredis 根本不连接，轮询 status 永远等不到 ready，会误判「连不上」。
  • server.close() 只停止接受新连接，不断开已有连接 ⇒ 模拟不了「Redis 挂了」，必须自己记账 socket 并 destroy。

六、X1 换绑楼清空团长 —— 我给的判定：现在不改代码，改注释

user.service.ts:139-148 换楼时清 teamLeaderId: null，日志与接口摘要都写着「待重算 / 按新楼重算跟随团长」， 但全仓无任何重算实现。
为什么不急着改：清空后用户下次下单会走 resolveLeader() 三级兜底，落到新楼在职团长 —— 结果是对的（佣金确实归新楼的人），所以不会「记错楼」。
真正该改的是误导性表述：注释承诺了不存在的「重算」，后续维护者会以为有兜底而放松警惕。
建议：把「待重算」改成「清空后由 resolveLeader 兜底重解析」，成本近乎为零。
若要「归给邀请我的人/最近合作过的团长」——那是新功能，另行派工。
