一、总体判断

这份文档的工程水准高于常见的「差不多能测」水平——第零节三条口径打底、错误码表 13 码齐全、第六节预先划出「不用报」的边界、第七节要求反馈带 code 而不是只截提示语，都是懂行的人才会写的。

但它有一个结构性风险：3.2 的步骤描述与代码的求值顺序不一致，且关键参数（停售日期区间、forceSuspend、停用阈值）都没交代。后果不是「测漏了」，而是测试队伍会集体把正常实现判成缺陷，或者反过来。

最严重的一条：本次修复的核心没有被安排验收。
本次提交 6b37218 修的是 N1（停用楼也拦不住下单），我回源确认这次确实修好了（见第三节）。
但错误码表列了 60010（楼已停用不可下单）/ 60011（楼未归群），第三节却没有一条步骤去验它们 —— 等于把这次最重要的修复，晾在了验收范围之外。

二、必修清单（按严重度）

#位置级别问题 · 建议改法
13.2 全节 / 五必修 求值顺序没交代 ⇒ 四步里两步会判错。
代码 suspend-gate.ts:110-116 是全序：A 组（已履约）>0 → 60013（最高优先）→ N=0 放行 → N>阈值 → 60012 → 其余未 force → 60006/60007。
⚠️ 文档第 1 步写「有未完结订单 → 60006/60007」只在订单都还没截单时成立；只要有一笔进了履约阶段，拿到的是 60013。
改法：把第 1 步改成「造 1~2 笔未截单的订单（待支付/已支付/退款中），停楼 → 60006」；并把第 3 步提到最前面，注明「这是优先级最高的一票否决」。
23.2 第 2 步必修 阈值没给 ⇒ 这一步造不出来。阈值是配置 building.suspend_force_max_count，默认 20（biz-config.service.ts:182-184，后台配置页已上架）。
改法：写明「默认 20；为便于构造，可临时在后台把该值调到 2」，并注明必须全是未截单订单——混进一笔已履约的就会被引到 60013。
33.2 全节必修 完全没提 forceSuspend（强制停用）。这是运营的逃生舱：1 ≤ N ≤ 阈值时勾上它，停用会被放行（allow_forced，带审计+通知）。
这是会真放行的分支，零覆盖。建议补一条：「在 1 ≤ N ≤ 阈值时勾选强制停用 → 应成功，且操作日志有记录」。
43.1 第 1 步必修 停售不是「即时开关」，是「按出餐日的区间」，而文档只说「填原因并提交」，没说要填起止日期。
后果很直接：测试人员停在明天，今天照常能下单，会立刻判成「停售无效」。代码是 mealDateFrom / mealDateTo 两端含首尾。
改法：步骤写成「填起止日期（含首尾，同一天=只停一天）+ 原因」，并加一句「若停的是未来某天，当天仍可下单，属正常」。
5五 / 第三节强烈建议 补 60010 / 60011 的验收步骤（见下节第 3 条这是本次修复本体）。
建议新增 3.7 节，手写「后台停用 A 楼 → 该楼用户下单 → 报 60010」「楼未归群 → 报 60011」。
63.3强烈建议 「送达前不泄露」只验 UI，拦不住真泄露。服务端 order.service.ts:540 是 blindBoxName: order.blindBoxName ?? null —— 无条件下发，没有按状态遮蔽，「没泄露」完全靠小程序端不显示。
这意味着任何人抓一次响应体就能提前知道内容（隐藏 ≠ 拦住）。
改法：加一条「用任何抓包方式看订单详情响应体，送达前 blindBoxName 应为 null」。若确实要求保密，应由服务端在 DELIVERED 前不出参——这条要不要改，请您拍板。

三、实证：按文档步骤，代码实际给什么码

我没有靠推断。写了一个临时探针直接调 decideSuspend 真跑（跑完已删除，工作区干净），输出如下：

[订单状态=cut_off（已履约）]     total=1  A组=1  ⇒ 60013  ⚠ 文档写的是 60006

[21笔，含1笔已履约]             total=21 A组=1  ⇒ 60013  ⚠ 文档写的是 60012

补 3.7 · 停用后能否下单（本次修复本体，原文档缺失）
