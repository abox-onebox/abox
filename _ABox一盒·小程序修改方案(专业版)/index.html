ABox 一盒 · 小程序修改方案（专业版）

替代原创意发散式建议 · 重新定位供应商/溯源页 + 落地首页「天地盖」布局 · 2026-10-10

零、决策基线与范围澄清

本方案替代此前「创意发散 129 条」式的不专业建议。此前那轮问题不在"点子少"，而在 没有边界、没有合规判据、把"数据同源"误当"同一页面"。本方案以三条硬约束为底盘： ① 单一套餐（一饭四菜，用户只能订或不订）；② 预售制（T-1 24:00 截单，次日 11:30 送达）； ③ 小程序合规铁律（见附录）。

0.2 本方案范围

  • 第一部分：供应商/溯源页新功能方向（替换"展示资质"）—— 含功能要点、页面定位、合规与风险、落地步骤。
  • 第二部分：首页修改建议（天地盖布局）—— 基于 v0.1→v0.4 迭代沉淀的专业复盘 + 最终推荐 + 待拍板项。

第一部分 · 供应商/溯源页重新定位

原页面唯一功能 = 展示供应商资质（许可证号、有效期）。这一功能信息密度低、冷感、且与合规强绑定， 被砍掉跳转外卖后更显单薄。若资质并入首页，该页必须找到一个不与首页重叠、且能变现或增益信任的新核心。

原则：首页是"今天下单"的转化页，供应商页应是"明天期待 / 品牌信任 / 增量营收"的内容页或工具页——两者各司其职，不抢同一块屏幕。

方向 A ·「明日出餐阵容」预告页 零合规风险 内容页

页面定位：预售制下的"明天吃什么"内容页，承接首页"今日下单"之后的期待感。首页答"现在订什么"，本页答"明天谁来做、值不值得期待"。

功能要点

  • 明日四格菜的厨房来源预告：哪家厨房出哪一道（与首页四格对应，但不重复下单功能）。
  • 厨房人物卡：主厨 / 档口故事（非冷冰冰的许可证号），传递"有人在做饭"的温度。
  • 信任凭证替代资质：用"这栋楼吃过 860 次 · 在供 240 天"这类行为数据替代证件号——同样是真凭实据，但轻、有人味、不触发合规敏感。
  • 订阅"明日菜单提醒"：微信订阅消息（一次性授权，点一次收一条），把"每周只开一次"的痛点变成"每天开一次"的轻触达。

为什么专业：首页是转化页、本页是内容页，不重叠；纯展示无第三方跳转，合规安全；复用首页已有的 dishes / supplierName 数据，零新增契约。

方向 B ·「合作商家到店券 + 核销」营收页 需先解定性 工具页

页面定位：把 ABox 手里"别人拿不到的写字楼午间流量 + 信任"变现的轻资产营收页。这是此前对话里唯一真正成立的创意——不是功能堆砌，而是资产变现。

功能要点

  • 合作商家的到店消费券（午市折扣 / 第二份半价 / 满减），以 ABox 自有权益形式发放。
  • 用户领券 → 到店核销（核销码 / 扫码），ABox 赚取核销抽佣。
  • 单位经济（来自 SPEC 真数）：核销抽佣 ≈ ¥250/楼/月；对比此前"首页位置包月 ¥500×5 = ¥2,500/栋/月"—— 两者差 10 倍，但这是纯增量营收，不与位置广告冲突，可并行。
注意 合规铁律（这一条是原创意专家完全没提的，也是本方案的核心专业增量）：
若 ABox 帮合作商家"发券并抽佣"，极易被认定为网络食品交易第三方平台 → 触发 EDI 证 + 网络食品交易第三方平台备案 + 二清（整套创意里最大的雷，会直接拖垮 MVP 节奏）。

安全做法（二选一）：
① 自营买断：ABox 以自营名义向商家采购买断券，再作为 ABox 自有权益发放/售卖 → 性质变为 ABox 自营营销，规避平台定性；
② 广告/引流服务：明确是"广告服务"而非"交易"，券的交易在商家自己系统完成，ABox 只收广告/服务费（需规范合同与发票，且小程序内不得出现第三方平台名称/标识/链接/可跳转物/可复制口令——铁律）。

落地步骤（建议小步）：

  1. 先选 1–2 栋楼试点，仅接入 1 家合作商家，跑通"领券→到店→核销→对账"。
  2. 同步法务确认采用"自营买断"还是"广告服务"定性，写进《团长合作协议》补签条款。
  3. 核销流程接入现有结算（佣金自动结算通道已具备），不新建支付链路。
  4. 数据跑通、合规口径落地后，再扩楼、扩商家。

方向 C ·「这一盒的来路」深度溯源故事 品牌信任 内容页

页面定位：品牌信任页，讲"食材从哪来、谁做的、怎么到的你手上"，服务于高端极简的品牌调性。

功能要点

  • 食材产地 / 供应商故事：用叙事替代证件号（冷→暖）。
  • 食安旅程时间线：采购 → 加工 → 配送 → 到楼，可视化时间轴。
  • 检测报告：以"凭证"形态呈现（非许可证号列表），呼应合规但不堆砌。

与方向 A 的关系：A 是"明天吃什么"的轻预告，C 是"为什么信得过"的深层故事。建议 C 作为 A 的深化模块（点厨房人物卡展开来路），而非独立成页，避免页面过多。

1.3 若你最终保留中栏版（"来自：X ›"仍跳溯源页）

则供应商页未冗余，第一部分从"重新定位"转为"增强"：保留资质展示，叠加方向 A 的"明日出餐阵容 + 厨房人物卡 + 订阅提醒"， 把"冷证件页"升级为"有温度的出餐档案页"。方向 B（到店券）仍可作为独立入口，不依赖首页是否吸收资质。

1.4 供应商页待拍板项

  • 首页最终走 B 稿（资质并入）还是中栏版（保留跳转）？—— 决定本页是"重新定位"还是"增强"。
  • 方向 B 的定性（自营买断 vs 广告服务）需法务确认，是 P2 能否启动的前提。
  • 订阅消息开通需产品侧确认文案与订阅场景（一次性授权限制）。

第二部分 · 首页修改建议（天地盖布局）

基于与创意专家的对话沉淀（v0.1→v0.4），此处给出专业复盘 + 最终推荐，而非再次发散。核心结论：首页布局 = 产品形态布局（天地盖：上两排四格菜 + 底部通栏米饭），既展示菜品，又让用户一眼认出"我们就是这么一盒"。

2.2 最终推荐方案（v0.4）

核心思路：两层分离

层级装什么本版处理
内容层
（这盒里有什么）		天盖日期 · 四格菜 · 米饭四格 1:1 实拍图 + 底部通栏米饭（纯展示，无任何控件）
决策层
（要几盒、付多少）		份数 · 应付 · 单价 · 上限独立"决策条"：份数 [− 1 +] ¥25.80 + 小字 ¥25.80/份 · 单笔最多 10 份

实物证据（最硬的依据）：天地盖实物里没有任何一格可以单独加量——不存在"米饭两份、排骨一份"。所以"份"只能是整盒的倍数，绝不可贴在某道菜旁边。这从产品物理形态上证明了 v0.3 的层级错配。

2.3 功能要点（逐项）

  • 顶部倒计时（保留并强化）：深棕底、金字等宽数字、下圆角 36rpx；取值纪律——cutoffTimeText 取不到返回空串、整行不显示、绝不回落写死值。
  • 产品形态即首页：天地盖 2×2 四格 + 通栏米饭，所见即所得，降低认知成本。
  • 四格实拍图（硬前置）：四张 1:1 俯拍图，后台菜品管理填 imageUrl。契约已存在（home.dto.ts 有 imageUrl、meal.service.ts 已下发），无需改后端、不加表。
  • 份数 / 应付决策条：控件带"份数"语义主语，不误读为某道菜的份数；单价回填小字行，比原来还省一行。
  • "来自：X ›"保留跳转（中栏版）：点击跳溯源页，不动后端；若走 B 稿则改为原地展开证照（会动后端，U1 需补发证照字段）。
  • 既有模块全保留：骨架 / 团长身份横幅 / 跟随团长卡与"本单佣金归 TA"明示 / 无团长引导 / 最大份数提示 / 已订概览 / 两个主按钮 / bottom-bar / 空态分级——只做布局形态改造，不删不减。

附录 · 小程序合规铁律（改动任何页面前必读）

第三方平台五项禁令（平台运营规范 5.10/5.16/5.20 等）：小程序内不得出现第三方平台 名称 / 标识 / 链接 / 可跳转物 / 可复制口令。违规高风险，审核必卡。
推论：方向 B（到店券）的核销与展示，绝不可出现合作商家的平台名、Logo、外链或可复制码； 供应商页"资质墙"是已实装的合规替代物，保持。
  • 自营 vs 平台定性：开放商家入驻 / 代销分账 = 平台 → 触发 EDI + 第三方平台备案 + 二清；采购买断自营 = 安全。
  • GB 28050 营养声称：打勾 = 营养声称，须有含量依据，否则虚假声称（原创意"营养打勾"因此被否）。
  • 个人信息保护法：可做聚合/脱敏洞察，不可出售可识别到个人的数据。
  • 微信订阅消息：一次性授权（点一次收一条），requestSubscribeMessage 只能用户点击同步调用。
本方案为规划文档，未改动任何代码。供应商页与首页的最终走向取决于 §1.4 / §2.6 的待拍板项。 落地前请以真机实测尺寸与法务合规口径为准。
