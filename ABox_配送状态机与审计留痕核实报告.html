本批最重要的一条（新发现 X2）：限制 AI 助手的「禁止清单」，它的解除动作没有任何审计痕迹。
OpBlocklistService.remove() 直接执行 repo.delete() —— 物理删除， 不记谁解除的、不记什么时候解除的，解除后连「这条禁令曾经存在过」都查不出来。
对比同一张表的「列入」操作（add()）是完整记录了操作人与时间的 —— 同一个文件的两个相邻方法，一个留痕一个不留，这是典型的不对称缺口。

T8 / T9 · 配送状态机的订单联动：历史缺陷 #79 确认已修好

这条我原本担心还能查出问题，核实结果反而是全项目里写得最讲究的地方之一
① 联动确实生效，而且是逐单条件更新
  • T8 发货：delivery.service.ts:869 advanceGroupOrdersToDelivering() —— 订单 cooked → delivering
  • T9 送达：delivery.service.ts:922 advanceGroupOrdersToDelivered() —— 订单 delivering → delivered
  • 两者都是：WHERE id = ? AND status = '来源态' 条件更新 + version + 1，affected = 0 就跳过
② 「静默卡死」这个历史病根是怎么被根治的
我之前提到的风险是「写条件不命中 ⇒ 一单都没动且不报错」。delivery.service.ts:779-789 专门处理了这个形状：
当 advanced === 0 时，代码会回头查 remaining 里还有几单停在来源态，并生成一句能照着排查的话回给运营 —— 「该楼群当日仍有 N 单停在『已出餐』而无法推进 —— 请先确认上游是否完成（出餐确认 / 上一段发车），订单不会替物理流程做假设」。
这正是「不静默」的标准做法：做不到要说出来，并且要说清楚卡在哪。
③ 一个我很认可的设计细节（他们主动放弃了「少写几行」）

delivery.service.ts:736-748 的注释解释了为什么 T8 和 T9 要写成两个独立方法，而不是共用一个「传目标状态进来」的通用更新：

  • 通用写法更短，但两处订单状态写入点在静态扫描下都是「动态值 · 判不出来」
  • 而门禁 state:audit 正是靠能静态判定才对得上「声明 ↔ 写入点」
  • 源码原话：「等于亲手把 #79 逃过全部门禁的那个盲区重新打开一次。不要为了少写几行，把可对账性让掉。」

我核实了这个门禁确实存在（不是注释里的空承诺）：scripts/check-order-edges.mjs —— 订单状态机「边级」对账，就是为守这个而写的。

结论：T8/T9 这条可以划掉了，不用再提。顺带一提，这两处还做到了「每次状态迁移都在事务内落 ab_operation_log」—— 见下文 X3 的对比，这里的留痕反而是最扎实的。

X2 · 真缺口：禁止清单的「解除」是一道不留痕迹的门

本批唯一建议尽快补的一条 ｜ 等级：建议排 P1 ｜ 性质：安全管控自身的变更缺少审计
这道闸门是干什么的
  • OpBlocklistInterceptor 以 APP_INTERCEPTOR 全局注册（common.module.ts:84）
  • 它专管 AI 知识助手的写操作：只拦截带 X-KB-OpBlock 头的 POST / PUT / DELETE 请求
  • 一旦某个操作码进了清单，助手就会收到 OP_BLOCKED，无法执行也无法提交审批

简单说：这是你用来约束「AI 能替你做什么」的唯一一道闸门。

问题出在哪 —— 同一个文件的两个方法，一个记一个不记
操作代码位置留痕情况
列入禁令 add() op-blocklist.controller.ts:38 → op-blocklist.service.ts:29-42 完整：写 createdBy（谁列入）+ createdAt
解除禁令 remove() op-blocklist.controller.ts:45 → op-blocklist.service.ts:44-46 零留痕：repo.delete({ opCode }) 物理删除
三个层面同时失效，这是我把它的等级定得比看起来更高的原因：
  1. 不记操作人 —— remove() 这个方法签名连当前登录人都没有取（对比同为 admin 端点的 add() 明确取了 @CurrentAdmin() actor 并传下去）。它既没挂 @OperationLog，也没取身份。
  2. 不记时间 —— 表里有 createdAt，但没有「解除时间」字段。
  3. 记录本身被删掉 —— 用的是 delete() 而非软删除（项目里用户注销这类场景用的都是 deletedAt 软删）。解除之后，连「这条禁令曾经存在过」都无法证明。
再加一层放大：这道栅栏本身是 fail-open 的。
op-blocklist.interceptor.ts:48：catch 到任何非业务异常（数据库连接抖动、查询超时）时， 日志写的是 「禁止清单查询失败，放行助手写操作」 然后继续放行。
这个取舍本身可以理解（不能查库失败就全站瘫痪），但它和「解除无留痕」叠加之后效果是： 想让助手去做一件被禁的事，只需要一个带 admin 权限的 HTTP 请求删掉那条禁令，事后查无此人、查无此事。
建议的修改（三选一，成本都不高）
  • 最小改动：给 remove() 补上 @CurrentAdmin() + @OperationLog，让它至少写进 ab_operation_log（module 建议用 'security'，便于单独筛）
  • 更彻底：把物理删除改成软删除或历史表 —— 加 deletedAt / deletedBy，或删前先插一条 op_blocklist_history。这样「谁在什么时候打开了哪道门」永久可查
  • 配套：把这个删除操作纳入现有的高危审批（operation-request）范围，而不是普通 admin 直接执行

X3 · 操作日志「留痕 ≠ 真落库」：写失败会被静默吞掉

这是「留痕不等于真落库」这个问题的准确答案 ｜ 等级：取舍合理，但建议加监控
机制
  • 全局拦截器 common/interceptors/operation-log.interceptor.ts，按 @OperationLog() 元数据决定是否落库
  • :240：整个写库过程包在 try/catch 里，失败只打一行 WARN，原文注释「旁路失败不影响业务：仅告警」
我的评价：这个取舍是对的，但缺少后半段

对的部分：不能因为日志表炸了就让「退款审批」失败 —— 这是正确的取舍，反过来实现才是错的。
缺的部分：一旦触发（磁盘满、表容量、连接池耗尽、JSON 字段异常），审计日志会静默消失，而运营和业务方完全没有感知。等到真要追责时才发现「那几天的日志是空的」。

顺带说清楚一个好消息（防炸措施其实相当到位）：
MAX_FIELD_LEN = 2000 字段截断 · 数组只留前 50 项 · 嵌套超过 4 层写 [depth-limit] · password/token/secret 自动脱敏 · IP 再截到 64 字符。
这几条把「日志自己把库写爆」的常见路径基本堵死了。剩下会触发 catch 的主要是基础设施级故障（磁盘 / 连接 / 权限），概率低但一旦发生影响是全量的。
建议（不需要改代码逻辑）
  • 给这条 WARN 配一个监控告警 —— 只要出现一次就该有人看（它平时应该是零出现，任何一次都是异常）
  • 或加一个「每日落库条数」的心跳检查：某天条数突降到 0 就告警。「恒零的检查等于没有检查」，这条正好可以用上。

X4 · 团长与用户的动作为什么查不到「谁干的」—— 结构性限制，不是遗漏

这条解释了「为什么大量端点没挂留痕」，答案和「开发偷懒」无关
全量统计（84 个写端点）
分类端点数说明
写操作端点总数84全部 controller 的 @Post / @Put / @Patch / @Delete
有 @OperationLog54拦截器自动落 ab_operation_log
无 @OperationLog · 用户/团长侧24登录、下单、支付、评价、埋点、团长申请/资料/退出等
无 @OperationLog · 后台类6见下表逐条判定
为什么团长那 24 个「挂了也白挂」
  • operation-log.interceptor.ts:63：subject = req.admin ?? (req.user?.typ === 'admin' ? req.user : undefined) ?? undefined;
  • 团长令牌的 typ 不是 'admin' ⇒ subject 恒为 undefined ⇒ 落库时 adminUserId = null
  • 而 ab_operation_log 表只有 adminUserId 一列承载主体（system.entity.ts:59-115 核过：没有 userId / leaderId 列）

结论：这不是开发漏挂，而是这张表结构上就装不下团长身份。要审计团长行为，得查业务表本身 —— ab_withdraw（提现流水）、订单状态流转时间戳、佣金 pending 明细，这些是真实可用的证据。

本轮方法论记录（第三次踩同一个坑，值得单列）

  • 统计类探针必须先看真实样本再定规则。我统计「多少写端点没挂 @OperationLog」时，连续两次写错窗口：
    ① 第一版只向上找 —— 但项目里 @OperationLog 写在 @Post 下面，误报 70 条；
    ② 第二版改成 ±6 行窗口 —— 但 refund-admin 里两者相隔 9 行，把明明有留痕的退款审批又判成了缺口；
    ③ 第三版改成「从 @Post 一直读到方法签名行」，才拿到准数 84 / 54 / 30。
    教训：先抽 3 个真实样本确认格式，再写规则；更要拿「肉眼确认有留痕的端点」做负控。
  • 「有没有 @OperationLog」不等于「有没有留痕」。高危审批用自有表，比通用日志更完整 —— 判据要落在「有没有可查的记录」，不是「有没有那个注解」。
  • 同一张表相邻两个方法，add 记录而 remove 不记录 —— 这类「不对称」是真缺口的高发形状，值得专门去找。
