我认错：前五版我默认了同一个错误前提。 我一直假设「这是一个给用户看的合规页」，然后往里塞东西——核验、口碑、排期、投票、请客、加购。 塞了五轮，你否了五轮。因为那个前提本身就是错的。 ⭐ 但更深一层的错是：我把它当成「一个页面」在做。
「出品方档案」其实是 ABox 唯一一份能被四个人同时读、且四个人都要读的资产—— 用户、团长、物业、监管。而现在它只被用在最不值钱的那一个读者身上（监管公示）， 浪费了四分之三的价值。前五版全灭，是因为我在一个只值 1/4 的地方反复装修。

为什么这版跟前五版不一样

  1. 前五版改的是「页面里有什么」，这版改的是「这份东西是谁的、要给谁用」。 前五版是同一个错误前提下的第五次迭代；这版换了前提。
  2. C 端：最好的合规页是没有页面。不跳转 = 不打断 = 不损失转化；原地展开同样满足「可查」。 让用户感觉不到合规存在，才是合规做得好的样子。
  3. 三个出口动的分别是留存、转化、获楼——这是这只生意仅有的三个杠杆， 而它们共用同一份不用新建的数据。一份成本，三处收益，这才是 1+1>2。
  4. 它没有跟你的定位拧着。「省心」是对 C 端的承诺；这份说明书对 B 端讲的是「可靠」； 给团长的是「有话可说」。三个受众、三套语言，互不干扰。
⚠️ 三条必须如实说明：
① B 端那份里的稳定性数字（99.2% / 0 次 / 0.4%）现在是示意值，真拿去谈楼必须换成真实运营数据—— 在物业面前写假数字是致命的；
② 它与 G4 企业团餐是同一条线不是两件事：这份说明书是拿客户用的，G4 是接客户用的； 它不依赖 G4 卡住的那两个前提（发票能力、已有客户）；
③ 「还有 42 道没吃过」需要 菜品池去重计数，可走「订单 → 套餐项 → 菜品」推导， 但用户未评价的菜也能算进来（不依赖评价表）——这一点要先跟后端口径对一次。
