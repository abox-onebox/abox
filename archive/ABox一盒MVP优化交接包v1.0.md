## 一、30 秒读懂项目

**一句话**：办公楼白领的「团体订餐」小程序——每天一栋楼共享一个「一饭四菜」套餐，4 家供应商各出一菜，在集散中心打包装箱，货拉拉送到楼下，楼里的团长取餐分发；平台赚差价，团长赚佣金。

**业务时序（关键锚点）**

| 节点 | 时间 |
| --- | --- |
| 开团 / 下单窗口开始 | T-1 14:00 |
| **截单（关键锚点 1）** | **T-1 24:00** |
| 供应商出餐 → 送集散中心 | T 日 06:00–09:30 |
| 货拉拉叫车（线下） | T 日 10:00 |
| 兼职打包完成 | T 日 11:00 |
| 送达办公楼 → 推送取餐通知 | T 日 11:30 |
| 团长取餐窗口 | T 日 11:30–12:30 |
| **自动确认收货 + 佣金结算（关键锚点 2）** | **T 日 14:00** |
| 财务跑批（分账 / 打款） | T+1 02:00 |

**4 个角色（无楼长）**

| 角色 | 载体 | 核心动作 |
| --- | --- | --- |
| 用户（白领） | 微信小程序 | 微信授权即注册、1 步下单、看状态 |
| 团长（按办公楼） | 同一小程序（叠加身份） | 分享拉单、取餐分发、确认收货、赚佣金 |
| 商家（供应商） | Web 后台 | 看明日备料量、确认出餐、查分账 |
| 平台运营 | Web 后台 | 套餐编排、订单管理、财务结算、数据看板 |

## 五、本次优化任务书

> 已勾选 A / B / C / D。建议按 **B → A → D → C** 推进（B 是已定型的主链路、最急；C 相对独立）。

### B. 交互与主链路（优先）

**目标**：让「用户下单 → 截单 → 出餐 → 送达 → 取餐确认 → 分账」这条链在原型上无断点、无歧义。

**要回答的问题**
1. 截单瞬间（T-1 24:00）系统具体做什么？（待支付订单处理、订单锁定、备料量推送）
2. 团长「手动确认收货」与 T 日 14:00「自动确认」冲突时以谁为准？
3. 截单后退款的完整链路：谁发起、谁审批、钱怎么走
4. 用户端 5 个状态 → 团长端 6 个状态 → 后台 8 个状态，三者映射是否自洽

**期望产出**：一张「全链路状态流转图」+ 每个节点的责任人与系统动作
**验收标准**：任意一条用户路径，都能在原型里走完全程不卡壳

### A. 产品定义与范围

**目标**：把 MVP 收敛到「一个办公楼能跑通」的最小集合。

**要回答的问题**
1. 约 88 人天里，哪些是 MVP 必须、哪些可二期？（重点：商家端 Web 能否先用人工 + Excel 替代）
2. 余额账户（属平台负债）是否必须进 MVP？
3. 供应商分账：走方案 A（微信分账）还是方案 B（人工月结）？

**期望产出**：MVP 功能清单（必做 / 可砍 / 二期）+ 每项取舍理由

### D. 技术可行性

**目标**：验证现有设计能否落地。

**要回答的问题**
1. 25 张表是否覆盖全部链路？有无缺表 / 冗余表？
2. T-1 24:00 截单、T 日 14:00 自动确认这类定时任务的补偿与重试机制
3. 多个集散中心并行的数据一致性
4. 「反向分账」（已分账后发生退款）如何实现
5. RabbitMQ 是否必要（按 88 人天体量评估）

**期望产出**：表结构评审意见 + 关键技术风险清单

### C. 视觉与品牌

**目标**：统一视觉规范并落地到小程序 + Web 两端。

**锁定约束**：主色 米色 `#F6F0E5` / 暖棕 `#6E5435`；字体 楷体（simkai）；风格 高端极简

**要回答的问题**
1. 小程序不支持自定义字体文件，楷体在真机上的降级方案是什么？
2. 一套 design token 如何同时适配小程序与 Element Plus 后台？

**期望产出**：设计 token 表（色彩 / 字体 / 间距 / 圆角）+ 关键页面视觉稿

## 六、技术基线（不得更换）

| 层 | 选型 |
| --- | --- |
| 小程序 | uni-app（Vue3 + Vite + TS） |
| 后端 | NestJS（Node.js + TS） |
| 主库 | MySQL 8.0（订单表按月分区） |
| 缓存 | Redis 7 |
| 消息队列 | RabbitMQ ⚠️（D 方向可评估必要性） |
| 对象存储 | 腾讯云 COS |
| 支付 | 微信支付 V3（JSAPI + 分账 + 企业付款） |
| 消息推送 | 微信订阅消息 |
| 后台前端 | Vue3 + Vite + Element Plus |
| 部署 | Docker + Kubernetes |
| 工程结构 | Monorepo · pnpm workspaces |

**数据约定**：金额 `DECIMAL(10,2)`；时间 `DATETIME(3)` · UTC+8；表名 `ab_<module>_<entity>`；每表必备 `id / created_at / updated_at / version`；软删除用 `deleted_at`。

**工作量基线**：约 88 人天（PRD v2.0 评估）。分期与砍项是本次 A 方向的核心议题。

**本期做**：一个办公楼的完整闭环 —— 下单 → 截单 → 出餐 → 配送 → 取餐 → 分账 → 看板
