你指出的「容易被误解为米饭需要多少份」是真的，而且根因比"位置没摆好"更深一层。 这一版把它从内容层挪回决策层，并顺手把单价比也一起解决了。左栏是 v0.3 的写法，右栏是修正后。

根因：这不是视觉问题，是信息层级错配

份数不归属于任何一道具体的东西——它归属于「整盒」。用户买的是盒数，不是"几份米饭"或"几份红烧排骨"。 而 v0.3 把它塞进了饭位，等于把决策层的信息放进了内容层。控件紧挨着"米饭"二字， 按邻近原则人的第一反应自然是"这是在选米饭的份数"。

⇒ 所以靠调间距、调颜色都救不回来——层级错了就得挪回去。

一、试过的另外三个方向，以及为什么没选

#方案结论理由
1 给控件加「份数」标签，
但留在饭位		 否决 只是打补丁，层级没变。而且 295px 宽度下饭位会挤：标签+控件+米饭文字+备注放不进一行，备注要么换行要么删。
2 份数移到天盖 否决 语义倒是匹配（天盖 = "这一盒"的概念层），但天盖是品牌区，往里放交互控件会破坏调性，且挤压「四方好味汇一盒」那两行文案。
3 饭位文案改「这一盒」
（不写米饭）		 否决 歧义能消，但牺牲掉"米饭 = 底座"这个最像实物的隐喻——那个隐喻正是天地盖成立的原因，为消歧义把它弄丢，不划算。
4 份数与应付合成决策条
（内容层保持纯净）		 采纳 份数回到决策层，语义正确；饭位保持纯粹 ⇒ 盒内就是盒内的东西； 且顺势把单价塞进小字行，一行同时给了单价和上限。

二、其实实物早就把答案给出来了

拿实物对照一下就清楚了
这只盒子里没有任何一格是可以单独加量的——不存在"米饭要两份、排骨只要一份"这种买法， 四格菜加一格饭永远是一整份。

所以"份"根本不是一个可以贴在某道菜旁边的概念，它只能是盒的倍数。

⇒ v0.3 把份数控件放进饭位，等于暗示"这一格可以单独加"， 而实物上恰恰做不到。这就是那个歧义的物理根源。

三、这条派生的落码纪律（新增第 7 条）

  1. 时刻一律从响应取，端上不写死。cutoffAt / deliverAt；取不到整行不显示，不回落写死值。
  2. 格子顺序 = 服务端顺序，端上不重排。dishesOfSetMeal 已按 slot ASC 下发。
  3. ⛔ 不许写 <ab-icon> 组件。唯一写法 <text class="abi abi-16">{{ I.chart }}</text>，script 段不许出现 I.xxx。
  4. ⛔ 「来自：X ›」不许变成第三方平台的东西。名称 / 标识 / 链接 / 可跳转物 / 可复制口令五项全禁（撞 5.10 / 5.20 / 5.15.4）。
  5. 菜数 ≠ 4 时要有降级。dishesOfSetMeal 没过滤主食槽 slot=5。规则：4 条 2×2；3 条 2+1 左对齐；≥5 或 <3 退回纵向列表。
  6. 图位优先读 d.imageUrl，读不到回落到 iconfont 占位图标。此回落是允许的（它回退的是"没有图"，不是"假装有图"）。
  7. ⭐ 本轮新增：份数控件的语义主语必须是「份数」，且不得与内容层元素共处一行。 更一般地说——任何表数量的控件，都不能紧贴一个可被计数的名词（米饭、某道菜）， 否则控件会被读作那个名词的量词。这条是从这次歧义里提炼的，建议写进设计系统。
