ABox 一盒 · AI 编排智能化工作流方案

评审版 v1 · 2026-11-02 · 覆盖「开发→测试→提审→运营」四阶段 · 复用现有体系（自研 API + 企微助手 + 微信 + 云服务免密钥 LLM）
原则零（用户硬约束，最高优先级）：AI 为可剥离的旁路增强，绝不影响小程序的发布与使用。 任何 AI 节点失效或整体摘除，传统人工模式必须仍能正常运营。本方案所有设计均以此为不可逾越的红线。

一、设计原则

编号原则说明
原则零AI 可剥离 / 可降级任一节点失效，传统模式照常运营；AI 是"叠加"不是"替换"。
原则一AI 不进交易主链路下单 / 配送 / 支付 / 门禁 不受任何 AI 服务影响（A、C 为 CI 期；B 为发布前；D 为售后客服）。
原则二门禁唯一真源scripts/gate.mjs 是硬闸，AI 审查仅作软建议，绝不 fork 门禁清单。
原则三确定性优先企微助手默认走规则/意图确定性路径；LLM 仅作增强分支，配置可关、失败即跳过。
原则四人工终审闸所有 AI 产出需人工确认；资金 / 不可逆操作走既有 op-policy tier 人工确认。
原则五不做静默降级AI 失效即显式降级到传统路径或转人工，不假装成功（呼应项目"不做静默降级"纪律）。

二、端到端流程拆解（含传统兜底路径）

阶段环节承担者输入输出传统兜底路径（无 AI 时）
开发提交 PR人 + CI代码 diffPR —（本就无 AI）
开发A 代码审查AI 审查 Agent + gate.mjsPR diff、门禁结果、ref 口径审查报告 + 修复建议 已具备仅靠 gate.mjs 门禁 + 人工 review（即现状）。AI 关闭不影响合并。
测试门禁 / 验证gate.mjs（CI）代码全绿 / 红 不变，无 AI 依赖。红→阻断。
发版C 提审材料Launch-Prep Agent备案通过信号、gate 全绿、op-catalog提审包 已具备人工按既有《备案后上线清单》《提审前最后一公里复核》手工汇编（文档模板已存在）。
运营B 文案素材Content-Studio Agent活动 brief、品牌规范招募页 / 卖点 / 配图 已具备人工按品牌规范（#F6F0E5/#6E5435/楷体）手写或套现有招募页 HTML 体系。
运营D 智能客服企微助手 + LLM 层用户消息、KB、137 端点应答 / 转人工 已具备回退到现有规则/意图驱动企微助手（137 端点 + stats，2026-11-02 已上线）；LLM 关即纯确定性。
关键事实支撑：① 企微操作助手当前是规则/意图驱动、未接任何 LLM（package.json 无 openai/anthropic 依赖），因此 D 节点加 LLM 是纯"叠加"，摘除即回到已上线状态； ② CI 门禁由 gate.mjs 独立执行，AI 审查是独立并行 job，不改动既有 gates/verify； ③ B/C 均为"发布前生成助手"，不参与用户下单交易。

三、AI 编排总体架构（叠加式，非替换式）

两层平面 + 一个已存在的路由中枢

  • 核心系统（独立存在，不依赖 AI）：小程序下单/配送/支付链路 · gate.mjs CI 门禁 · 企微助手确定性路径（137 端点 + stats 意图）。
  • Dev/Release 平面（GitHub Actions）：在现有 CI 上新增两个独立 job——ai-review（PR 时）、release-prep（备案通过时）。不改动现有 gates/verify。
  • Ops 平面（企微助手 + 云服务 LLM）：把 wecom-chat.service.reply() 扩为"路由层"——确定性意图走既有 ops/stats，开放意图走 LLM（检索 KB 增强）。企微助手即运营编排中枢。
  • 共享能力：① 云服务免密钥 LLM（唯一模型源，不引新付费）；② ref 口径 + 品牌规范作知识约束；③ op-policy tier 作资金/不可逆人工闸。

隔离要点：所有新增文件（scripts/ai-pr-review.mjs、scripts/gen-launch-pack.mjs、scripts/gen-campaign.mjs、llm.adapter.ts）均为独立新增，不修改 gate.mjs/deploy.sh/既有企微确定性逻辑；摘除即还原。

四、四节点角色卡（含降级 / 传统兜底）

A · AI 代码审查（Dev 平面）

工具云服务 LLM + gh api（PR diff）+ gate.mjs（门禁漂移）
边界仅"软建议"，不自动 merge；安全/高风险项转人工
降级LLM 不可用 → 仅转发门禁结果；误报 → @人复核
传统兜底无 AI 时等于当前状态：gate.mjs 门禁 + 人工 review，完全不受影响
触发/落地PR 到 main/develop · 新增 scripts/ai-pr-review.mjs + CI 扩展（独立 job）

B · 文案与素材生成（Ops 平面）

工具云服务 LLM（文案）+ 品牌模板（HTML/SVG，#F6F0E5/#6E5435/楷体）+（可选）ImageGen
边界不自动发布；须人工确认；偏离品牌规范拦截重写
降级偏规范 → 重写；LLM 超时 → 退回模板占位
传统兜底人工按规范手写 / 套现有招募页 HTML 体系（已有大量成品）
触发/落地新团/新菜品/活动，或企微"生成招募页 <brief>" · scripts/gen-campaign.mjs / command-parser 加指令

C · 提审材料准备（Release 平面）

工具gate.mjs --json + op-catalog（137 端点）+ 云服务 LLM（起草说明）+ 备案状态
边界门禁非全绿 → 阻断；不替人做合规判断
降级缺项 → 列待补；gate 红 → 停
传统兜底人工按《备案后上线清单》《提审前最后一公里复核》手工汇编（模板已存在）
触发/落地备案通过（workflow_dispatch 一键 / 手动脚本）· scripts/gen-launch-pack.mjs

D · 智能客服（Ops 平面 · 重点隔离）

工具云服务 LLM + KB 检索（_app/abox-kb）+ 137 端点 + op-policy
边界钱的口径/不可逆操作仍走 tier 人工确认；LLM 仅起草/应答，不越权执行写
降级幻觉/超时 → 跳过 LLM，走确定性路径或转人工（绝不阻塞消息回路）
传统兜底LLM 关闭即回到已上线的规则/意图驱动企微助手（100% 可用）
触发/落地企微消息回调 · 新增 llm.adapter.ts（云服务免密钥）+ reply() 加 LLM 分支 + KB RAG；配置开关 LLM_ASSIST_ENABLED，默认关或失败即关

五、关键隔离措施（确保原则零成立）

  • D 节点是唯一需重点隔离者：LLM 分支必须置于 reply() 的"可跳过"包装内（try/catch + 超时），失败时原样回到 parseIntent → 确定性 ops/stats，绝不在消息主循环里 await 阻塞或抛错。
  • 新增 LLM_ASSIST_ENABLED 开关：关闭后，企微助手行为与"未接 LLM 的当前线上版本"完全一致——这是可剥离性的硬验证点。
  • A/C 的新 CI job 与现有 gates/verify 解耦：删除新 job，CI 退回当前绿态；不影响发布。
  • B/C 的新脚本为独立文件：删除后，人工按既有文档/模板照常工作。
  • 所有新增代码不触碰 gate.mjs、deploy.sh、订单/配送/支付核心逻辑与企微确定性逻辑（只"加"不"改核心"）。

六、上线检查清单（含"可剥离性"组）

分组检查项
可剥离性① 每个 AI 节点能否独立禁用而不影响核心？② 摘除后传统路径是否完整可用？③ D 节点关闭 LLM 后是否 = 当前线上行为？
可靠性① LLM 超时/重试/降级策略；② 门禁漂移检测；③ 不静默降级（失效显式可见）
成本① 每次 PR / 每条消息的 token 预算；② 限流与熔断；③ 自费/免密钥边界
权限① 云服务 LLM 密钥来源（免密钥）；② 企微回调主体与限流；③ op tier 人工确认覆盖资金/不可逆
可维护性① 门禁唯一真源（gate.mjs）；② 口径/品牌规范版本化；③ AI prompt 随 ref 更新机制

七、执行顺序与触发

  1. 开发期（现在起）：提交 PR → 触发 A 代码审查（与 CI gates 并发，AI 软建议）
  2. 合并 main，门禁全绿
  3. 备案通过（主触发） → 触发 C 提审材料自动生成提审包 → 人工终审 → 微信提审
  4. 提审通过 / 上线 → 运营期并发：B 文案素材（按活动触发）+ D 智能客服（7×24 企微应答）
对"不影响发布与传统运营"的承诺小结：四个节点里，A/C 是 CI 期的"建议/助手"，B 是发布前"草稿生成"，D 是在已上线确定性助手之上"叠加 LLM 增强"。 任意节点失效，系统均退化为你今天已经在用的传统模式——这一点由"确定性路径优先 + 独立新增文件 + 配置开关"三重保障。
