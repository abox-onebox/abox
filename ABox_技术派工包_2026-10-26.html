A1 · 支付单边账：补一个主动查单任务真缺口 · 资金

对应探针表 P3 ｜ 证据：modules/payment/wxpay.service.ts ｜ tasks/ 全部 9 个任务

现状（代码事实）

  • wxpay.service.ts 对外只有四个方法：下单、解析回调、回调钩子、模拟支付
  • 反向验证：全仓 grep queryOrder / closeOrder / 主动查单 / 补单 零命中
  • 9 个定时任务（cutoff / commission-settle / auto-confirm / delivery-generate / leader-expire / meal-publish / reconciliation / supplier-share / page-track-cleanup）中没有查单类

后果

用户微信端扣款成功，但回调没打到服务器 ⇒ 订单停在「待支付」⇒ 超时关单。
结果：用户的钱扣了、单没了，而我们完全不知道。每次发生都要靠用户主动投诉才发现 —— 而用户往往先怀疑自己手机坏了。 这是本包唯一一条「每天都在可能发生、且发生时无人知晓」的资金缺口。

修法

  • 新增定时查单任务：扫描「已创建预支付、超过 N 分钟仍未回调」的订单，逐笔调微信 queryOrder
  • 查到已支付 → 推进订单状态并补发后续动作（通知、配送单计入）；查到未支付/已关闭 → 关单
  • 连续查不到结果的订单（超过重试上限）→ 落异常清单并告警，不要静默丢弃

验收标准

  • 用 mock 制造一次「回调丢失」，跑查单任务后：订单状态与微信侧完全一致
  • 同一笔订单连续跑两次查单：不重复入账、不重复发通知
  • 查不到的订单能在异常清单里被看见（而不是只在日志里一行）

A2 · 幂等键：Redis 抖动后永久降级，改成 fail-closed真缺口 · 资金

证据：common/cache/kv.service.ts:112-130 ｜ 已附可执行测试

现状（代码事实）

  • :126 catch { —— 不区分异常类型，连接失败 / 超时 / 命令报错一律捕获
  • :127 degraded = true → :128 递归走进程内内存 Map

  • 加重因素：enableOfflineQueue: false + maxRetriesPerRequest: 1（:38-45）⇒ 亚秒级抖动立刻抛错触发降级，不是罕见分支

实况：两个实例对同一个幂等键 setNx 都返回 true ⇒ 同一请求可执行两次； 且不抛错、业务完全无感，只在日志留一行 WARN。连跑 3 次结果一致（PASS 7 / FAIL 1）。

修法（三选一，推荐第一项）

  • 推荐 · fail-closed：Redis 驱动下 setNx 抛错直接向上抛，不降级 —— 与本项目队列的既有口径统一（文档原文：队列「Redis 驱动连不上是 fail-closed 抛错，不静默降级」）
  • 次选 · 可自愈降级：保留降级，加后台探活，Redis 恢复后把 degraded 复位
  • 最小 · 至少吵起来：日志从 WARN 升到 ERROR 并接入告警

验收标准

  • 运行 node abox-onebox/scripts/test-kv-idempotency-degradation.mjs ⇒ 退出码 0（当前为 1）
  • 注意：改成 fail-closed 后，该测试第①条断言（「不抛错」）的预期语义需同步更新为「抛错」，请一并维护测试，别让它恒绿

A4 · 发券：面额无上限 + 总量限制可整段绕过内控缺失

对应探针表 F10 ｜ 证据：modules/coupon/dto/coupon.dto.ts ｜ modules/coupon/coupon.service.ts:136
先澄清一个被夸大的说法：此前有「一次输错就是百万级事故」的表述，经核实不成立。 discountOf() 返回 Math.min(面额, 订单额)，且 payAmountFen = Math.max(0, …) ⇒ 一张天价券最多免掉一单 ¥25.80。性质是「慢性内控漏洞」，不是资金爆雷。请按真实等级排期，不必紧急。

现状（代码事实）

  • 面额无上限：coupon.dto.ts 两处 faceValueFen 只有 @Min(1)，没有 @Max；反向验证全仓无面额上限常量
  • 限量可绕过：coupon.service.ts:136 全部限量校验写在 if (input.couponDefId) 里头， 而该字段在 DTO 里标了 @IsOptional() ⇒ 不传它发券，totalLimit 判断整段不执行，连 issuedCount 都不回写
  • 已防住的部分：券归属校验在（uc.userId !== userId），别按这条去问责

修法

  • faceValueFen 补 @Max（数值请祝总定，建议不超过单份餐价）
  • 把限量校验移出 if 块，或将 couponDefId 改为必填
  • issuedCount 必须回写 —— 目前这个通道连计数都没有，系统对它零感知

验收标准

  • 不传 couponDefId 发券 ⇒ 返回明确的参数错误，而不是静默成功
  • 超过 totalLimit 发券 ⇒ 拒绝，且 issuedCount 不增长
  • 面额填超过上限的值 ⇒ 校验拦截

A5 · 跑批与日志的可观测性（一组四小项）看不见

对应探针表 T1 / T2 + 走查新发现 X3 / X6 ｜ 证据：tasks/schedule.service.ts:64
这一组的共性是「静默失败」：本包 A2 是「Redis 抖动没人知道」、A3 是「解除禁令没人知道」， 这一组是「跑批没跑、日志没写，也没人知道」。四次独立发现指向同一个系统性取向，建议作为一个主题整体处理。

现状（代码事实）

小项证据
T1 无执行记录 反向验证：全仓实体与迁移中 grep schedule_run / lastRun / runLog 零命中，没有任何任务执行记录表。 schedule.service.ts:64 注释自承：「要查『昨夜跑批跑了什么』看日志，不查表」—— 这是明确的设计声明，不是漏写
T2 无心跳告警 失败只有 logger.error（:158）、成功 logger.log（:152）。 没有心跳检测 ⇒ 「进程压根没起来 / 任务没被调度」这种不抛异常的情况，完全无人知晓
X3 日志写失败被吞 common/interceptors/operation-log.interceptor.ts:240：整个写库包在 try/catch，失败只打一行 WARN。 取舍本身合理（不能因日志表炸了让退款审批失败），但无补偿、无告警
X6 日志表只涨不清 ab_operation_log 全仓零清理任务；对账不平也会往里写（reconciliation.task.ts:54）。 对比 ab_page_track 有 page-track-cleanup.task.ts 每日 03:30 清理
为什么 T2 值得单独当回事：如果 cutoff.task（截单）某天没跑成 —— 当天所有订单都没截单，供应商照做、系统还在收新单。第一个发现的人是谁？多久发现？ 答案是：靠用户投诉。而它失败时不会抛异常（如果进程没起来），现有告警抓不到。

修法

  • ① 加心跳：关键任务（cutoff / commission-settle / delivery-generate）跑完写一条「我跑过了」的记录（表或结构化日志），监控按预期时刻没来告警
  • ② 连续失败告警：同一任务连续 2 次失败必须触达到人（分钟级）
  • ③ 日志写失败升级：WARN → ERROR 并接入告警；再加「每日日志条数心跳」，骤降即说明写入在静默失败
  • ④ 留存与归档：先定留存期（建议与财务对账周期对齐），照 page-track-cleanup 的样子做先归档再删的任务

验收标准

  • 把进程停掉 1 小时，监控系统应报「任务心跳丢失」—— 这是唯一能证明 T2 真修好的测试
  • 人为让日志表不可写，应触发 ERROR 级告警（而不是只有一行 WARN）
  • 跑批看板或查询接口能回答「每个任务上次几点跑的、成功还是失败」
