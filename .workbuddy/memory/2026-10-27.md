## ⛔ 生产库误覆盖事故（本轮最严重的一次，已恢复，务必记住）

**经过**：回滚演练的「DB 导进临时库验证」那步，运维执行
`zcat 锚点sql.gz | docker exec -i mysql ... <临时库名>`，但 **mysqldump 产物自带
`CREATE DATABASE` + `USE \`abox_onebox\`` ⇒ `USE` 覆盖命令行指定的默认库**，
36 条 DROP + CREATE + INSERT 全部落在**生产库**上，库被回退到 19:42 快照。
**发现方式**（值得学）：导入「成功」后去数临时库的表 = **0 张** —— 「成功却是 0 张表」这个矛盾
立刻指向「语句没进这个库」，回查 dump 头部就看见了 `USE`。
**处置**：2 分钟内用**晚于**被覆盖时点的备份（19:57 > 19:42）全量恢复；无业务数据损失（已由 binlog 证实）。
**残留**：`ab_config` 那行 `description` 退回长描述（且 HEX 呈 `C3A6…` mojibake）⇒ 已授权补回短描述。

### 三条硬教训
1. ⭐ **mysqldump 的 `USE` 会吃掉「指定库」** ⇒ 导进别的库必须 `--one-database`、
   或先剥掉 `USE`/`CREATE DATABASE`、或起独立实例。已做成 `restore-db.sh` 的两道闸门
   （跨库拒绝执行 + `--verify-only`：把导入流里的库名**改写成临时库名** ⇒ 流里没有生产库名，
   物理上碰不到；且 **临时库 0 张表直接判失败** = 把人的警觉固化成断言）。
2. **任何恢复/导入动作，第一次必须在非生产实例（或一次性容器）上跑通**，不许在生产实例上第一次执行新命令。
3. **核验窗口内必须冻结写入** —— 我在派测试独立核验的同时授权了运维写入，导致「核验对象在核验期间被改动」。

### 证明「没丢业务数据」的正确姿势（本次实测有效）
- 业务表查 `MAX(id)` + `MAX(created_at)`，并数 `created_at > 截止点` 的行数；
- ⚠️ 光看恢复后的表**不能**证明「被覆盖前没有更晚的行」⇒ 补 binlog：
  确认 `binlog_format=ROW` + `binlog_row_image=FULL`，扫窗口内的 TABLE_MAP/ROWS 事件。
  本次结论：那 60 分钟里四张业务表**只有两轮恢复导入自己的 Write_rows**，没有任何业务 DML。
