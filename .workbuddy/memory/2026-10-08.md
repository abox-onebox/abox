### 本轮定下的可复用设计原则（跨页面适用）
- ⭐ **纸面上的合规 ≠ 心里的放心**：证照编号用户看不懂 ⇒ 说服力最弱却占了现在整页；把「过去时快照」翻成「持续动作 + 可查记录」才有说服力
- ⭐ **给次数不给评分**：「4.8 分」抽象且可疑（用户不知谁评的）；「你这栋楼 1,240 次 · 91% 好吃」具体且自我解释。**且范围必须限定到「本楼」**（全平台数据对用户无意义）
- ⭐ **诚实留空反而更可信**：显示「12 月 · 待核验」这种未完成状态，比只挑三次已完成的来展示更能建立信任
- ⭐ **北极星指标必须是「流转」不是「占有」**：信任页的成功 = 人走了且走回下单页（返回下单转化率），不是停留时长 / 打开频次。上一版「周报」正是错用了后者，才做出没人看的页面

#### 根因（这次才想明白，写死以免再犯）
- ⭐⭐ **前七版被否的共同点：我一直在做「更好的展示页」——换内容、换证据强度、换排版。**
  而用户的判据是「**去掉它有没有明显损失**」（原话「可有可无」）⇒ **展示页去掉了没有损失**，所以再怎么优化都过不了这一关。
- ⭐⭐ **我把用户点进来的动机假设错了**：我假设是「这家安全吗」（疑虑消除）⇒ 产出全是安抚性内容（放心吃 / 核验记录）；
  **而安抚性内容天然无趣、天然可有可无**。实际动机是看到一道菜想知道「**我什么时候还能吃到**」。
- ⭐ 可复用判据：**用户要的是「承重墙」不是「锦上添花」**。判断法 —— 去掉后是否有**可归因的收入/留存损失**。
  前七版全部不扛收入，所以全灭。

#### v0.2 定案 = 「排期页」：从回顾过去翻成预约未来
- ⭐⭐ **1+1&gt;2 的准确位置**：同一份 `ab_meal_assignment` 排班数据，把组织维度**从「按天」换成「按出品方」**，就长出了**可预期性**。
  用户能规划一周 / ABox 提前拿到需求信号备货更准（盒饭第二大成本是损耗）/ 供应商知道自己哪天出多少份 ⇒ **三方都得利，零新增表**
- ⭐ **频次质疑由此解决**：用户会在**馋某一道的时候**自己打开 ⇒ **按需，不是按周期**（v0.1 的核验日历没人会主动想看）
- 页面结构（有档期态）：`hd 三味屋[川菜][本周在供]` → **`next` 下次上桌（第一屏，34px 大日期）10月14日 周三 / 香煎鸡腿 / 还有6天 / [到时提醒我]**
  → `后面还排了 10/21 红烧肉 · 10/28 麻婆豆腐` → `本周这一次 10月8日·周四 香煎鸡腿 / 这栋楼吃过1,240次·91%好吃`
  → `他们只出这一道` → `exit 明天你吃的是它做的 · 去看看 ›` → 页脚证照
- ⭐ **未排期态绝不给死路**：出口换成「看看明天是谁做的 ›」（留灰按钮 = 死路）

#### 核过的数据事实（勿重查）
- `ab_meal_assignment`：`meal_date`(date) / `building_group_id` / `set_meal_id` / `status`(pending|active|cancelled) / `publish_at` / `cutoff_at`
  ⇒ **未来日期在结构上完全支持，零 DDL**
- ⚠️ **种子「出餐日 = 今天 + dayOffset（一律 ≤ -2）」⇒ 只排过去** ⇒ 未来档期现在没数据
  ⇒ ⭐ **本方案唯一的真成本 = 运营从「每天排明天」改成「提前排一周」**，是**排班习惯**不是技术
- 🟡 待核：**玉子屋是提前公布菜单制（据称月度）** —— 我据记忆陈述，落地前需再核一次（它是本方案的对标依据）

#### 待用户裁决（两项）
1. **订阅消息冲突**：项目既有纪律「一周一条是上限」，而「到时提醒我」是用户点一次收一条 ⇒ 同一天多道菜时，**合并推一条** 还是 **只认用户点的第一个**？
2. **页头是否换成「李师傅 · 三味屋」**（需新增 supplier 主厨名字段）：信任从机构落到具体的人 ⇒ 单一套餐的「没得选」变成「有人替你担着」。**核心方案不依赖它**

3. **单一套餐既是护城河也是天花板** —— 换来了供价 ¥14.00，代价是**客单价钉死 ¥25.80，这一维天然为零**
