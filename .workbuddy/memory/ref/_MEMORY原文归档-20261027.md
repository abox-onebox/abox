## 二、技术与环境 → `ref/工程纪律.md`
- ⭐ **重构搬家前先查「谁在按文件名盯你」**：按路径/文件名扫的判据是重构的头号受害者（代码搬走 ⇒ 判据假红）。做法=**判据跟着真源改指，不改判据、不放宽判据**（2026-10-27 T5：N2-10/N2-TPL-2 改指 `buildingSuspend`；N1-20 改指 `buildingQuery`）
- ⭐ **判据豁免必须 bind 到真实存在的对象**：登记豁免不是免死金牌 —— `blockOf('xxx(')` 取不到方法块**即判红**，否则豁免指向空气 ⇒ 退化成永久盲区（比不豁免更坏）。配 HELPER_CHECK 专项自证「对象改名后同样违规必红」（2026-10-27 N1-16 修 `buildingWarnings` 盲区）
- ⭐ **多文件判据的 `mutateFirst` 只破化 `files[0]`** ⇒ 「第二、三份是否真被守」通用自证**证明不了**。验证办法=往 `files[1]` 注入一份必报样本、确认报红、再还原（2026-10-27 实测：往 `building-query.service.ts` 注入内联合取 ⇒ N1-16 立即红）
- ⭐ **「判据恒绿」的三种成因要分清**：① 产物真对 ② 判据看不见（正则漏形态，如 N1-16 旧版漏 `!==`/`gid === null`）③ 破化锚点已腐烂（如 N2-8 的 `const GROUP_A_STATUS` 真文件里已不存在 ⇒ 自证只活在 sample 上）。②③都表现为绿 ⇒ 必须构造必报样本反证
- ⭐⭐ 上条还有**反面一半**：不只查「谁在盯」，还要查「**它盯不盯得到**」—— 判据若对某处**失明**（正则放过它），搬走就 = 从「盲区」升级成「彻底扫不到」。实例：N1-16 对 `buildingWarnings` 的两处合取失明（正则只认 `===` 与 `gid !== null`，放过 `!==` 与 `gid === null`）⇒ **裁定前禁止搬走它**（已写进 spec §5.4.6）
- ⭐ 登记进 spec 的行数**必须取 prettier 之后的值**（2026-10-27 实测 118→115，spec 三处数字回改过）
- ⭐ **spec §0「行数上限」表只管「本批授权新建的文件」白名单，不含既有文件** ⇒ 别拿它当既有文件的行数合规依据（2026-10-27 曾据此误称「building-admin.service.ts 1611 行超额」，回源后更正：拆分理由是四个关切混在一个文件，不是合规）
- 原型v4.10.0；uni-app+NestJS+MySQL8/Redis7+Vue3；表33(parity权威)·迁移17支（2026-10-23 增 `ab_coupon`/`ab_user_coupon`）
- ⭐⭐ **改 `packages/shared-types` 后必须 `npm run build`**：api-server 解析的是 **`dist/` 不是 `src/`**（`dist` 被 gitignore 不入库、CI 自行构建）。症状=tsc 报「xx does not exist in type XxxResult」，而 src 里明明加了（2026-10-27 实测）
- ⭐⭐ **「有没有值」别用 `!== null` 判**：实体列类型是 `string | null | undefined`，`undefined !== null` **为 true** ⇒ 把「没查这个字段」误判成「有值」。判有无用 `Boolean(x)`，取值再 `?? null` 兜底（2026-10-27 盲盒 `blindBoxPending` 实测）
- ⭐⭐ **TypeORM 默认命名策略不做 camelCase→snake_case 转换**：实体多词列**必须**显式写 `name: 'snake_case'`。漏写 ⇒ 生产建出 `faceValue`、迁移建 `face_value`，`schema:parity` 同时报「迁移缺列 X」+「迁移多出 x_y」（2026-10-23 实测）
- ⭐⭐ **时间三件套（别手写）**：`toBjIso()` 转 ISO+08:00（`toISOString().replace('Z','+08:00')` 是**错**的，只给 UTC 贴标签、差 8 小时）；`now()` 取「相对现在」（非 `new Date()`）；`bjDateTime(dateStr, hour)` 日期→时刻（**hour 可传 24** = 次日 0 点，正好做「含尾上界」）
- ⭐⭐ **判断「有没有并发保护」必须同时查悲观锁与乐观锁**（2026-10-26 教训）：只 grep `pessimistic/forUpdate/setLock` **会漏判**——本项目写钱路径统一用**乐观锁** `version: () => 'version + 1'` + `.where('id=:id AND version=:v')`，覆盖 withdraw / balance-admin / commission / refund(4 处) / reversal(2 处) / delivery。**不要用「grep 不到悲观锁」推出「有并发风险」**。同理，判断幂等要看有没有 `WHERE status='pending'` 这类条件更新，不要只看「注释说不带锁」。
