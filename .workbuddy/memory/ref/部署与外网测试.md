## 1 服务器投递方式
- ⭐⭐ **`/opt/abox-onebox` 没有 `.git`**（代码是 scp 上传的，顶层 owner 是 Windows UID 197609）
  ⇒ **`git pull` 在这台机器上根本不能用**（此前的部署口令是错的）
- 正确方式：**本地 `git archive --format=tar.gz -o pkg.tgz HEAD` → scp → `tar xzf` 覆盖**
  优势：精确等于本地 HEAD（门禁已绿的那一版）；天然排除 `node_modules / dist / .env.prod / data`
- ⭐⭐ **三个 Dockerfile 都必须在 `pnpm install` 前 `COPY scripts ./scripts`**
  - 根 `package.json` 的 `prepare` = `node scripts/setup-husky.mjs`
  - ⚠️ **易误读点**：该脚本设计为"永不失败"（内部 try/catch `husky install`，非 git 环境 warn + exit 0），
    但**模块找不到是 node 解析阶段的硬失败，try/catch 根本来不及执行** ⇒ "脚本健壮"≠"不拷也能过"
  - 旧镜像没踩到，只因那份代码早于 prepare 引入。已三端统一补 COPY（提交 `8443fb8`）
  - 注：`.npmrc` 里**没有** `ignore-scripts`，不是开关所在
- 服务器原代码是 **09-14 快照**，早于 09-15 重建工程仓 ⇒ 曾落后远不止几笔提交

## 3 部署形态硬事实
- **`deploy.sh` 七阶段**：预检 → 备份 → 起依赖 → 构建 → 迁移 → 起应用 → 健康验证（轮询 `/api/v1/health/ready`，90s）
  ⚠️ 首次部署 2/7 报「备份失败」**属正常**
- 端口：原只对外 `8080:80`（admin）；**2026-10-02 新增 h5 `8081:80`**；mysql/redis **不映射宿主端口**
- **api 容器刻意没有 healthcheck** ⇒ 不能用「是否 healthy」判 API，只看 `/health/ready`
- **4C8G 不可省**（机上要构建两个 Node 镜像；OOM 表现为 `Killed` 且**无其它报错**）
- Dockerfile 带 `--enable-source-maps` ⇒ 线上堆栈可直接对应 **TS 行号**
- ⚠️ **改 `.env.prod` 后必须重建容器才生效**（compose 用 `env_file:` 不是 `environment:`）：
  `docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --no-build api`
- **宿主机 nginx 两个易漏项**：`client_max_body_size 20m`（否则传图 413）+ `proxy_request_buffering off`（微信支付 V3 回调要原始报文验签）

## 5 生产数据 / 团期
- ⭐⭐ **生产库跑不了 seed**：`seed.ts` 守卫 `NODE_ENV === 'production'` 直接 exit（`ABOX_SEED_CONFIRM` 盖不住，两个 if 独立），且会 `wipeAll()` 清 27 表
  ⇒ **服务器上的"明日团"只能后台「菜单矩阵 `/meal/matrix`」发布**（团长端**没有**开团入口，`publish` 是 `meal-admin` 接口）
- **幂等脚本** `_tmp/h5fix/open-group.mjs`（copyAssignments 10-02 → 10-03…10-08 + 逐个 publish）
  ⇒ ⚠️ **排期不是永久的，10-08 之后又会空**，需周期性补
- 根因逻辑：业务只能订"明日"（`isOrderable` 上界算出来的）⇒ matrix 里只有当天有排期时必然"未开团"
- ⭐⭐ **「明日开团」SOP（2026-10-20 立；祝总反对自动任务留痕 ⇒ 只做手动，不建定时任务）**：
  ① **只读核查**（容器内跑，`dateStrings: true` 必带）：`docker exec abox-api-prod node <探针>` 查 `SELECT meal_date,status,COUNT(*) FROM ab_meal_assignment WHERE meal_date >= CURDATE() GROUP BY meal_date,status`；明日 0 行 ⇒ 走 ②
  ② **补团+上架**（生产写，须用户当轮批准）：`docker exec abox-api-prod node /app/scripts/prod-patch-insert-assignment.mjs --target-date=<明天YYYY-MM-DD> --apply --publish`（默认参照=全表最大日期；截单为明日 00:00(+08:00)，**过了午夜 publish 护栏会跳过**，须赶在当天 24:00 前）
  ③ **落库复核**：同 ① 查 target 日 5 行全 active
  ⚠️ 脚本在**容器内 `/app/scripts/`**（宿主机 `/opt/abox-onebox/scripts/` 同内容，md5 可核对）；`docker cp` 进去的探针属 root，删除要 `docker exec -u 0`
  ⚠️⚠️ **mysql2 把 DATE 解析成「本地午夜」Date，UTC+8 下 `toISOString().slice(0,10)` 会把日期系统性提前一天**（2026-10-20 实测：`MAX(meal_date)` 返回 `2026-10-18T16:00:00Z` 其实是 10-19）⇒ 只读探针一律 `dateStrings: true` 或 SQL 侧字符串比较；**显示与脚本结论矛盾时，先疑探针**
  ⚠️ 2026-10-20 实况：10-20/10-21 连续两天 0 行（人都没建），10-21 已按 10-19 格局补齐（1=红烧肉/2=东坡肉/3=宫保鸡丁/4=零食能量包9/5=泡面宵夜包8）

## 8 用户端 H5 与「小程序异地测」（2026-10-03 修正）

> ⚠️ **本节的旧结论「小程序异地必被拦，唯一可行形态是 H5」已被推翻** —— 那条只考虑域名校验，
> 漏了「体验版 + 真机调试态」这条豁免路径。下面保留 H5 方案，**并补上小程序形态的正确做法**。

### 8.0 ⭐⭐ 先分清三种「扫码入口」（这条决定方案）
| 入口 | 谁能扫 | 有效期 | 异地同事可用 |
|---|---|---|---|
| 预览码（开发版） | **仅管理员/开发者本人**（他人扫码报错） | 约 30 分钟 | 否 |
| **体验版** | 后台添加的**体验成员** | 约 7 天 | **是** |
| 正式版 | 所有人 | 长期 | 需 HTTPS + 备案域名（暂无） |

- ⭐ **域名校验真相**：**开发者工具勾「不校验合法域名」只对模拟器生效，真机完全无效**。
  真机豁免唯一途径 = 进入小程序 → 右上角「…」→ **打开调试/开发调试** → 出现**绿色 vConsole** → 退出重开。
  ⇒ **只有「调试态」才允许 IP 且允许 http**。
- ⭐ 上线服务现有硬件条件：**宿主机无 nginx、无域名、无 SSL 证书** ⇒ HTTPS 路径短期不成立。

### 8.1 小程序给同事异地测的正确做法
1. mp 后台「管理 → 成员管理 → 体验成员」添加同事微信号
2. **development 模式**构建（见 §8.3）+ 微信开发者工具上传 → 后台设为体验版
3. 发体验版二维码 → 同事扫码 → **务必开启调试态**（否则 http+IP 被拦，症状是「网络异常 / 本楼今日未开团」，极易误判）
4. ⛔ **上线前必须用 production 重新构建上传**（development 版带 demoMode 后门，任意 devCode 可换身份）

### 8.2 ⭐⭐ development 是唯一可用模式（不是洁癖问题）
- `mock-wx-mini.provider.ts:51-55`：仅 code 匹配 `/^dev:(.+)$/` 才给固定 openid，否则取 **sha1 前 16 位**。
- 而**微信 `uni.login()` 每次返回新 code** ⇒ 生产模式 + mock provider = **每登录一次换一个新用户**
  （订单/余额/团长身份全丢；源码注释自己写了这个陷阱）。
- 另一条路（切 `PROVIDER_MODE=real` 拿真 openid）会连带把支付换成 real provider ⇒ 缺商户号必挂，已被否（见 §6）。

### 8.3 构建命令与产物位置
```

  ~/.workbuddy/binaries/node/versions/22.22.2-3/pnpm --filter miniprogram build:mp-weixin --mode development
```
- ⭐ **产物 = `apps/miniprogram/dist/build/mp-weixin`（在包目录下，不在仓库根 `dist/`）**
- ⭐ API 基址**复用 H5 的 8081**：h5 的 nginx `location /api/` 已反代 `api:3000`
  ⇒ **不用放行 3000、不用新容器**；小程序 `wx.request` 不受 CORS 限制。
- 验证方式：grep 产物 `constants/env.js`，确认 `apiBaseUrl` 正确、**无 localhost 残留**、`demoMode:!0`。

  ⇒ 用**带参小程序码**（`devCode=tom` / `lucy`，`[A-Za-z0-9_-]{1,32}`）给每人独立账号。
  缺省所有人都是 `dev:1001`（李明）。

### 8.5 H5（原方案，仍有效且更快）
- ⭐⭐ **H5 是最快的兜底**：放行 8081 后直接把 `http://154.8.164.180:8081/?devCode=tom` 发同事，
  微信里点开即网页，**不用上传代码、不用加体验成员、不用开调试**。缺点：非小程序形态。
- 组成：`apps/miniprogram/Dockerfile` + `nginx.conf` + compose `h5` 服务（`${H5_PORT:-8081}:80`，`abox-net`，`depends_on api started`）
- ⭐ **必须 `--mode development` 构建**：非 demo 走真实 `uni.login`，而 **H5 端没有 uni.login** ⇒ 登录必失败 ⇒ 无 token ⇒ **一个接口都不发**，表现是「页面能开、本楼今日未开团」，极易误判成开团逻辑坏了
- ⭐ `VITE_API_BASE_URL=/api/v1`（同源）：① `.dockerignore` 排除了 `.env`，镜像读不到绝对地址；② 后端 CORS 是白名单制（`corsOriginOf`），写绝对地址会被跨域拦 ⇒ 由容器 nginx 反代 `/api/`
  ⚠️ Git Bash 传值要加 `MSYS_NO_PATHCONV=1`（否则 `/api/v1` → `C:/Users/.../PortableGit/.../api/v1`，**无报错**）
- ⭐ **路径冲突**：uni-app H5 产物自带 `static/`（品牌楷体 `static/fonts/ab-kaiti.woff2`），后端上传目录也挂 `/static/`（`main.ts useStaticAssets`）⇒ nginx 用**更长前缀** `/static/fonts/` 留给本地
- ⛔ development 模式 `?devCode=<任意>` 可切任意身份 ⇒ **仅测试期临时开放，测完 `docker compose stop h5`**
- 本机验证方式（无 Docker）：写 node 模拟容器（静态托管 + 同源反代到真实服务器）+ playwright ⇒ 登录 201 / 首页 200 / 五个图标有实际渲染尺寸
- ⛔ **腾讯云安全组放行 TCP 8081 待用户操作**（云服务器在外网访问前必须在控制台放行，我无法操作）⇒ 放行前公网 8081 = 000，容器内 200

## 9 每次开测前的准备
- ⭐⭐ **每天第一次测试前先跑 `node scripts/local-test.mjs --seed --smoke`**：种子按**当天**生成"明日团"，**隔天必失效**，
  症状「所有账号都提示本楼今日未开团」，极易误判成开团逻辑坏了
  ⚠️ `local-test.mjs --seed` 内部 spawn `gate.mjs seed` 用 stdio pipe ⇒ **不带 pipefix 垫片会 `exit=null (1ms)` 假失败**
- 入口卡 IP 与种子是**两条独立的「隔天失效」**：IP 换网要重跑，种子隔天也要重跑
- ⚠️ `make-qr.mjs --ip=<IP>` 在第 4 个码上崩（`qrcode`：degree does not match number of roots），且 **PNG 输出目录写死**会覆盖本地版 ⇒ 跑完用默认参数重跑恢复
- 本地二维码**只在同一个 WiFi 下有效**；同事异地测走服务器副本

## 11 ⭐⭐ 体验版 / 容器 的三条硬事实（2026-10-03 真机实测 · §8 的补充，冲突时以本章为准）

### 11.1 体验版的「一码独占」与重启生效
- ⭐⭐ **打开调试后必须杀掉小程序重启**才生效（下次启动才生效）；成功标志 = 右下角**绿色 vConsole**。
- ⭐ 体验版码**长期有效**，但**同时只有一个体验版** ⇒ **改码重传后必须重新「选为体验版本」**，否则同事扫到的是旧码。
- ⭐ 体验成员填**微信号**（不是昵称、不是手机号）；漏加会报「**没有体验权限**」。

### 11.2 ⭐⭐ 小程序形态下 `h5` 容器（8081）不能停
- 小程序端 API 基址是 `http://154.8.164.180:8081/api/v1`，**走的就是 h5 容器的 nginx 反代**。
- ⇒ **停 h5 = 小程序全部请求断**。
- ⚠️ 与 §8.5「测完 `docker compose stop h5`」的旧口径冲突时，**以本章为准**：
  只有**纯网页版**测完才可停 h5；只要还有人在用小程序，h5 必须留着。

### 11.3 端口不用重复放行
- 小程序 `wx.request` **不受 CORS 限制**；API 基址复用 H5 的 8081（nginx `location /api/` 已反代 `api:3000`）
  ⇒ **不用放行 3000、不用新容器**。
- 服务器**无 nginx / 无域名 / 无证书**（指宿主机层）⇒ **HTTPS 路径短期不成立**，只能靠调试态绕。

### 12.1 标准投递链路（服务器**无 .git**，别 clone）
```
git archive --format=tar.gz -o _tmp/abox-deploy-<sha>.tgz HEAD   # 本机
scp _tmp/abox-deploy-<sha>.tgz abox-srv:/tmp/                     # 投递
tar xzf /tmp/abox-deploy-<sha>.tgz -C /tmp/abox-stage             # 服务端 staging
cp -a /tmp/abox-stage/. /opt/abox-onebox/                         # 覆盖（不删宿主机独有脚本）
/opt/abox-onebox/scripts/deploy.sh --tag manual-<YYYYMMDDHHMMSS>  # 7 步：预检→备份→依赖→构建→迁移→起服务→健康验证
```
- root 登录 ⇒ **不用 sudo**；`--dry-run` 先看一遍再真跑（会打印回滚目标 `PREV_TAG`）；回滚 = `./scripts/rollback.sh`
- ⚠️ 必须显式 `--tag`：默认取 git short sha，而服务器无 .git 会失败

## 15 ⭐ H5 测试环境的三条「多人测试」事实（2026-10-27 实测）
- **H5 是 `--mode development` 构建的**（`apps/miniprogram/Dockerfile` 硬参数）⇒ `?devCode=<标识>` 才生效；

- ⭐ **`devCode` = 身份本身，`dev:xxx` 相同即同一用户**（共用订单/券/余额/佣金）。

  ⚠️ 给多人发同一条链接会互相踩踏；`Dockerfile` 文件头原本就写着「每个同事一个独立身份」。

### 12.6 ❌ 已推翻 → ✅ 正确口径：代码 36 = 生产 36，`ab_wecom_binding` **不是孤儿表**
> ⚠️ 本节前身为「生产有孤儿表、parity 不覆盖」—— **结论错误，已推翻**。保留错误版本只为留痕，
> **以下为现行口径**。错误成因见下「探针三组踩坑」，这是本项目**第 N 次**栽在探针写错上。

**正确事实（2026-10-29 二次取证）**：生产 `ab_*` BASE TABLE **36** 张，代码侧实体**同样 36** 张，
**双向差集为空**。`ab_wecom_binding` 三样齐全：
- 实体 `apps/api-server/src/modules/wecom-kb/wecom-binding.entity.ts:15`
  —— 写法是 `@Entity({ name: '...' })`，**不在 `database/entities/` 目录下**；
- 迁移 `database/migrations/1700000000013-wecom-binding.ts`；
- controller / service / dto / module 全套在 `modules/wecom-kb/`。
且 `database/schema-parity.ts:292` **早已显式白名单登记它**（第 39/256/288 行注释说明：
该迁移整篇编程式建表、无裸 SQL ⇒ 源A 推演不出这张表 ⇒ 手工登记）。**parity 是覆盖它的。**

⭐⭐ **探针三组踩坑（这才是本节真正价值）**
1. **扫目录 ≠ 扫全仓**：我首次只扫 `database/entities/*.ts` ⇒ 实体完全可以住在模块目录下。
2. **`@Entity` 有两种写法**：字符串式 `@Entity('ab_x')` 与**对象式 `@Entity({ name: 'ab_x' })`**；
   按前者写正则会**静默漏掉**对象式的表（数量为 0 时不报错，看起来像"真的没有"）。
3. ⚠️ **POSIX ERE 不支持 `\s`**：`grep -oE "@Entity\(\{[^}]*name:\s*'ab_[a-z_]+'"` 永远不命中
   —— 改用 `[ ]*`，或先 `grep -rn "@Entity({"` 再从中 `grep -oE "'ab_[a-z_]+'"`。

⇒ 判「某张表有没有实体」必须：**全仓扫 + 两种写法都扫 + 探针先在已知命中上自证**。
⇒ 正确计数口径：`{ grep -rhoE "@Entity\('ab_[a-z_]+'\)" . --include='*.ts' | sed ...; grep -rn "@Entity({" . --include='*.ts' | grep -oE "'ab_[a-z_]+'" | tr -d "'"; } | sort -u`
⇒ 查生产表数仍要**排除 `migrations`（TypeORM 元表）**，用
   `information_schema.tables WHERE table_name LIKE 'ab\_%' AND table_type='BASE TABLE'`。

### 12.7 ⚠️ `deploy.sh` 在 `scripts/` 下，且失败会留下「新代码 + 旧产物」中间态（2026-10-29 实测）
- 路径是 **`./scripts/deploy.sh --tag <tag>`**，不是 `./deploy.sh`（写错报
  `No such file or directory`）。
- ⭐ 危险点：投递脚本通常是「`tar xzf` → `cp -a` → `nohup deploy.sh`」。若最后一步因路径写错
  失败，**前两步已经生效** ⇒ 服务器处于**新代码 + 旧构建产物 + 旧容器**的中间态：
  页面看着正常，实际跑的是旧逻辑，而 `.deploy-state` 还停在旧 tag（看起来像"没部署过"）。
- ⇒ 纪律：部署报错后**先确认代码是否已被覆盖**（比对某个新文件的存在性或 mtime），
  再决定是**补跑 build+重启**还是回滚；不要因为 `.deploy-state` 没变就以为"完全没动"。
  补跑直接再跑一次 `./scripts/deploy.sh --tag <新tag>` 即可（本次 110s，readiness=ready）。

### 12.8 ⭐⭐ `No space left on device` 先查 inode，别只看 `df -h`（2026-11-03 实测）
- 现象：`deploy.sh` 在 `docker build` 解层时报
  `failed to extract layer …: no space left on device`，而 `df -h /` 明明还有 **22G 可用**。
- 真凶：**inode 用满**（`df -i` = 7,849,332 / 7,864,320，剩 1.5 万）。镜像层里全是
  `node_modules` 小文件，每个文件一个 inode；磁盘够、inode 不够，表现与"磁盘满"一模一样。
- 处置：`docker builder prune -af`（纯构建缓存，不动运行容器）⇒ 磁盘 92G→50G、inode 100%→46%。
  之后 `docker system df` 显示还有 45G 可回收旧镜像，暂不必动（保留回滚 tag）。
- ⇒ 纪律：**凡 `no space left` 先跑 `df -i`**；清理优先 `builder prune`（最安全），其次按 tag 删旧镜像，
  别用 `docker system prune -a --volumes`（会连数据库卷一起清）。

### 12.9 ⭐⭐ `docker builder prune -af` 会连带清掉 pnpm store ⇒ admin 构建失败（同次实测）
- 因果链：`prune -af` 清掉 `--mount=type=cache,id=pnpm` 的 store ⇒ `better-sqlite3` 失去预编译产物
  ⇒ 回退 `node-gyp` 源码编译 ⇒ **`apps/admin-web/Dockerfile` 的 builder 阶段刻意不装
  `python3 make g++`**（见其注释）⇒ `pnpm install` 报 `gyp ERR! find Python`，admin 构建失败，
  连带 api 阶段被 CANCELED（compose 并行构建）。
- ⚠️ 注意：`admin-web/Dockerfile` 注释称 `--filter "admin-web..."` 不会装 better-sqlite3，
  **实测会装**（2026-11-03 日志明确出现 `[admin builder 11/15] … better-sqlite3 install`）——
  冷缓存下这条假设不成立，别再依赖它。
- 恢复办法（已验证）：**先单独 `docker compose -f docker-compose.prod.yml --env-file .env.prod build api`**
  （api 阶段带 python3/make/g++，会编译成功并把 store 焐热），再跑完整 `./scripts/deploy.sh --tag <新tag>`
  —— admin 直接命中缓存，秒过。
- 根治方向（未做）：把 `deploy.sh` 的 `compose build api admin` 改成**先 api、后 admin 串行**；
  给 admin 阶段补工具链不划算（apk 装 gcc 实测 >20 分钟）。
- 另注：GitHub releases 在本机**完全不可达**（12s 超时，`http_code=000`）⇒ 别指望
  `prebuild-install` 下预编译包；`registry.npmmirror.com` 通（302）、`nodejs.org` 通（200）。

### 12.10 ⭐ 部署前的空间预处理：删旧镜像 tag，别碰 build cache（2026-11-04 实测）
- 起点：inode 86%（剩 113 万）；`docker system df` 显示 Images 20.34GB + Build Cache 23.63GB 可回收。
- 做法：**只删旧镜像 tag**（97 → 36，保留 `latest` + 当前 `TAG` + `PREV_TAG`）⇒ inode **86%→37%**、磁盘 82G→40G。
- ⛔ **别顺手 `builder prune`**：会打掉 `id=pnpm` 的 store，冷缓存下 admin 阶段缺 python3 直接失败（见 §12.9）。
  历史 tag 每个都拖着一整套层，才是 inode 的主要消耗者，删它们已经够。
- ⏱ `docker rmi` 逐个 1–3 秒，97 个约 **4–5 分钟** ⇒ 必须 `setsid` 后台跑再轮询；
  前台 SSH 会被 10 分钟超时 SIGTERM（本次第一次就断在「删了一半」处，靠 `docker images | grep -c` 才看清进度）。

### 12.11 ⚠️ `backup-db.sh` 必须给 `--out` 绝对路径
- 现象：`cd /opt/abox-onebox && ./scripts/backup-db.sh` 报
  `line 90: ./backups/xxx.sql: No such file or directory`，**而同一次的「代码备份」是成功的**
