# ABox 一盒 · 接口口径明细（从 MEMORY.md 迁出，做接口/账务改动前必读）

> 迁移时间：2026-09-15（M3-3 完成后）。MEMORY.md 因超出注入上限被截断，故把明细归档到此。
> **口径以代码与《ABox一盒接口规范v1.0.md》为准；本文是"易错点提示"，不是契约源。**

## 通用金额与日期
- 金额：接口出参**一律整数分**（字段名 `Fen` 结尾）。**例外**——L5 订单导出是「元字符串」行；L14/L15 的 `balance`/`totalCommission` 是元字符串；`commissionRate` 是 `'0.0800'`；**L12 提现入参 `amount` 是「元」**
- 日期：`mealDate` = `YYYY-MM-DD`；`toBjIso` 出 `+08:00`；实体 `Date` 序列化为 UTC `...Z`
- **余额真源 = `ab_balance`（user_id 维度）**；`ab_team_leader.balance/totalCommission` 只是统计快照，**不可用于展示或判断**
- **计佣基数 = 实发份数**（completed 订单份数，剔退款），非下单份数

## 通用红线（跨批次 · 每个批次都要遵守）
- **错误码纪律**：扩展码**必须回写《接口规范》§九**（号段末尾登记），**禁止挪用已占号位**；声明后未用要**显式释放**（如 `50014`）
- **后台接口挂载 `/admin/...`**（前缀本身就是鉴权依据）；控制器内**静态路由必须声明在参数路由之前**（否则 `GET /x/summary` 会被 `GET /x/:id` 吃掉）
- **双主体隔离**：`/admin/*`、`/supplier/*` 只收 `typ=admin`（越权 → `10003` / 未登录 → `10002`）；C 端与后台 id 各自自增 → **不隔离即静默越权**
- **两级权限白名单**：**类级**放 `operator`（能看列表/能跟进），**方法级**把写动作与**资金动作**收窄到 `super_admin`/`admin`/`finance`；写接口白名单时要**对照该角色菜单**（`admin-role.ts` = 唯一来源），否则出现「菜单能点、点了报 10003」
- **出款通道抽象** `PayoutChannel`（一期 `FLEX_MANUAL` 人工登记 / 二期 `FLEX_API`）；微信「商家转账到零钱」**不使用**
- **派生值不落库**（`licenseState` / `canServe` / `gap` / 集散主备路线号 R1…Rn）；**例外**：生产计划**生成即冻结**须落库
- **C9 结构不变**：`¥25.80 = 供价 + 场地费 + 打包 + 配送 + 佣金 + 经营毛利(结果值)`；供价逐菜协商
- **反向结算**：原记录**不得改写**（冲销写负行 `type='reversal'`，原 `normal` 行只翻 `status='cancelled'`）；出参金额恒正 / 份数为负；余额允许扣成负；⚠️ **供应商应付不被退款冲减**
- **可退额 = `total_amount − discount_amount`**（不是 `pay_amount`）；退款**拆两路**（通道 + 余额）；**C6 三段式**：审批与实退**同事务**、驳回资金零变动、缺 `order_status_before` → **`40014` fail-closed**


## ⭐ 结算口径（2026-09-16 自营裁定 · 详见《ABox一盒自营结算口径定义v1.0.md》）
> **做账务 / 结算改动前必读那一份**。此处只留最易踩的几条：
- **等式结构不变**（售价25.80 = 供价 + 场地费 + 打包 + 配送 + 佣金 + 毛利），变的是**付款对象 / 计费基数 / 退款承担 / 科目语义**
- **应付对象只剩供应商**（半成品采购款）；场地摊销 / 打包人工 / 配送费是 ABox 自身成本，**不出付款单**、进成本核算；`payee_type='distribution_center'` **冻结**（历史可读、新单不产生）
- **计费基数 = 实收量** `ab_supplier_dish_daily.actual_quantity`（未申报则 = 计划量），单价 = `ab_dish.cost_price`；**不是订单销量**
- ⭐ **用户退款不冲减供应商应付**（半成品已交付）→ 与 M3-3 已验收的 `reverseSupplierShares` **相反**，M3-9 前置要回退；`type='reversal'` 改义为「应付单算错」的纠错冲销。**但佣金侧退款冲减、余额回退不变**
- **S9 出单 fail-closed**：该日该菜父表 `status != 'done'` → **不出单**（此时 `actual_quantity` 只覆盖已确认明细，按它出单会少付、按计划补齐会多付）→ 进「未出单异常清单」
- **场地费语义换血**：`siteFee` 从「复用供应商场地·默认 0」→「**ABox 自有持证场所摊销**」，默认值不再为 0；经营毛利（计算值）≠ 实际净利（再扣履约成本）
- **不变量 I1**：供应商端**禁止出现**终端售价 / 佣金 / 毛利 / 成本合计（B2B 采购只该看到「我的价 × 我的量」）
- S9 新错误码预留 `50012` 单不存在或状态不允许 / `50013` 缺回单号 / `50014` 出餐确认未完成无法出单

- **L21 我的推荐** `GET /leader/invites`：只回**昵称**（零手机号）；`summary` 按全量算；**只统计 `inviter_leader_id = 我`**（自荐记录 `NULL` 不计入任何人的裂变成果）
- **L22 晋级审计** `POST /leader/level/audit`：月单 = 当自然月 `ab_commission` 份数合计（`status='settled'`，`type='reversal'` 按**负数量**折算）；介绍转正数 = **实时统计 与 `invited_formal_count` 取大**（兼容后台人工修正）；**只升不降**；**未升级也回写指标**（否则 P16 进度条永远读陈旧种子值）
- **U17 客服入口** `GET /me/support`：一期**不做在线客服** → 统一引导加客服微信人工处理；全字段来自 `ab_config.service.*`（**代码不写死联系方式**）；`wechatQrcodeUrl` 未配置回 `null`，端上隐藏图片位**不得伪造图片**
- 错误码 **20008 = 暂不能退出团长**；`error-code.ts` 自带纪律：**扩展码必须回写《接口规范》§九**（号段末尾登记，禁挪用已占号位）

## M3 后台基座（A2–A5 / D51–D56）
- **双主体隔离（M3 核心）**：小程序用户 `ab_user`(`typ='user'`) 与后台账号 `ab_admin_user`(`typ='admin'`) 是**两套独立表、id 各自自增**；`JwtAuthGuard` 按路径集中隔离 —— `/admin/*` 与 `/supplier/*` **只收 `typ=admin`**，越权 → **10003**(用户打后台) / **10002**(后台打用户端)；`/auth/profile|logout` 为双主体端点按 `typ` 分流。⚠️ 不隔离则 id 撞号 → **静默越权**
- **令牌吊销不入库**：改角色/停用 → 写 KV `admin:revoked:<id>`；`AdminGuard` 比对令牌 `iat` vs 吊销时刻 → **旧 token 立即失效**（12h 特权滞留 → 0）。`/admin/*` 走 AdminGuard；`/auth/profile` 由 `adminProfile` **查库兜底**（停用 → 20006）—— **两条防线独立**
- **角色→菜单以代码为唯一来源**（`common/constants/admin-role.ts`）：`menu key = 前端路由 path`；`super_admin=['*']`；**一期不建 `ab_admin_role` 表**；A5 每次**查库**返回 menus，是前端重建侧边栏的唯一来源
- **A2 后台登录**：失败 5 次锁 15 分钟（KV `admin:login:fail:<username>`，窗口 **TTL 只首次落**，防攻击永久锁死）；口令 `scrypt:<salt>:<hash>`（node:crypto 零依赖），种子期 `dev_plain:<明文>` 占位
- **D53 防自锁**三条 → **20010**（不能停用自己 / 降级自己 / 动最后一个 `super_admin`）；D52 登录名重复 → **20009**；D55 改角色**一期明确不支持**（`10001`，刻意不返回「保存成功」）
- **D56 操作日志**：全局 `OperationLogInterceptor` + `@OperationLog()` 声明式 → 业务模块零侵入；**写操作才记、失败的也记**、`password`/`token` 脱敏、写库失败仅 WARN

## M3-2 套餐编排 D1–D7
- **创建 ≠ 上架**：D2 建出来是 `pending`（用户端文案「该办公楼今日未开团」）；必须再走 **D4 `publish`** 才 `active`、用户端才 `canOrder=true`。编排可提前几天做，开团是临近时的动作
- **D1 矩阵返回「完整网格」** `cells.length = dates × groups`（无分配格 `assignmentId=null`）—— 空格子本身就是信息；单次上限 跨度 ≤31 天 且 `天数×楼群数 ≤400` 格
- **`assignedBuildings` / `emptyBuildings` 是派生值**：粒度是「出餐日 × 楼群」，**没有楼栋级分配表**；楼群内 `status=1`（合作中）算已分配，`status≠1` 算未分配（种子国贸组 C 座 `status=2` → 落 `emptyBuildings`）
- **唯一性** `uk_meal_assignment_date_group`；重复创建 → **30011**；已 `cancelled` 的历史行**复用**（唯一索引占位），不新建
- **D3 只改 `setMealId`/`distributionCenterId`**；改「日期/楼群」= 删旧建新（混进 PUT 会让幂等与操作日志的「改前/改后值」失去意义）；已截单不可改 → **30003**
- **D4 上架闸门**：已过截单（T 日 00:00）不许上架 → **30013**（放行 = 运营亲手造一个「用户端看得见可下单、下单必被 30001 拦下」的套餐）；**下架不设闸门**（紧急安全阀）；同向重复操作**幂等**
- **D5 三条**：① **不覆盖**已存在项（进 `skipped[]` 带 `reason`）② 复制出一律 `pending`（复制 `active` = 绕过 D4，未来若干天同时可下单）③ 已截单目标日跳过；建多行走**单事务**
- **D6 `usedCount`** = 被多少个**未取消**的分配引用（模板库最有用的一列）
- **D7 入参不含 `supplierId`/`costPrice`**：由菜品**反查** `ab_dish.supplier_id` + 供价求和；同菜重复占两档 → 10001；菜品不存在/已下架 → 30008；未传 `price` → 回落 `ab_set_meal.default_price`（¥25.80）
- **档位映射由服务端下发**（`GET /admin/meal/dishes` 的 `slots`：1 主荤/2 半荤/3 素菜/4 汤/5 主食），端上不维护第二份；该接口**只回上架菜品**
- **两个扩展只读选择器挂 meal 模块**（不挂 `admin/supplier/*`）：菜品/集散中心的**管理**属 D23–D32（未落地），编排页不该依赖未落地模块
- **类级权限** `@Roles('super_admin','admin','operator')` —— 财务与只读观察者无写权限（前端菜单过滤只是体验层）

## M3-3 订单中心 D8–D12
- **挂载路径 `/admin/orders/*`**（**不可写成 `/orders/admin/*`**）—— 前缀正是 `JwtAuthGuard` 的隔离依据，写成后者鉴权会退回用户端规则
- **路由顺序**：`GET export` / `GET filter-options` 必须声明在 `GET :orderNo` **之前**，否则被 `orderNo='export'` 吃掉
- **`tab=abnormal`** = `pending_pay` + `refund_applying` + `refunding`（**`cancelled` 不算异常**）；D8 无 `status` 时返回**含 `cancelled` 的全量**
- **`summary` 按同一过滤条件的全量**，不受分页影响；`validAmountFen === validQuantity × unitPrice` 恒成立（已取消/已退款剔出「有效营收」）
- **后台列表同样 `phoneMasked`**；**全号只有 D12 导出**一条路，且 D12 **无条件写操作日志**（含筛选条件 + IP）、单次上限 5000 行（超出置 `truncated`）
- **D9 `actions`** = `{canAdjust, adjustBlockReason, canForceRefund, refundBlockReason, refundableFen}` —— 按钮可用性口径**唯一在服务端**；`refundableFen = total_amount − discount_amount`（**不是 `pay_amount`**，后者只是微信那一段）
- **D10 入参是目标值**（`quantity`/`buildingId`）；改份数**仅 `pending_pay`**（已支付 → 30003，引导「先退款再下单」）；改取餐楼须**同楼群**（否则 **30015**）；两者都拦已截单 → **30014**；**不动 `ab_user.building_id`**（归属楼长期属性 vs 本单取餐地短期事实）
- **D10 操作日志 `targetId` 取自请求体**（路径里没有订单号）—— 拦截器已支持，否则 P31 按订单号查该单日志一条都查不到
- **D11 与 D41 分工**：订单已在 `refund_applying` → **40008 并指向 D41**（D11 是跳过申请与审批的**客诉兜底通道**，刻意不做隐式分流）；`amountFen` 是**防误操作参数**（不符 → **40011**，不是部分退款，一期只支持全额）；重复强制退款 → 40008
- **D11 退款拆两路**：微信实付走通道原路退，**余额抵扣单独退回余额**（喂给通道会被微信拒；喂进去了就是重复出款）
- **C9 反向结算落库**（`finance/reversal.service.ts`）：`ab_refund.reversed=1`+`reversed_at` · `ab_order.status='refunded'`（`cancelled_at` 复用为异常区时间线时刻）· 佣金**写新行 `type='reversal'`（金额/份数取负）+ 原 `normal` 行只翻 `status='cancelled'`**（**原记录不得改写**）· `ab_balance` 扣减（**允许为负**）· 应付三态 `not_generated`/`reduced`/`offset`（未生成时**不造空冲销行**）；平台毛利**留存**
- **`ReversalResult` 符号**：`commissionReversedFen` **恒正**、`commissionReversedQuantity` **为负**
- **`executeRefund` 是唯一执行口**（D11 强制退款 + D41 审批共用）；`refund.service.ts`（通道）与 `reversal.service.ts`（账务）职责分离
- **类级权限** `@Roles('super_admin','admin','operator','finance')` —— `finance` 可读订单（对账要用），`viewer` 不在白名单
- **扩展只读选择器 `/admin/orders/filter-options`**（楼群/办公楼/团长/11 态）—— 理由同 M3-2：订单中心不该反向依赖未落地的 3.5/3.7

## M3-4 退款审批 D40–D42（C6 第二/三段收口）

落点：`apps/api-server/src/modules/finance/refund-admin.{controller,service}.ts` · `dto/refund-admin.dto.ts` · 页面 `apps/admin-web/src/views/finance/refund.vue`（P34）

- **挂载路径 `/admin/finance/refunds/*`**；`GET /`（D40 列表）· `GET detail/:id`（**必须声明在 `:id` 之前**）· `POST :id/approve`（D41）· `POST :id/reject`（D42）
- **两级权限白名单（本批次核心权责分离）**：**类级** `@Roles('super_admin','admin','finance','operator')` —— 运营要跟进退款进度，所以 `operator` **能看**；**方法级** D41/D42 收窄到 `('super_admin','admin','finance')` —— **决定钱退不退是资金动作**，运营不能拍板。`viewer`/`supplier` → `10003`。「能看不能批」必须两条都断言（只测一条会把权限收窄写成全拦）
- **D40 `tab`** ∈ `all`/`pending`/`approved`/`rejected`/`refunded`（Tab → 状态集合**由服务端展开**，端上不各记一套）；`summary` 按**同一过滤条件的全量**（不受分页影响，含各 Tab 计数供角标）
- **D40 拆两路金额**：`wxAmountFen`（通道原路退）+ `balanceAmountFen`（余额抵扣回余额）—— **不合成一个数**（两者出款通道不同，合成后前端只能反推）；`keyword` 命中订单号 **或** 用户昵称；手机号一律 `phoneMasked`
- **D40 枚举下发**：`statusOptions[]`/`sourceOptions[]`（`REFUND_STATUS_LABEL`/`REFUND_SOURCE_LABEL` 落 `packages/shared-types/src/enums/order-status.ts`）—— **端上不维护第二份文案**
- **D41 状态闸门**：仅 `applying` 可审批（否则 **40013**）；退款单不存在 **40012**
- **D41 金额复核**：审批时以**当前订单**重算 `total_amount − discount_amount`，与申请单金额不符 → **40011**（防「申请后订单又被改」）
- **D41 审批与实退同事务**：先置 `approved` 再调 `executeRefund`（**D11 与 D41 共用唯一执行口**）。一期无 W2 退款结果回调 → 审批**不可逆见**；W2 接入后异步化
- **D41 出参**：回带订单快照 + `executionChain`（前端二次确认弹窗预览「将发生什么」）
- **D42 驳回资金零变动**（不写任何流水）：`ab_refund.status: applying → rejected`，订单回退到 **`ab_refund.order_status_before`**
- **`order_status_before` 是驳回唯一回退依据**：订单状态机对退款分支**只有单向箭头**（`paid → refund_applying`），反向没有边 → 不记则**无家可回**，只能猜默认值；缺失 → **40014 fail-closed**（宁可人工，不静默写错状态）。可空是为了兼容历史行，**不是「可以不写」**
- **D42 入参** `reason` **必填 ≥2 字**；驳回后订单回原状态 → **可再次申请**（不设次数上限，每次重走三段式）
- **操作日志 `targetId` = 退款单 id**（**不是订单号**）—— 与 D10 取请求体的理由相反，别照抄

  「平台还欠用户多少钱」不该因为运营敲了个昵称就变小 —— 把它做成「当前页求和」是最容易犯的错

- ⭐⭐ **冻结 / 解冻不动 `total_in` / `total_out`**：钱没进出平台，只是从「可用」挪到「冻结」（与 L12 提现
  「申请阶段不计入累计支出」同口径）。若把冻结记成支出，`total_out` 会随冻结 / 解冻来回跳并与提现累计互相污染

### D43 对账（`/admin/finance/reconciliation?date=`）

- ⭐⭐ **一期不许假装已经跟微信对过账**：无商户号 + 无 API 证书 → **物理上拿不到微信账单**。
  出参**强制**带 `channel.source = 'local_only'` + `billAvailable = false` + 人话 `note`（端上常驻
  `el-alert` 原样展示）。若实现成「内部两张表比对通过 → `balanced: true`」，运营会以为「**微信侧也平了**」
  —— 真正危险的差异（**微信收了钱、我们不知道**）将**永远不可见**。接入账单下载后只需把 `source` 改
  `'bill'` 并补比对段，口径不变
- ⭐⭐ **`date` 锚 = 支付日**（出参回显 `anchor: 'paidAt'` + `anchorLabel: '支付日'`）：微信账单**按支付日切日**，
  这是财务域**唯一一个 `date` 不指出餐日**的端点；拿它对 D33 / D34 / D36 的出餐日数字必然对不上 ——
  **那是两个时间轴，不是 bug**
- ⭐ **主体是差异清单、不是流水列表**（流水列表去 D33 / D40 看）：五类差异
  `order_paid_no_log` / `log_success_no_order` / `amount_mismatch` / `duplicate_transaction` /
  `no_transaction_id`，按「先查钱去哪了 → 再查状态 → 最后补凭证」的**处理优先级**固定排序
  （`RECON_DIFF_TYPES_ORDER`，也是分组顺序）；中文文案与 `nextAction` **由服务端下发**，端上不自造
- ⭐ **`nextAction` 必须写「不要做什么」**：「对账不平」四个字无法执行。实际下发：
  「**不要直接改库**」/「不能靠调平掩盖」/「**不可作为税前扣除凭证**」/「查回调是否重复消费」
- ⭐⭐ **三角恒等式**：`orderFen`（`ab_order.paid_at` 当日已付款）− `logFen`
  （`ab_payment_log.paid_at` 当日 `success`）= `diffFen`（**正常必须为 0**，正数 = 系统少收）；
  退款按 `refunded_at` **单列** `refundFen`、`netFen = orderFen − refundFen`
  （退款**不改写**原支付流水的日期归属）
- ⭐⭐ **`balanced` 是双条件**：金额相等 **且** `diffs.length === 0` —— 重复交易号 / 缺交易号
  **可能不影响两侧合计**（金额一样、只是凭证重复），只比金额会报「已平」，而凭证重复恰恰是
  **重复入账的前兆**
- ⭐ **差异检测三个方向**（缺一条就漏一类）：
  ① 当日订单 → 「订单说付了、账上没有」（含流水停在 `pending` 的形态，`statusText` 写明停在哪个状态）；
  ② 当日订单的**全部**流水 —— **刻意不限日期**：回调丢失时流水 `paid_at` 为空，按日期切会
  **恰好切掉最该抓的那一类**；③ 当日成功流水 → 「钱收了但订单没标」+ 同交易号多行（重复）
- ⭐ **刻意不提供「一键平账」**：对账的作用是**暴露**差异，不是把差异抹掉（`RECON_NOTE` 写明）
- 订单侧排除 `pending_pay` / `cancelled`（`ORDER_EXCLUDED_STATUSES`，**防御性**过滤：`paid_at` 理论上
  不会落在它们上）；`refund` 取 `status = 'refunded'`；流水取 `status = 'success'`
- 排序：**先按类型分组、组内按订单号**（运营是「一类一类去处理」，不是「按时间顺序看」）；
  `summary` 不受分页影响；`diffTypeStats` **每类都下发**（含 `count: 0`，端上不必自己补空洞）

### D44 发票管理（`/admin/finance/invoices?page=`）

- ⭐⭐ **零 DDL · 派生视图**：**不建 `ab_invoice`** —— 发票的全部事实已在 `ab_supplier_share`
  （`invoice_no` + `paid_at` + `payee_id`）。建表立刻产生**第二份真相**（「应付表说付了、发票表说没票」
  时以谁为准？），且与项目「**派生值不落库**」不变量冲突。表数仍 **27**
- **票的性质**：**进项票**（供应商开给 ABox），自营下是**税前扣除凭证** → 「钱付了、票没到」是一项
  **实打实的税务风险**，不是一张待办
- ⭐⭐ **粒度 = 供应商 × 月份**（不是单条应付行）：按应付行平铺会让运营看到「同一发票号重复 30 次」，
  **完全看不出**「这家这个月只开了一半」—— 而这正是最需要被发现的状态。三态
  `none` / `partial` / `full` 中 **`partial` 才是本页存在的理由**
- ⭐ **月份锚 = 应付单生成月**（`share_date`，**权责发生制**台账）：供应商拿当月全部货款催票、不是拿
  付款日催票，跨月付款（8 月账单 9 月付）**仍归 8 月**；复用 `monthRangeOf()`
  （项目里**月份边界的唯一实现**，与佣金 / 晋级审计同源）
- ⭐⭐ **分母只含「已付款」行**：未付款就要票，供应商不会给。未付款额**单列**
  `unpaidAmountFen` / `unpaidRowCount`、**不进开票状态判定** —— 否则一个刚出单的日子会满屏「未开票」，
  把真正的欠票淹没
- ⭐ **两个可执行的下一步**：
  `titleMissing`（**未登记开票抬头** → 去 D28 补，**没有抬头票开不出来**，最容易被漏的一环）·
  `overdue` + `overdueDays`（已付款超 **30 天**仍无票 = **税前扣除凭证缺失**的税务风险，
  `INVOICE_OVERDUE_DAYS = 30`）
- ⭐ **冲销行不进发票分母**：`type = 'reversal'` 负行只累加 `reversalFen` 作提示（若已按原金额开票，
  需与供应商**另行换票**）；本期不做换票流程 → **只提示、不改态**，边界在出参 `note` 写明。
  失效应付集合**直接复用** `stats.constants.ts` 的 `PURCHASE_VOID_STATUSES`
  （与 D47 / D33 **同一份定义**）
- ⭐ **分月必须在服务端内存完成**：`strftime('%Y-%m', …)`（SQLite）/ `DATE_FORMAT(…, '%Y-%m')`（MySQL）是
  **驱动相关**语法 → 用了就破坏「**四驱动零改动切换**」这条基线承诺，且**本地全绿、换驱动才炸**
  （同 M3-6 / D29 楼群筛选的处理）。`month` 筛选仍走 `share_date` 区间比较（跨库一致）
- ⭐ **`status` 是派生值**（库里只有 `pending` / `success` / `failed` / `reversed`）→ 必须
  **先聚合再筛**；非法枚举 → `10001`（**不静默回落成「全部」** —— 回落会让运营以为在看「未开票」
  而漏催一批）
- `payee_type` 仍显式过滤 `= 'supplier'`（自营下 `distribution_center` 已冻结）；**只给筛选条件时才**

- **D44 扩展入参**（M3-15 登记）：`month`（`^\d{4}-(0[1-9]|1[0-2])$`）/ `supplierId` / `keyword`（供应商名）/

  而补跑的动机恰恰是「跑批没跑成」，被锁挡住就完全失去用途；重复补跑的安全性由**业务幂等**保证。
- 日期校验：`date` 非法 → `10001`。⭐⭐ **必须走 `isRealDate`，不能只 `isDateStr`** ——
  后者放行 `2026-02-30`，而 `Date.UTC` 会**静默滚动**到 03-02：运营以为在补跑「2 月 30 日」
  并看到「完成」，实际批量改了 3 月 2 日的单（《缺陷与陷阱》#60 / 同族 #56）。
- 权限**两级**：类级 `@Roles('super_admin','admin')` —— **不含 `operator`**（补跑是改写历史数据的
  高危操作，不是日常作业，与 P39 打包任务含 `operator` 的取舍**相反、理由也相反**）；
  也不含 `viewer` / `finance`。菜单：`/system/schedule` 仅进 `ADMIN_NAV` 的**系统组**
  （`super_admin` / `admin` 可见），`ADMIN_MENU_KEYS` 同步 —— 授权了就必须有入口。
- **零新增错误码**：未知任务名 / 未实装 / 日期非法 → `10001`（均属「请求形状不对」）。

### 调度基座（`TASK_SCHEDULES` 单一真相）

- ⭐ **「几点跑」与「动哪一天」分开声明**：8 个任务一张表（cron + `dateKind` + 职责文案）。
  任务体**永远不写日期计算** —— 日期由 `ScheduleService.run()` 从声明表推导并**回传给 `fn`**，
  于是任务里根本没有写错日期的地方。
- `dateKind` 语义：`today`（T 日）/ `tomorrow`（次日）/ `yesterday`（前一日）/ `null`（**与出餐日无关**，
  全量扫描型如 `leader-expire`）。对 `null` 任务取目标日期**直接抛**（那是编程错误，不是运行时状况）。
- ⚠️ **锁不是保险丝**：`KvService.setNx` 加 `(任务, 目标日期)` 锁只防**并发重入**（Nest 的 `@Cron`
  在上一轮未跑完时**不会**自动跳过下一轮）。KV 在 `memory` 驱动下**重启即丢** —— 把幂等托付给锁，
  一次重启就会重复执行跑批。**成功保留锁、失败立即释放锁**（满足 4.11「失败可重放」）。
- 本服务**不落库**运行记录（不变量「派生值不落库」）；要查「昨夜跑了什么」看日志，不查表。

### 截单（4.2 · T-1 24:00）= 三分支，**顺序不可颠倒**

1. `pending_pay → cancelled`（批量，**同时解冻余额** —— 只改状态不解冻，用户的钱会被永久
   锁在一张已取消的订单上）
2. `paid → cut_off`（**锁定、不可逆**）
3. **定格备料量基数** → 再刷新生产计划（`SupplierService.freezeProducePlan`）
- ⚠️ **必须先截单再刷计划**：反过来的话计划量会按**未定格**的销量算出来，而它一旦生成就冻结了。
- ⭐⭐ **`ab_meal_assignment.sold_count` 的语义已改为「截单定格的已售份数」**（原注释「实时累加」
  是假的 —— 全仓无累加点，见《缺陷与陷阱》#59）。口径：计入 `status NOT IN ('pending_pay','cancelled')`
  的订单份数。**截单前不承诺准确，截单后不再变**。它是**采购款的基数（自营口径 = 实收量）**。
- ⭐ `freezeProducePlan` 只覆盖父行 `status='pending'`；已 `cooking`/`done` 的**跳过并告警**
  （那说明生产已经发生，改计划量只会让「计划」与「实际已生产」对不上）。
- ⭐ **跑批路径也必须落 `ab_operation_log`**（状态机 §2.1.5）：全局拦截器只对 HTTP 请求生效，
  故两次迁移在事务内**显式** `OperationLog.insert()`，`snapshot.source='system'`。
- 幂等以 `meal_date` 为键：重跑时已无 `pending_pay` / `paid` 订单，两分支自然为空，**无需幂等占位表**。

### 配送单（4.3 · T 日 00:30）

- 粒度 = **楼群**（唯一键 `(meal_date, building_group_id)`）：一天一个楼群一张单，与「一车货送一个
  楼群、团长在楼下收」一致。
- 份数与备料量**同源**（同一句「哪些订单算生产」），否则会出现「供应商做了 120 份、配送只送 100 份」
  而**两边都不报错**。
- ⭐ **幂等不覆盖**：已存在该楼群当日单即跳过 —— 司机 / 车牌是人工录入的，跑批抹掉就找不回来。
  ⚠️ 代价见《缺陷与陷阱》#61（份数也被冻住，**待补人工修正入口**）。
- ⭐ **可信度告警**：找不到任何 `cut_off` 订单时明确告警「截单可能没跑成，份数可能偏小」——
  否则份数偏小且**没有任何报错**。
- `expected_at` 锚在 **T 日 11:30**（存 UTC `03:30`）。

### e2e 相关

- 三个任务一律经**补跑接口 + 显式出餐日**驱动，不依赖 cron 触发时刻（cron 由调度库读真实钟）。

  **只影响 `now()`，不改 `@Cron` 真实触发时刻**（详见《缺陷与陷阱》§三）。

## M4-2 结算链路（4.4 自动确认 / 4.5 佣金入账 / 4.7 对账 · 2026-09-17 · **零 DDL · 零新增错误码**）

> 权威清单：《订单状态机与全链路流转 v1.0》§3。本批实装**结算链路三个任务**，8 个任务**全部补齐**
> （`GET /admin/schedule` 的 `summary.implemented` = **8/8**）。本批**改了两处既有口径**：
> ① 佣金引入**两段式**（影响 M2 的 L9 一键分发与后台 D34/D35）；
> ② `reconciliation.dateKind` 由 `today` 改 **`yesterday`**。

### ⭐⭐ 佣金两段式（本批头号口径）

```
T 日 14:00   accrueForOrders()  ──► ab_commission(status='pending')   只记账，钱不动
T+1 02:00    settlePending()    ──► status='settled' + ab_balance      钱到账（唯一入账口）
```

- **`creditCommissions()` 是唯一**把钱写进团长余额的地方，只被 `settlePending()` 调用 ——
  跑批（`commission-settle.task`）与后台 D35（`POST /admin/finance/commissions/settle`）
  **同一执行口**，故两条路径得出的 `balance_after` 必然相同。
- ⭐ **`pending` 是每天都会出现的正常中间态**。M3-13 时期写的「**一期 `pending` 常态为 0**」
  **已作废**；`scanned=0` 的含义收窄为「当天没有新确认的订单」，**记 log 不记 warn**。
- ⭐ **激活了一条死代码守卫**：`collectQuitBlockers` 的「有未结算佣金不得停职」——
  两段式前 `pending` 恒为 0、判据永不成立；现在天天有 `pending`，守卫**真正开始运行**（#52）。
- ⚠️ **入账金额一律取 `ab_commission` 行快照**（`leader_level` / `rate`），**不读团长当前值**；
  D35 仍**不收金额、不收团长**（一旦允许就等于开了「手工往团长余额加钱」的后门）。
- ⚠️ **补账只改账、不改事实**：只累加 `total_commission`，**不动** `total_orders` / `last_order_at`
  （否则污染 C2 晋级审计 —— 余额对了、佣金对了，只有晋级进度被悄悄推快）。

### ⭐⭐ 退款冲销 = **两条路径**（C9 修订）

| 原佣金状态 | 处理 | 余额 |
| --- | --- | --- |
| `pending`（已计佣、**尚未入账**） | 原行 `pending → cancelled`，**不写负向冲销行** | **一分未动**（钱从未进过余额）；`notes` 明写「**未动余额**」 |
| `settled`（**已入账**） | 写 `type='reversal'` 负行 + 原行 `status='cancelled'` | 扣余额（发生额历史保真） |

- ⚠️ **旧实现只有 `settled` 路径**：在 `pending` 窗口下会**从余额里扣一笔从未入账的钱** ——
  而余额**允许为负**（佣金已提现即形成欠款），于是会扣成负数形成**假欠款**，且**没有任何地方报错**
  （《缺陷与陷阱》#62）。
- ⭐ **出参符号与「是否已入账」无关**：`commissionReversedFen` **恒正**、`commissionReversedQuantity`
  **恒负**（端上按 `−X` 展示），故端上**不需要**按状态分叉。
- ⭐ **应付侧分文未动**：退款**不冲减**供应商应付（自营口径 2026-09-16 裁定），出参**保留字段**
  并显式声明 `supplierShareMode='not_applicable'` + 0 行 —— 让「应付未调整」成为一条**可断言的事实**。

### 4.4 自动确认（`auto-confirm.task` · T 日 14:00 · `dateKind='today'`）

- ⭐⭐ **只转 `delivered`**：其余态（`pending_pay` / `paid` / `cut_off` / `cooked` / `delivering` /
  `refund_applying` / `refunding`）**一律原样不动**，收进 `notDelivered.byStatus` 并 `logger.warn`。
  到 14:00 还没送达是**履约异常**，把它当「确认收货」会把异常洗成正常单（且佣金照计）→ **fail-closed**。
- ⚠️ **与 L9 手动确认刻意宽严不同**：L9 放行 `delivered` / `delivering`（团长在楼下收款时可能面对
  刚到货的实况），4.4 只认 `delivered`。两处差异已登记为**待裁决项**。
- ⭐ **无归属团长**：仍转 `completed` 并**收口计佣为 0**（`orphanConfirmed` 计数 + 日志），
  **不猜、不建号**（同 D35 `skippedReasons` 纪律）。
- 计佣走**两段式第一段**（只写 `pending`），晋级审计同批触发。

### 4.5 佣金入账（`commission-settle.task` · T+1 02:00 · `dateKind='yesterday'`）

- 执行口 = `CommissionService.settlePending()`（与 D35 **同一方法**，不另写第二套入账逻辑）。
- ⚠️ **不做「补计佣」**：只把**已存在的** `pending` 行入账；`ab_order` 没有「确认时刻的团长等级」
  快照 → 事后补算只能读**当前**等级 → 晋级后必然多算且无法自证（《缺陷与陷阱》#51）。
- 整批单事务 + 逐行 `UPDATE ... WHERE id=? AND status='pending'` 以 `affected` 判归属
  （并发下已被别处入账的行进 `skipped` 而不是重复加钱）+ 无归属进 `skippedReasons`。
- ⭐ **`monthOrdersOf` 的双计 bug 已修**：只数 `type='normal' AND status IN ('pending','settled')`。
  旧写法 `SUM(CASE WHEN type='reversal' THEN -quantity ELSE quantity END)` 配 `status` 过滤，
  会让退款单**先被排除、又被 `CASE` 加回** → 月单**不降反平**、可**凭退款刷 C2 晋级**（#63）。

### 4.7 对账（`reconciliation.task` · 每日 04:00 · **`dateKind='yesterday'`**）

- ⭐⭐ **目标日期 2026-09-17 由 `today` 改正为 `yesterday`**：04:00 对「今日」只能核
  `00:00–04:00` 这 **4 小时切片**，昨日 23:00 后的流水要等次日才被覆盖 → **每天都漏核一段**
  （《缺陷与陷阱》#64）。
- ⭐ **锚 = 支付日**（`paid_at`）：**财务域唯一不指出餐日的端点**（与 D33/D34/D36 刻意偏离），
  故出参显式回显 `anchor` / `anchorLabel` —— 否则运营会拿它对出餐日数字并得出错误结论。
- ⭐⭐ **不平才写日志，平了不写**：落 `ab_operation_log`（`module='finance'` /
  `action='对账不平'` / `target_id=日期`），后台「操作日志」页直接可见、可人工跟进
  （**零 DDL**，不建对账异常表）。**平了不写** —— 否则一年 365 条噪音会把这页淹掉。
  **幂等**：同日已有告警行则不重复写（补跑回报 `alerted=false` + `alertSkippedReason`）。
- ⭐⭐ **告警自带 caveat**：快照含「仅本地三头核对，**不等于已与微信侧对平**（一期无商户号与账单文件）」
  + `channel.source='local_only'` + `billAvailable=false` —— 这句话**写进告警本身**，
  不能只写在文档里（同 #55：**别让系统看起来比实际更可靠**；「不能把告警藏在服务器日志里」）。

## M4-3 队列消费者 + 订阅消息投递点（4.9 / 4.10 · 2026-09-17 · **零 DDL · 零新增错误码**）

> 权威来源：《接口规范 v1.0》§6.9（Q1 `/admin/queue`）+ §6.8 的「M4-3 实现口径」表 + §3.5 的「U15 / U18 一期口径」。
> 本节只留**最容易误用 / 最容易被读错**的那几条。

### 队列驱动与「会不会丢任务」（`GET /admin/queue`）

- ⭐⭐ **`durable` 必须如实下发，禁止静默降级**：`QUEUE_DRIVER=memory` → `driver='memory'` + `durable=false`
  + `note` 明写「进程内、**重启即丢**」。⚠️ **不能照抄 `KvService` 的「连不上就退回内存 + WARN」** ——
  缓存丢了只是慢一点，丢一条「**退款待重试**」**既无报错也无处可查**。故 `redis` 驱动**连不上拒绝启动**（fail-closed）。
- ⭐ **`failed` = 重试耗尽进死信**，**不是**「失败过一次」：中间的重试仍在 `waiting` / `delayed`。
  这条口径写进 `note`，否则运维会把「**重试中**」读成「**已经放弃**」并去做多余的人工介入。
- ⭐ **`attempts=3` 的语义 = 「总共执行 3 次」**（不是「重试 3 次」），且**两个驱动下必须一致** ——
  「换驱动不改行为」是四驱动架构的底线。
- 权限：`super_admin` / `admin` / `operator`（**含 `operator`**，运维要能第一时间看到「退款任务在重试」，同 P39 打包任务）；
  **不含** `finance` / `viewer` / 供应商 / 小程序 token（`10003`）。⚠️ 与 D47–D50 看板（**含 `viewer`**）**刻意相反**：
  那边是**业务数据**（只读角色本就该看），这里是**运行态实现细节**（驱动名 / 积压 / 重试参数）——
  给业务观察者看没有用途，只是扩大暴露面。

### 退款：外部通道**必须**在 DB 事务之外（本批头号口径）

- ⭐⭐ **为什么必须拆**：事务内调通道，一旦「通道成功 → 事务失败」，结果是**钱出去了、系统里没有退款单、订单也没变** ——
  **账实不符且没有任何机制能发现它**（旧实现抛 `40010` 只解决了「有单没退」这一个方向，反而制造了一个**更严重且不可自愈**的方向）。
- ⭐⭐ **事务 A（纯 DB，先提交）**：冲销 + 退款单 `refunding` + 订单 `refunded`。**提交之后就不可能再出现「钱退了系统没记录」**。
- ⭐⭐ **事务外**：调通道 → 成功走事务 B（`refunded` + `wx_refund_no`）；失败 → 单据 `failed` + **入队 `refund-apply` 退避重试**。
- ⭐⭐ **`refundNo` = 微信 `out_refund_no` = 幂等键**：重试带**同一个号** → 微信识别为**同一笔** → **不会重复出款**。
  ⚠️ **这是「允许自动重试」的前提**，没有它，重试就是把「一次失败」放大成「多次退款」。
- ⭐⭐ **失败不回滚账务**：`failed` 只描述「**通道**那一段」。订单**仍 `refunded`**、余额**已退回**、佣金**已冲销**。
  回滚会造成用户可见的反复（**余额退回来了又被扣走**）。对外语义因此是「**已受理，通道待重试**」，不是「什么都没发生」。
- ⭐ **`wx_refund_no` 未受理就留空**：写个假的等于**伪造凭证**，对账时无从分辨「真退了」与「我们以为退了」。
- ⭐ **纯余额退款（`wxFen<=0`）没有通道那一段** → 直接收口 `refunded`，**不入队**。
- ⭐⭐ **死信必须可人工处理**：重试耗尽 → 队列 `failed+1` **且**落 `ab_operation_log`
  （`module='queue'` / `action='任务重试耗尽'`，`target_id` = 队列名、`requestData.payload` 带**业务主键**如 `refundNo`、
  快照带**可重放 hint**）。⚠️ **只打服务器日志不够**（会随轮转消失，且没人会主动翻）：队列最大的风险不是「失败」
  而是**静默失效** —— 重试耗尽的含义是「这件事**已经没有人再管了**」。与 M3-15 对账告警**同一张表**。
- ⭐ **`enqueueRefundRetry` 失败也必须留痕**：若「微信退款失败」之后**连重试任务都没能入队**（Redis 抖动），
  则该笔退款**既不会重试、也不会有人知道** —— 账务已冲销、余额已退回，**微信实付那部分永远不会到账**。
- ⭐ **消费者是薄适配层**：三个 `.consumer.ts` 只做「注册 + 转发到原服务」，业务逻辑仍在原服务 ——
  不在消费者里复制第二份实现（否则「手动执行」与「队列执行」迟早分叉）。
- ⭐ **`attemptWxRefund` 自己判断「该不该跑」**：单据已 `refunded` → 直接返回（上次其实成功了，只是收口没跑完）；
  已 `rejected` → **记 WARN 后正常结束**（那是**本不该存在**的任务，重试 3 次只是白等 3 次）。
- ⭐ **「未启用导致 `delivered=false`」不算任务失败**：不得因它重试 3 次再进死信 ——
  否则真正的故障会淹没在「每天一条假死信」里（`completed≥1` / `failed=0` 才是正确期望）。

### 订阅消息投递点（3 个真实 / 3 个如实标 pending）

- ⭐⭐ **真实投递点只有 3 个**：`refund_result`（M3-12）+ `leader_apply`（团长申请确认）+ `commission_settled`（佣金入账）。
  里程碑原文列的四项场景里，`user_order_status`（简化原则不推）/ `leader_delivery`（走微信群人工）/
  `merchant_cook`（收件人是**供应商**，不是用户小程序身份）三者**接了也没有真实收件人** → **如实标 `pending`**。
  **宁失真绿，不假装贯通。**
- ⭐ **`wiring` 与 `enabled` 是两件事**：`wiring=live` = **代码有真实投递点**；`enabled=1` = **配置就绪**。
  一期 3 个 live 场景**全部 `enabled=0`**（缺微信模板 ID）——页面必须能同时表达「代码接好了、配置还没到」。
- ⭐⭐ **投递点一律在事务外 + `notify()` 不抛异常 + 服务内再兜 `try`（双保险）**：
  **通知是既成事实的告知**，永远不能把一笔成功的业务（退款 / 入账 / 申请）变成失败。
  e2e §30 用「通知失败仍返回 `isLeader=true`」钉死。
- ⭐⭐ **`settle-orders` 载荷按团长逐条，不按整批聚合**：订阅消息**必须能寻址到收件人**；
  聚合载荷没有收件人 → 消费者只能写日志 → **「通知用户」实际没发生却看起来成功**（《缺陷与陷阱》#68）。
- ⭐ **未启用 = 不投递且不留日志**（`ab_message` 语义是「**发过什么**」）—— 与 M3-12 同口径，本批新增的两个投递点**不得开例外**。
- ⭐ **幂等要跟到通知**：入账幂等，通知也必须幂等 —— 重跑一次就给团长重复发一遍「你的佣金已入账」是**用户可见**的骚然
  （e2e §30：重跑 `settled=0` **且 `notifyQueued=0`**）。

### U15 / U18（用户端订阅授权）

- ⭐ **U18 `GET /me/subscribe/templates` 是「问端上该请求什么」**：由服务端下发模板 ID，
  **端上不得硬编码**（硬编码 = 第二份真相：运营换模板后端上还在请求旧 ID，**两边都不报错**）。

  靠 `includes('用户')` 判断要不要索权，**改一次文案就静默失效**（不报错、只是从此不索权）。

  **空清单时什么都不做**（不拿假 ID 去请求）。

## M4-4 提现审批 D45 + D46/D46a/D46b/D46c（P34 · 2026-09-17 · **零 DDL · 新增 2 码**）

> 权威来源：《接口规范 v1.0》§6.5（D45/D46 系列）+「M4-4 实现口径」表 + §八 P34 映射 + §九 `40016` / `40017`。
> 本节只留**最容易误用 / 最容易被读错**的那几条。

### 端点与权限（两级白名单的最后一个缺口在此收口）

- 五个端点：`GET /admin/finance/withdrawals`（D45 列表）+ `POST /admin/finance/withdrawals/{id}/approve|reject|paid|fail`（D46 / D46a / D46b / D46c）。
- ⭐ **路由形态安全**：`withdrawals` 是**静态首段**、`{id}` 只在段中 → 不存在「参数路由吃掉静态路径」的问题（同 #45 判据）。**若将来加 `withdrawals/{id}` 详情，仍必须声明在 `withdrawals/export` 之类静态段之前。**
- ⭐⭐ **角色白名单收敛为单一真相**（`modules/finance/finance.constants.ts`）：`FINANCE_READ_ROLES`（**含 `operator`**）/ `FUND_ACTION_ROLES`（**不含 `operator`**）。
  此前 D35 / D39 / D41+D42 三处**各自硬编码**字面量 `'super_admin','admin','finance'` —— 四个副本的后果不是编译不过，而是**静默漂移**：改一处忘一处，就会出现「按钮亮着、点了 `10003`」（出参说可点、`@Roles` 说不行）或更糟的「按钮灰着、其实有权限」（**本该受管控的资金动作被默默放行**），二者都不报错，只在某次审计里才被发现。
- ⭐ 列表出参带 `actions.canApprove` 等**可点性提示**，但它**不是判据** —— 判据仍在服务端 `@Roles`，两者**共用同一份常量**（否则就是第 5 个副本）。
- ⭐ **与菜单同源**：`apps/admin-web/src/constants/index.ts` 的 `ADMIN_NAV` 里 `/finance/*` 出现在 `admin`/`operator`/`finance` 菜单中，故此处**不含 `viewer`** —— 「授权了就必须有入口，有入口就必须有权限」，两边不许单边漂移。⚠️ 与 D47–D50 看板刻意**含** `viewer` **正好相反**（那边 viewer 的菜单**只有**看板页，漏了就整个角色不可用）。

### D46a 驳回 / D46b 到账 / D46c 失败 —— 三路共用 `releaseFrozen()`

- ⭐⭐ **解冻只有一个方法，三个动作都走它**（`private releaseFrozen()`），差别**只有 `direction`**：

| 动作 | 结果状态 | `direction` | 账户变化 | `total_in` / `total_out` |
|------|----------|-------------|----------|--------------------------|
| D46a `reject` 驳回 | `rejected` | `'in'` | `frozen −X` / `balance +X` | **都不动** |
| D46b `paid` 到账 | `success` | `'out'` | `frozen −X` / `balance` 不变 | **`total_out +X`** |
| D46c `fail` 失败 | `failed` | `'in'` | `frozen −X` / `balance +X` | **都不动** |

- ⭐⭐ **解冻前必须校验 `frozen >= X`，不足 fail-closed `40015`**（**不复用 `40002`**）—— 两者对运维是**相反的动作**：`40002` 是「余额真的不够，让用户充值 / 少扣一点」，`40015` 是「**冻结记录与余额快照不一致**」的**账实不符信号**，必须去查数据（谁动过 `ab_balance`、有没有并发丢更新），**充了钱也解不开这笔**（#54 判据的第二次落地）。
- ⭐⭐ **`total_out` 的增量是「申请金额」而不是「实付金额」**：到账写 `frozen −X`（X = 申请额），若按实付（X − 代扣个税）记，`total_in − total_out` 就与 `balance + frozen` 对不上。e2e §31 用「到账前后 `(total_in − total_out)` 的**差值 === 申请金额**」钉死。
- ⭐⭐ **到账不写 `ab_balance_log`**：该表语义是「**可用余额的每一次变化**」（`direction` 只描述可用余额），而到账时**可用余额不变**（钱早在申请时就已冻结）。⚠️ 这**不是**「账本与快照不同源」—— `frozen` 与 `total_out` 的变化**从来**不由流水解释，D39 的 `freeze` 行即先例（`direction=-1` 而 `total_out` 刻意不动）。**到账事实由 `ab_withdraw` 自身完整承载**（`status` / `paid_at` / `actual_amount` / `payout_batch_no` / `voucher_no`）。
- ⭐ **`actual_amount` = 到手额**：`PAYOUT_TAX` 代扣的个税**没到团长手里** → 「累计已提现」取 `actual_amount` 而非 `amount`（与 `LeaderMoneyService.withdrawnFen` 同口径）。
- ⭐ **`payoutBatchNo` = `PB{yyyyMMdd}`**（按审批日聚合、**无随机位**）：与订单号 / 退款单号生成器**刻意区分** —— 批次号是**给灵活用工平台对账用的人可读标识**，同一天一批；随机位反而让人无法从号上读出日期。
- ⭐⭐ **状态机守卫 fail-closed `40017`（提现单状态不支持）**：`pending → approved`；`pending → rejected`；`approved/paying → success`；`approved/paying → failed`。**单不存在 → `40016`**。⚠️ 两码**刻意分开**：前者是「你把 id 打错了」，后者是「这单已经走到别处了」—— 看到码的人下一步动作不同（同 #54 判据）。
- ⭐ **驳回 / 失败都原路解冻回可用余额**（不是留在冻结里等人处理）：`collectQuitBlockers`「退出团长」的守卫以 `WITHDRAW_FROZEN_STATUS` 为判据、**只认占用中的单据**，三路都离开该状态集 → 不会把团长**永久困住**。

### 团长「钱」的唯一真源（修复《缺陷与陷阱》#69）

- ⭐⭐ **`ab_team_leader.balance` / `pending_amount` / `withdrawn_amount` 三列 = 历史字段**（列保留 · 可空 · **新逻辑不读不写**），与 M4-0 `ab_supplier.type` / `ab_distribution_center.supplier_id` 同一模式。

## M5-3 试运营交付 + 安全自检 + #49 时间类配置接调度（2026-09-17 · **零 DDL · 零新增错误码** · 表数仍 27）

> 权威来源：《接口规范 v1.0》§6.7（D57 / D58）+ §6.8（S1 / S2）+「M5-3 实现口径」表 + 《安全自检报告 v1.0》。
> 本节只留**最容易误用 / 最容易被读错**的那几条。

### ⭐⭐ 时刻的唯一真相与「两处派生」（#49 的修法）

- **只有 `common/utils/order-timeline.ts` 的 `DEFAULT_TIMELINE` 能声明时刻**（9 个）。`TASK_SCHEDULES[*].cron`（跑批几点触发）与 `time.ts` 的 `publishAtOf` / `cutoffAtOf` / `arrivalAtOf` / `autoConfirmAtOf`（下单窗口锚点、送达时刻）**全部是它的派生值**。
  - ⚠️ **在别处再写一遍数字（哪怕只是注释里当默认值用）＝ 重新制造 #49**。改时刻相关代码时先搜数字。
- ⭐⭐ **8 个任务类已全部移除 `@Cron`** —— 装饰器参数在**模块加载时求值一次即成静态元数据**，后台改配置**永远影响不到它**，这就是「配了不生效」的机制性根因。cron 改由 `tasks/schedule.registrar.ts` 在 `onModuleInit` 读生效时间轴生成并 `SchedulerRegistry.addCronJob()`。
- ⭐⭐ **热重载，不是「启动时读一次」** —— 只在启动时读一次会造出**半生效**：配置改了 → 下单窗口**立即**变（锚点逐次读 `currentTimeline()`）→ 但截单跑批仍按老时刻跑，且**两处都不报错**（比不接线更难查）。`setCurrentTimeline()` 带变更通知，注册器订阅后热重载。
- ⭐⭐ **读表失败绝不回落默认时间轴**（`BizConfigService.loadedOk`）—— 一次 DB 抖动若回落，就会把运营配的开团时刻**静默改回出厂值**且不报错；宁可沿用旧值。
- ⚠️ **`currentTimeline()` 是进程级单例** —— 一期单实例成立；**多实例部署必须改成配置变更事件广播**，否则「A 实例已改、B 实例仍按旧时刻跑」。
- ⚠️ **最危险的失败形态 = 任务静默不跑**（不再有装饰器报错兜底，而 e2e 全走补跑接口 → **发现不了**）→ 三道防线：注册完**逐名 `doesExist` 核对**（缺一个即抛错**拒绝启动**）· 启动横幅打印实际 cron（含「配置覆写」标记）· S1 下发 `registeredCron`。

### D58（系统配置写入）—— 三条新纪律

- ⭐⭐ **`24:00` 是合法值**（`time` 类型）：截单口径的原生表达就是 `T-1 24:00`（= **T 日 0 点**）。原校验只收 `00:00`–`23:59`，**模型根本表达不出来** → 种子只能写 `23:59` 当近似 → 与实际按 `00:00` 跑的 cron **差 1 分钟**且到处不报错（**这不是笔误，是模型缺一个值**）。`parseTimeOfDay` 现接受 `24:00`（**仅整点**，`24:01` 非法），配置校验与之**同源**（不是各写一份正则）；展示**原样写 `24:00`**、cron 折算 `0 0 0 * * *`。
- ⭐⭐ **跨键自洽校验**（`timelineConflict()`）：**逐项合法 ≠ 组合有意义** —— 开团晚于截单 → 下单窗口是**空区间**（谁都下不了单），而每项单独校验都通过、系统照跑、**没有任何报错**。规则：① 开团须**严格早于**截单；② 间隔须**大于** `order.cutoff_window_minutes`。不满足 → `10001` + **点名是哪两个键冲突**，与逐项校验**同一批失败**（整批不写入）。
  - ⭐ 判据在**服务端**：前端只是入口之一。
- ⭐ **5 项时间类配置 `unwired` → `live`**（`set_meal.publish_time` / `cutoff_time` / `delivery_arrival_time`、`commission.auto_confirm_time` / `settle_hour`）；**余 4 项仍未接线**（`supplier.settle_cycle` / `distribution_center.default_count` / `rice_fee` / `pack_fee`）+ 2 项策略标识 —— **如实标注不变**。

## M5-7 整体审查可修项收口（2026-09-18 · 零 DDL · **2 个新增错误码** · 门禁 19 → 20 道）

> 来源：`ABox一盒代码整体审查与缺陷汇总v1.0.md` §二 的 P1/P2。**先裁决**的 P0（#79 履约链 T7–T9）

1. **新增错误码（本轮唯一的两枚）**：
   - **`40018 BALANCE_CONCURRENT_MODIFIED`** = 「余额已被其它操作改动，请重试」——余额写入的 `version` 乐观锁未命中。⚠️ 它**不是**业务规则失败，而是**并发冲突信号**：调用方（运营后台 / 跑批）应**重试**；佣金入账跑批拿到它时**整批回滚**（结算可重入，重跑即可补齐）。

2. **退款审批的并发语义（`40013` / `40008` 现在各多一个来源，看 `message` 区分）**：
   - `POST /admin/finance/refunds/:id/approve` 的失败可能来自 **① 退款单行**（`findOne` 判状态，非 `applying` → `40013`）或 **② 退款单行原子占位失败**（`40013`，同一条已被别的操作员抢走）或 **③ 订单闸门**（`settleRefundDb` 第一步 `UPDATE ab_order … WHERE status IN (…)` 影响 0 行 → **`40008 REFUND_DUPLICATED`**「该订单的退款已被处理」）。

### 2. ⭐⭐ 本批最关键的发现：页面**默认日期 = 今天**

后台有 **4 处页面**的默认查询日期就是**今天**，而此前演示数据**全是 T-2 及更早**：

| 页面 | 默认口径 | 原后果 |
| --- | --- | --- |
| 佣金明细（A12/A13） | `date` 缺省 **今日** | 打开即空表 |
| 打包任务（A7） | `q.date` 缺省 → `defaultPackingDate()` | 空 |
| 看板（A2） | `range` 缺省 **7d**（尚可），但切到「今日」档 | 空 |
| 配送单（A7b–d） | `date` 缺省 → **最近一个配送日** | 若最新只到 T-2，则默认视图是 T-2 |

⇒ **「库里没数据」与「页面打开是空的」是两回事**。测试人看到空表会记成缺陷。
**修法：补一天的「今天（T 日）」数据**，而不是去改页面默认值（默认值是对的）。

### 3. ⭐ 「今日完成 → 佣金 `pending`」是**算出来的**，不是编的

`commission.service.ts::settlePending` 的文档已写明：**T 日确认收货计佣写 `pending`，T+1 02:00 入账**。
故演示集固定跑在 T 日 20:00 时：
- `completed` 且 `meal_date = 今日` ⇒ **必然 `pending`**（跑批还没到）
- `completed` 且 `meal_date ≤ 昨日` ⇒ **必然 `settled`**

⇒ 佣金 `pending` 的样本**不需要人为构造**，反而「`completed` 一律写 `settled`」是**错的**
（会让今天的单凭空多出一天账期）。自检 ⑫ 专门守这条账期。

### 4. ⭐ 发票「部分开票」此前**造不出来**（数据层缺陷，已修）

发票视图的**开票分母只含「已付款」行**（未付款就要票，供应商不会给）。旧写法把
供应商 2 的奇数单标成 `none` —— 而 `none` 的行是**未付款**的 ⇒ 不进分母 ⇒ 供应商 2 仍被判
「全开」，`partialCount` **恒为 0**，A17 的「部分开票」这一态**根本看不到**。

**正确造法**：同一供应商同月内，**已付款行有的开了票、有的没开**（`status='success'` + `paid_at` 有值，
但 `invoice_no` 为 `null`）。

### 1. ⭐⭐ U1 与 U6 的「团长归属」必须同判据（缺陷⑫ 收口 · **跨批次不变量**）

- 两处都回答「这一单佣金归谁」，此前**各写一遍且第一级不同** ⇒ 团长停职后首页显示 A、佣金记给 B。

### 2. ⭐ U1 `dishes[].supplierId` / U5 `supplier.id`：端上定位只认 id，不认 name

- ⚠️ **C8 边界**：`id` 不属于禁忌（不是状态 / 供价 / 分账 / 联系方式），但只在**已经能看见该供应商展示名**的
  接口里下发（U1 菜品行 / U5 溯源卡）—— 不下发到任何无名场景。
- ⭐ **跳转只传 id、不传上一页的 supplier 对象**：跳过去是**另一个页面实例**，数据由 U5 现取；
  传对象会造出「页面显示 A、实际数据是 B」的**第二种真相**。
