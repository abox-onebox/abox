### 1.1 法理链条（为什么三条同时成立）

1. **不冲突 123 号令** —— 123 号令约束的是「网络餐饮服务第三方平台」与「入网餐饮服务提供者」。
   自营在**自有**小程序卖**自己制作**的餐，ABox 是经营者本人、不是「平台」，
   平台侧义务（食安总监、每 6 个月实地复核、每年 1/7 月报省局、入网商户证照核验台账）
   **不适用**。
2. **不需要 EDI** —— EDI（B21）是「在线数据处理与交易处理」增值电信业务许可，
   它是**平台方**为他人提供交易撮合/在线数据处理的法定前置。
   自营不替别人成交、不代收分账 → 不触发。
3. **不涉二清** —— 用户付款进 **ABox 自己的商户号**，全额是 ABox 的经营收入；
   给供应商的钱是 **ABox 的采购支出**（B2B 对公付款）。
   资金**没有「过手他人资金」这一环**，四要素（钱过你手 + 你说了算 + 时间差 + 你管商户）不成立。
   → 「原『按自营定性 → 不涉二清』结论**作废**」这条作废说明，**现在也一并作废了**，
   回到「不涉二清」。

### 1.2 被本次裁定撤销的旧结论（保留备查，勿再引用）

- ❌ 走第三方平台（多商家入驻）路线 → 微信类目 `餐饮服务 → 外卖平台`
- ❌ 需《网络食品交易第三方平台备案》+ EDI（25–45 工作日）
- ❌ 二清风险 → 必须改「电商收付通」（平台为服务商 + 4 家开二级商户号 + 分账，默认分账上限 30%）
- ❌ 《供应商合作协议》→《平台入驻协议》改造、支付/结算/对账/退款系统改造
- ℹ️ 唯一保留的教训：**微信支付有主体关联 + 法人关联风控** ——
  同营业执照下任一商户号因二清被处置，其他商户号（含已有电商小程序）会被连带限制。
  自营路线下这条风险自动消失，但**仍不要用「商家转账」去做代收清算**。

## 二、123 号令：平台条款不适用，但**自营仍须守住的内核**

123 号令的内核对自营同样有约束力（通过《食品安全法》《食品经营许可和备案管理办法》落地）：

| 要求 | 自营下的落点 |
| --- | --- |
| 实体门店 | ABox 必须有**实际加工场所**（不是纯分装点） |
| **证照地址 = 线上店铺地址 = 实际出餐地址** | ⭐ **本模式最关键的一条**，见 §六 |
| **禁止异地代工出餐** | 半成品可外部采购，但**最后一道关键工序（热加工/复热/拼装）必须在持证场所完成** |
| 网店名 = 门面招牌名 | 门头必须是 **ABox 一盒** |
| 公示证照 + 门店实拍 | 小程序内公示 |
| 食安封签 | 配送环节必做（自营也做） |
| 无堂食标识 | 纯外卖形态需标注 |

### 4.3 合同与财务

- 《供应商合作协议》= **采购框架协议 + 食品安全责任条款**（要求供应商提供半成品的合格证明/检验报告）
- 供应商付款：**人工对公转账**（C10，系统只出应付结算单 + 回单号，不接支付通道）**不变**
- 团长佣金：**灵活用工平台**代扣代缴（C11）**不变**
- ⭐ **结算口径已定稿（2026-09-16）** → 见 **《ABox一盒自营结算口径定义v1.0.md》**（4 条裁定 + 2 条不变量）：
  ① 用户退款**不冲减**供应商应付（半成品已交付，退款是 ABox 自己的经营风险）；
  ② 计费基数 = **实收量**（S2 确认的 `actual_quantity`），非订单销量；
  ③ 应付对象**只剩供应商采购款**，场地/打包/配送为 ABox 自身成本、**不出付款单**；
  ④ `siteFee` **保留科目改语义** —— 「复用供应商场地·默认 0」→「**ABox 自有持证场所摊销**」。
  等式结构不变；中文口径「平台毛利」改称「**经营毛利**」（字段名不动）；**经营毛利 ≠ 实际净利**（后者再扣履约成本）。

## 五、⭐⭐ 仍需注意的实操卡点（自营下唯一真正的硬约束）

**「证照地址 = 实际出餐地址 = 网店地址」要求场地必须是 ABox 自己的持证场所**，于是：

- 现口径「集散中心**复用合作供应商场地** → 场地费默认 ¥0」**必须改**：
  若场地仍属供应商，则 ① 证照挂不上 ABox ② 门头是供应商名 → 两条都踩红线。
- 三条出路（三选一）：
  1. **自租厨房 / 中央厨房**（成本上来，但最干净）
  2. **在合作场地内独立设区 + 换 ABox 门头 + 独立进出**（需场地方配合，且要能通过现场核查）
  3. 借供应商的证照对外 —— ❌ **不可行**（自营定性立刻崩塌，回到平台/代工问题）
- ⚠️ **「半成品」到「成品」的工序要够实质**：
  仅「拆袋 + 拼盘」可能被认定为「经营外购即食食品」而非自制。
  必须在 ABox 场所完成**热加工/复温**工序（要有加热设备、温度记录、留样）；
  经营项目须覆盖「热食类食品制售」。

## 八、⭐⭐ 小程序内第三方平台跳转的合规判定（2026-10-03 逐字核官方原文 · 已否）

### 8.1 直接跳转 —— 命中 5.10 + 5.23.7（处理 = 下架）
- **5.10 互推行为**：不得为他人小程序/APP「**集中设立跳转**」。三平台**并排 + 「推荐」标记**
  正是教科书式命中形态；处理规则 = **下架**。
- **5.23.7**：未经授权不得「展示或者推荐其他微信小程序」。
- ⛔ **用 `web-view` 打开第三方店铺页技术上不可能**：`src` 只认公众号文章或**自己配置的业务域名**

  ⇒ **风险 100% 落在运营规范，不在技术**。

### 8.2 「不跳转、只复制口令」—— 比跳转更危险，单独被点名
用户设想「我不跳转，只让用户复制，应该不算违规」。**微信把这条通道单独写了条款**：

- 旁证：微信官方春节过度营销公告里「口令类信息」的违规举例**点的就是拼多多**
  ⇒ 那是**整治对象，不是可效仿的范本**（它只是体量够大扛得住）。

### 8.3 产品层面的反直觉点（独立于合规）

## 十、⭐⭐ 小程序客服通道的选型与硬约束（2026-10-04 逐条核实 · **已拍板走 B · 已实装**）

> 起因：用户嫌「复制微信号再加微信」太麻烦，要「小程序里直接跟同事沟通」。
> 方案《`ABox一盒小程序在线客服方案v1.0.md`》。**以下为核实过的硬事实，动手前不必重查。**

### 10.1 决定性约束：本项目**无 HTTPS / 域名 / 备案**
⇒ 排除的是**自建类**：自建客服后台（会话存档/自动回复/工单，微信要 POST 到**你的**服务器）、
web-view H5 客服（需已备案**业务域名** + 根目录校验文件）、小程序内自建 IM（另需《即时通信》类目）。
⇒ ⚠️⚠️ **2026-10-04 更正：第三方 SaaS 客服（芝麻/智齿/美洽）其实能做** ——
   **回调 URL 由第三方提供，我们只是把小程序授权给它，不需要我们自己的服务器**。
   代价 = 付费 + AppID/AppSecret 授权第三方（**数据出域**，隐私政策需同步说明）+ 多一个供应商。
   接线：小程序后台开消息推送（填第三方 URL）+ **关闭「在官方客服工作台收发消息」**。
   ⇒ 可用路径共**三条**：A 原生客服 / B 微信客服 / C 第三方 SaaS（B 办不下来时的保底）。

### 10.1b ⭐⭐ A 最致命的短板：同事**收不到可靠提醒**（用户问出来的，勿忘）
A 的提醒靠「**服务通知**」（同事首次开客服小助手时需点允许）。**但社区长期反馈它不靠谱**：
服务通知完全收不到、只能点进去看；不弹提示；网页端要手动刷新才显示；需**手动点「在线」**；
一个客服账号**绑多个小程序时只收到一个**的推送。
⇒ **A 的真实成本不是开发成本，是人力盯梢成本，且盯了还可能漏** ⇒ A 不能当主力，只能当过渡。
⇒ 若「同事不能漏消息」是硬要求 ⇒ **直接办 B**（消息进企业微信，同事正常收弹窗推送；
  需在企微工作台「微信客服」开「在企业微信里使用微信客服」+ 开消息提醒）。
⇒ 真先用 A 必须做 4 件事：① 首次打开点「允许」服务通知 ② 每次上班手动点「在线」
  ③ 别开免打扰 ④ 客服账号只绑我们这一个小程序；并在客服页如实写服务时间 + 兜底电话。

### 10.2 ⭐⭐ 48h / 5 条（A 与 B **都受限**，不是某方案的缺点）
用户发 1 条 → 客服 **48h 内最多连回 5 条**；用户进入会话 → 2 条 / 1 分钟；**条数不累加**，
用户每发一条刷新额度。⇒ 必须写进《客服手册》：**让用户回一句即可重置**。代码解决不了。

### 10.3 A · 小程序原生客服消息

  （userId + 手机号尾号 + 订单号）⇒ 客服在「客服小助手」里能看到来源
- 开通：小程序管理员 → mp 后台「功能 › 客服」→ 添加客服人员（**绑同事微信号，≤100 人**）
- 同事接待：微信里搜「**客服小助手**」小程序，或 mpkf 网页端
- **零成本、当天可用**；短板在客服侧：无分配 / 无转接 / 无统计

  （与 10.7 一致；方案文档 §七第 3 行曾写条件编译，已改）
