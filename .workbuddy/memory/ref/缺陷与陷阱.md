42. **并行编辑同一文件会互相覆盖**（M3-5 实测 · 工具流程类）:一条消息里发多个针对同一文件的编辑，**只有部分落盘**（实测 3 个里生效 2 个、2 个里生效 1 个）→ 出现「运行时是对的、文件里是旧的」这种极难排查的状态。**同一文件的编辑一律串行**，改完用 Grep 逐个复核关键行。**M3-8 再次复现且代价更大**：同一消息内对 `supplier.module.ts` 发两个 Edit → 后一个基于原始快照写回，**`forFeature` 注册被覆盖回旧版**，Nest 启动即报「无法解析 `SupplierDishDailyRepository`」（看似 DI 配置错，其实是被回滚的编辑）；对 `seed.ts` 连发 4 个 Edit（给 4 家供应商补 `auditStatus`）→ **只落 2 家**，e2e 表现为 `canServe=false` + 少一道菜这类内容级红，比直接崩溃更难归因。**铁律：一个文件一次 Edit，改完 `grep -c` 复核条数（如查 `auditStatus: 'approved'` 的出现次数应等于 4）**。⭐ **M3-9 起改用「一次性原子脚本」彻底绕开本坑**：把该批全部改动写成一个 `_patch_*.py` —— 每项带**期望命中数**，`count(old) != n` 即 `sys.exit(1)` 且**不做任何部分写入**（读全部 → 校验全部 → 一次写回）。实测同一轮 4 处 e2e 断言 + 14 处代码 + 34 处文档文案**零丢失**，并且「命中 0 次」会当场暴露锚点写错（本轮即靠它抓到两处锚点笔误）。**判据：批量改动（尤其文档）优先写原子脚本，而不是连发 Edit。**
43. **凡「一变须两变」的字段对，两侧都要断言**（M3-5）:`level` ↔ `commission_rate`、`leader.status` ↔ `user.team_leader_id`、`leader.building_id` ↔ `user.building_id` —— 只验出参不验落库，会让「算出来了没落库」漏网（M2 已踩过反向版本）；只验一边的同步，另一边的漏写就永远测不出来
44. **新建类接口的操作日志永远挂不到对象上**（M3-6 首跑红 · **真缺陷已修**）:操作日志拦截器的 `resolveTargetId` 只查 `params` 与 `body`，而**创建接口的 id 是服务端生成的** → `targetId` 恒为 `null`。后果：`POST /admin/suppliers` 的日志以「新增供应商」落库但挂不到任何供应商上，日后要查「这家是谁建的」只能翻 `request_data` 全文比对名字，**审计等于半残**。修法：成功后用**响应体** `id` / `data.id` 兜底（只认两层、**不深挖子对象** —— `order.id` 与 `user.id` 同现时选错就把「改了这单」记成「改了这个用户」）。⚠️ 判据：断言不该迁就实现（把 «targetId = 新 id» 改松成 «action 存在即可» 就是掩盖缺陷）
45. **两个端共用同一菜单键 → 平台端误占商家端页面路径**（M3-6 · **真缺陷已修**）:脚手架里 `/supplier/dishes` 与 `/supplier/edit` **同时**被平台端 `ADMIN_MENU_KEYS` 与商家端 `SUPPLIER_MENU_KEYS` 引用，而《目录结构 v2.0》§10.2 明确这两个文件属**商家端 P23/P24/P26**。按功能直觉往里写平台页 → 商家端页面被静默顶掉（不报错、不进类型检查、只有人点进去才发现）。修法：平台端 P33 改独立路径 `dish-library` / `form`，并同步 `routes.ts` 与 `admin-role.ts`。**教训：往既有目录写新页前，先 `git show HEAD:<file>` 看它原本是谁的**
46. **断言把「跨驱动差异」当成契约**（M3-6 三处红）:① 把 HTTP 状态码 `404` 当业务码（本项目业务码在 `body.code`，实际是 `10004`）；② 把 sqlite 的 `REAL` 当 MySQL 的 `DECIMAL(8,2)` 串（`String(0) === '0.00'` 恒假）——sqlite 无 DECIMAL 类型，`DECIMAL(8,2)` 退化为浮点/整型；③ 断言写成恒真式。修法：**断言不变量而非存储形态**（`Number(x) === 7.5` / `Math.abs(v-7.5) < 1e-9`），业务码只用 `body.code`，并在断言文案里写明「为何不能写死形态」。⚠️ **M3-9 再次踩中同一坑（「看懂过」≠「会用」）**：断言 `String(amount) === '750.00'`，而 `ab_supplier_share.amount` 写 `'750.00'` 读回 **`750`**（SQLite **NUMERIC 亲和性**）→ 恒假。**统一做法**：金额一律先归一到整数分再比 —— `const fenOf = (v) => Math.round(Number(v ?? 0) * 100)`，断言写 `fenOf(amount) === 75000`。**凡比较金额 / 单价 / 份数，先看列类型是不是 decimal，再看断言有没有做数值归一。**
47. **DTO 的 `'x' in dto` 恒为 `true` —— 「未传」与「传 null」分不开**（M3-7 首跑红 · **真缺陷已修**）:本项目 `target: ES2022` ⇒ `useDefineForClassFields` **默认 `true`** ⇒ TS 的类字段声明会在实例上**逐个 `defineProperty`（值为 `undefined`）**。于是 Nest `ValidationPipe` 交给服务层的 DTO **永远**含全部声明字段，`'buildingGroupId' in dto` / `hasOwnProperty` **恒真**。后果：D15「只改楼名」的请求被误判成「要移出楼群」（`patch` 凭空多一项）→ ① 空变更 10001 断言得 `code=0`；② 后续「传 `buildingGroupId: null`」因楼群**已被上一次误改清空**而 no-change → `code=10001`。**两条红看起来毫无关联，其实同一个根因。** 修法：一律用 **`dto.x !== undefined`** 判「字段是否被传」（`null` 是合法意图、`undefined` 才是未传），与 D18 `buildingIds` 保持一致。⚠️ 探针验证法：`plainToInstance(Dto, {})` 后打 `Object.keys(inst)` —— 会列出**全部**声明字段。⚠️ 判据：若改为写死「`'buildingGroupId' in dto` 且值为 null」，那是掩盖缺陷（真实语义是「未传 ≠ 传 null」）
48. **`node:sqlite` 的 `busy_timeout` 默认 0 —— 夹具直连读会撞上服务端的写事务**（M3-9 实测 · **环境型假红**）:e2e 夹具用 `new DatabaseSync(DB_PATH)` 直连**同一个** sqlite 文件，而服务端（TypeORM）可能正在跑写事务；默认 `busy_timeout = 0` 意味着**立刻放弃**并抛 `database is locked`。后果：一次毫秒级撞车被放大成「**整节异常中断**」，失败点与被测行为毫无关系（本轮表现为 `readDb` → `waitDb` 直接抛错、§16 整节没了）。**修法**：夹具统一走 `fixtureDb()` —— 内部 `db.exec('PRAGMA busy_timeout = 5000')` 后再用；`readDb` / `readRows` / `writeDb` 三个入口全部换成它（夹具事务都是毫秒级，等一会儿即可，故统一设 5s）。**判据：报错是 `database is locked` 且不在固定位置复现 → 查夹具连接，别查被测接口。**

49. **时间类配置与调度「分家」—— 配置写了，实际由 `@Cron()` 决定**（M3-10 排查发现 · ✅ **2026-09-17 M5-3 已接线并关单** —— 成因 / 修法 / 端到端证据见下方 ✅ 段）:`ab_config` 里 `set_meal.publish_time=14:00` · `set_meal.cutoff_time=23:59` · `set_meal.delivery_arrival_time=11:30` · `commission.auto_confirm_time=14:00` · `commission.settle_hour=02:00` 这 5 项**从未被任何代码读取** —— 实际调度**硬编码在各 task 的 `@Cron()` 装饰器**里（NestJS 的 cron 是**静态元数据**，不读配置）。另 `distribution_center.default_count` / `rice_fee` / `pack_fee` / `supplier.settle_cycle` 4 项同属「配了不读」（口径已改表驱动或代码常量）。**共 9 项**。M3-10 的处理是**如实标注 + 置只读 + 点明原因**（`CONFIG_SPECS.wiring='unwired'` + `unwiredReason` 直指是哪个 task），**没有**顺手接到调度上 —— 动态化需改用 `SchedulerRegistry` 或 `@Interval` + 运行期判断，会动到**用户可下单窗口**（`isOrderable()` 截止 23:00，而 e2e 全量依赖 14:00–23:00 时间窗），属独立验收项；混在配置批次里只会让「配置页做完了」掩盖「调度还没接线」。⚠️ 附一处**口径不一致待裁决**：配置写「截单 23:59」、`cutoff.task` 在 `00:00` 跑、而下单窗口实为 `[T-1 14:00, T-1 23:00)` —— 三者对不齐。**判据：任何「配置项」若无人读取，要么接上、要么如实标为未接线，不能让它看起来可调（「改了不生效」比「不能改」更伤运营信任）。**

53. **「平台负债」若在两个页面各算一套，漂移时不会有任何报错**（M3-14 · **已按「复用同一函数」收口**）:D33 资金总览与 D38 余额账户管理都要答同一个问题「**平台还欠用户多少钱**」。若两处各自写 `SUM(ab_balance)`，只要口径有一丝差异（是否含冻结、是否剔停用用户、是否按 `user_id` 去重），两个页面就会显示**两个不同的数**，而且**都不报错、都「算得出来」** —— 运营无法判断哪个是真的，只能凭「哪个数字更眼熟」。这类漂移只会在有人**同时打开两个页面**时被发现，而且常常被解释成「刚才有笔单进来了」。**修法**：D38 的 `liability` **不自己算**，把 `FinanceService.loadLiability()` 由 `private` 改 `public` 后直接调用（与 D33 **同一个函数**）；e2e 用「D38 `liability` **逐项等于** D33」在**写前 + 写后各钉一次** —— 写后那次尤其关键：它证明两边**同时看到本次写入**，而不只是「签名相同」。⚠️ **判据**：同一个业务量出现在**第二个读取点**时，先问「它是不是又算了一遍」；**把函数提为 `public` 复用，比在同一份代码里抄一遍安全得多** —— 抄出来的那一份，**永远不会有人去同步它**。（同族 #36「共用库串跑用不变量」、#46「断言不变量而非存储形态」：本项目头号顽疾「两个真相」在**读路径**上的形态。）
54. **「钱不够花」与「冻结账对不上」是两种故障，合用一个错误码会让运维做错事**（M3-14 · **设计裁定：分码 `40002` / `40015`**）:D39 的四个动作里，「扣减 / 冻结」超出**可用额**与「解冻」超出**冻结额**在数据形态上完全一样（都是「要的比有的多」），很容易顺手复用同一个 `40002 余额不足`。但两者对运维意味着**完全相反的动作**：前者是**余额真的不够**（等佣金入账、让用户充值、少扣一点即可解决），后者意味着**冻结记录与余额快照不一致** —— 钱可能在别处被改动过，这是**账实不符信号**，必须去查数据（谁动过 `ab_balance`、有没有并发丢更新），**而不是让用户充钱**（充了也解不了这笔）。合流一个码的后果：运维看到「余额不足」就去催用户充值，**问题被推给用户，而真正的数据不一致被掩盖**。**修法**：新增 `40015 BALANCE_FROZEN_NOT_ENOUGH`；两个 `BizException` 的 `data` 都回带 `availableFen` / `frozenFen`（否则运营只知道「失败了」，不知道「差多少」）。⚠️ **判据**：新增 / 复用一个错误码时，先问「**看到这个码的人接下来该做什么**」—— **若两种故障指向两个不同的下一步，就必须是两个码**。错误码是给人看的**行动指引**，不是内部状态的名字。

55. **把「内部两张表平了」当成「与渠道对平了」——对账页最危险的假绿**（M3-15 · **设计裁定：强制诚实标注**）:D43 的名字叫「与微信支付对账」，但一期**物理上拿不到微信账单**（无商户号 + 无 API 证书）。最自然的实现是「本地订单表 ↔ 支付流水表比对，两侧合计相等 → `balanced: true`」—— 代码算得出来、e2e 也全绿，但它悄悄把「**对账完成**」这句话的含义**改小了**：运营看到绿色的「已平」，会理所当然地认为**微信侧也平了**。而真正危险的差异形态恰恰**不在本地两表之间**：微信收了钱、回调丢了、我们这边什么都没有 —— 本地两表**双双缺这一笔，合计依然相等**，`balanced` 照样是 `true`。这类差异**永远不会被发现**，直到某天与真实银行流水对不上，而那时已经过了几个月、无从追查。**修法**：出参**强制**带 `channel.source = 'local_only'` + `billAvailable: false` + 一句人话 `note`（「⚠️ **这不等于已与微信侧对平** —— 微信侧未核对，接入后此处补账单文件比对」），端上**常驻** `el-alert` 原样展示；并把 `balanced` 的含义在 `RECON_NOTE` 里写明「只对本地三头」。⚠️ **判据**：任何**名字里含外部主体**的功能（「与 X 对账」「已同步到 Y」「对得上 Z」），先问「**这个外部主体的数据我到底有没有**」；没有就**必须在返回体里说没有**，且这句话要**常驻页面**而不是藏在 hover 里 —— **让系统如实说「我没做那一步」，比让它看起来做了要安全得多**（同 #50「声明与闸门是同一件事的两面」、#49「配置项若无人读取就是假可调」：同族纪律「别让系统看起来比实际更可靠」）。
56. **`@Matches(格式正则)` 挡得住「不像日期」，挡不住「日历上不存在」——`Date.UTC` 会静默滚动**（M3-15 首跑即中 · **真缺口，已修**）:入参校验写成 `@Matches(/^\d{4}-\d{2}-\d{2}$/)` 时，`2026-13-01` 与 `2026-02-30` 都能**通过格式校验**。后者尤其隐蔽：`2026-02-30` 格式完全正常、只是日历上没有这一天。而只要往下一步走 `new Date(Date.UTC(2026, 1, 30))` 或 `Date.UTC(2026, 12, 1)`，JS 会**静默滚动**到 3 月 2 日 / 次年 1 月 1 日 —— **不抛错、不返回 NaN**。后果不是「报错」，而是「**悄悄看错一天**」：运营打开 2026-02-30 的对账，看到的是一份 **2026-03-02** 的数字，页面标题还老老实实写着「2026-02-30」，**没有任何提示**。e2e 首跑就抓到了它（`2026-13-01` 未被拦，期望 `10001` 实得不符）。**修法（三处同修，缺一不可）**：① DTO 正则收紧到 `^\d{4}-(0[1-9]|1[0-2])-(0[1-9]|[12]\d|3[01])$`（挡得住 13 月，**挡不住 2 月 30 日**）；② `time.ts` 新增 `isRealDate()` —— 解析回读年 / 月 / 日三字段是否与原串一致（**这一步才是真正的拦截**）；③ **服务层兜底** fail-closed（DTO 只保护 HTTP 入口，**内部调用不经 DTO**）。⚠️ **判据**：日期 / 时间入参的校验**必须有一层「回读比对」**，纯格式正则只能算第一道；且这一层要放在**服务层**而不是只放 DTO —— 判据是「**这个函数被内部调用时还安全吗**」。**同族**：`@IsIn` 挡不住的枚举由服务层 `switch default` 兜底（#48 未知 `action` fail-closed）；两个都是「**DTO 是给外部调用者的礼貌，服务层才是最后一道墙**」。
57. **「派生视图」不要建表 —— 一旦建表就立刻有了第二份真相**（M3-15 · **设计裁定：零 DDL，从应付单派生**）:D44 发票管理的表结构第一反应是「建 `ab_invoice`（发票号 / 供应商 / 金额 / 开票日 / 状态）」，看起来干净、还省了每次聚合。但发票的**全部事实**其实早就存在了 —— `ab_supplier_share.invoice_no`（D37 付款登记时录入）+ `paid_at`（付没付）+ `payee_id`（谁的票）。再建一张表意味着**同一件事有两个存放点**：运营在付款登记里补录了发票号，发票表没同步 → 「应付表说付了、发票表说没票」，**两边都不报错、都「说得通」**，只能靠人记得去哪张表看。**修法**：D44 做成**纯读派生视图**（`invoice.service.ts` 只查询 + 内存聚合，零写入、零 DDL），表数仍 **27**，与项目「**派生值不落库**」不变量一致。代价是每次请求多一次内存聚合 —— 应付单按「供应商 × 出餐日」一行、一年量级千行，完全可控。⚠️ **判据**：新建表前先问「**这些字段里，有几个是既存字段的函数**」；若是函数关系，就**别存，算**。⚠️ **反例边界**：项目里确实有「派生值必须落库」的例外（生产计划 `ab_supplier_dish_center_daily`「**生成即冻结**」—— 因为它是**协商价快照**，事后重算会得到不同的数）。两者的分野不是「派生 vs 原始」，而是「**这个值事后还能不能重算出同一个结果**」：能算就别存，算不出来（快照 / 已发生的冻结事实）就必须落库。

58. **字段停用后，依附它的「可见性判据」会静默失效 —— 而且往往同时暴露一个合规漏洞**（M4-0 盘出 · **真风险，已修**）:M4-0 把 `ab_supplier.type`（出餐型/集散型/混合型）与 `ab_distribution_center.supplier_id` 降级为历史字段后，S3 `GET /supplier/packing-tasks` 的可见性判据「**本主体名下有启用中集散中心**」立刻**整体失效** —— 没有「名下」这个概念了，判据的分母变成空集。症状极具伪装性：e2e §20 的 **7 条 S3 断言全红**，而**只有 S3 红**（S1/S2 与 D 系列全绿），看起来像「S3 实现写错了」，于是第一反应是去改 S3 的代码。**但真问题是设计层面的两个错误叠在一起**：① 判据的技术失效（好修）；② 判据的**语义本身** —— 「名下有启用中集散中心即放行」意味着**任一供应商都能看到他方的到货明细**（打包线按场所聚合，天然跨供应商），**违反 I1「不泄露他方经营数据」**。⚠️ **只改判据（换成「有任一启用场所即放行」）会治①不治②，等于把同业数据开给每一个供应商**。**修法**：S3 **整条路由迁运营后台** `GET /admin/packing-tasks`（P39），供应商端路由删除（→ `10004`），判据改为**不按供应商收窄**（`defaultPackingDate()` 取全量最近生产计划日，不复用带 `supplierId` 的 `defaultDate()`）。**判据（可复用）**：① 停用一个字段时，`grep` 它在**所有判据表达式**里的出现 —— 每个出现点都要重新裁决「这个判据还成立吗」，**而不是等 e2e 变红**；② 当判据涉及「归属 / 可见性」时，除了问「谁看不到」，必须问「**这个数据面本身是不是跨主体的**」—— 是跨主体的，就不能靠调整条件把它开放给其中任何一方，**只能换个主体来承载**。⚠️ 「看不到」是技术问题，「**不该看**」是合规问题 —— 换判据只能治前者（同族 #50 / #55：**别把「做得到」当成「该做」**）。

59. **注释写着「实时累加」的字段，全仓可能一个累加点都没有 —— 下游派生基数会静默为 0**（M4-1 盘出 · **真缺口，已修**）:截单任务要「汇总各菜品份数推给供应商备料」，聚合基数取的是 `ab_meal_assignment.sold_count`（注释：*已订份数（实时累加）*）。但这个字段**全仓没有任何累加点** —— 下单不加、取消不减、退款不管，只有种子写过值。于是供应商拿到的备料量**恒为 0**，而 `ensureProducePlan` 里那句「`sold_count = 0` 的分配很常见」被当成正常现象读了过去（其实是「唯一可能」）。⚠️ **症状不是报错，是数字偏小** —— 供应商照着做会不够卖，**没有任何地方会显示异常**。**修法**（与「生产计划生成即冻结」同族）**不引入实时累加**（要在下单 / 取消 / 超时 / 退款四条路径同步维护，漏一条就是一次静默错账），而是在**截单这一「定格」时刻从订单表聚合一次并落库**；语义随之明确为「**截单定格的已售份数**：截单前不承诺准确，截单后不再变」。同时补 `SupplierService.freezeProducePlan()` —— 截单前若有人访问供应商工作台，会按**当时还在涨**的 `sold_count` **惰性生成并冻结**一份偏小的计划，截单后必须**覆盖刷新**（只覆盖 `pending` 父行，已 `cooking`/`done` 的跳过并告警）。**判据**：① 看到 `xxx_count` / `xxx_total` 这类**累加语义**的字段，先 `grep` 它的**写入点**，一处都没有就是「假累加」；② 自营口径下**采购款基数 = 实收量**，这个数直接决定付给供应商多少钱 —— 定格的时点必须与「截单」这一**业务事件**对齐，而不是与「某次恰好被访问」对齐（同族 #57：算得出来就别实时维护，**在唯一的定格时点算一次**最安全）。
60. **同一类校验的教训会在新代码里原样复发 —— 除非判据进了 checklist**（M4-1 自查抓到 · **真缺口，已修**）:M3-15 刚为「`Date.UTC` 静默滚动」加了 `isRealDate()`（见 **#56**），M4-1 新写的 `ScheduleAdminService.run()` 里却又写成 `!isDateStr(date)` —— 而它的报错文案**已经**写着「须为 yyyy-MM-dd，**且日历上真实存在**」。也就是说：**文案承诺了一道校验，代码只做了另一道**。放行 `2026-02-30` 在「补跑」这个入口上后果比读接口更重：补跑会**改写历史数据**，运营以为在补跑「2 月 30 日」并看到「完成」，实际批量把 **3 月 2 日**的订单置成了已截单 —— 选错一整天、**没有任何提示**。**修法**：`isRealDate` 替换 `isDateStr`，并在注释里写明「DTO 正则挡得住 13 月、挡不住 02-30，故服务层必须再兜一道」。⚠️ e2e 已按「`2026-02-30` → `10001`」钉死。**判据**：① 写新入参校验时**先看报错文案承诺了什么** —— 文案与实现不一致时，错的通常是实现（**文案是给人看的承诺**）；② 一个坑修完要**登记成可检索的 checklist 条目**（本文档的作用），否则下一个批次的新代码会重新踩一遍 —— **「我刚修过」不等于「不会再犯」**；③ 高危入口（改写历史数据 / 动钱 / 发通知）的日期校验一律走 `isRealDate`。
61. **「幂等不覆盖」保护了人工录入，同时也把错误的份数永久固化 —— 需要一个修正入口**（M4-1 盘出 · ✅ **M5-1 已收口**）:`DeliveryService.generateByDate` 对已存在的 `(meal_date, building_group_id)` 行**跳过不覆盖**，理由是「司机 / 车牌是人工录入的，跑批抹掉就找不回来」（e2e §28 已钉死：人工写入 `driver_name` / `plate_no` 后重跑，两者必须原样保留）。取舍是对的，但有代价：配送单的 `total_quantity` 也被一起冻住了 —— 若截单跑晚、或补跑改过份数，**表里的份数与实际要送的份数会长期不一致，而且没有任何页面能改**（`DeliveryController` 仍是空壳，无后台修正入口）。⚠️ 这与 #59 是**同一个「定格」语义的两面**：定格让数字可信，但**定格错了就没救**。**待办**：M4-3 / P39 之前补一个「配送单人工修正」入口（只允许改份数 / 司机 / 车牌，改动写操作日志），否则这个口子只存在 DBA 手里。

62. **退款落在「已计佣、尚未入账」的窗口里 —— 反向操作会扣一笔从未入账的钱，且没有任何地方报错**（M4-2 设计阶段盘出 · **真缺陷，已修**）:M4-2 把佣金改成**两段式**（T 日 14:00 计佣写 `pending` → T+1 02:00 入账写 `settled` + 进余额），这才暴露出旧实现的一个**静默错账**：旧的冲销只有一条路径「写 `reversal` 负行 + **扣余额**」。当退款恰好落在两段之间的窗口里（这正是两段式**引入**的窗口），原佣金仍是 `pending` —— **钱从未进过余额** —— 而冲销却去扣余额，扣的就是一笔**不存在的余额变动**。更糟的是 `ab_balance` **允许为负**（佣金已提现即形成欠款，这是**刻意**设计，硬拦会把退款卡死）→ 结果是**悄无声息地扣成负数、形成假欠款**，而账本自洽、接口返回成功、**没有任何校验会失败**。只有当团长提现或对账时才会发现「我欠平台钱」而自己并没超额提现。**修法**：冲销**拆两条路径** —— ① `pending`（未入账）→ **只把原行作废**（`pending → cancelled`），**不写负向冲销行、不动余额**，并在 `notes` 里明写「该单佣金尚未入账（`pending`），已直接作废、**未动余额**」；② `settled`（已入账）→ 保持原路径（`reversal` 负行 + 扣余额）。两条路径都**保持原行金额为原值**（C9：原记录不得改写）。⭐ **判据（可复用）**：任何「反向操作」实现前先问「**正向那一步到底做到哪了**」—— 只要流程有中间态，「还没做」与「已经做完」就**必须走不同的反向路径**；用同一条路径处理两种前置状态，反向操作就会作用在一个**从未发生的变动**上。⚠️ 这类 bug 的特征是**不报错、账本自洽、只有跨主体结算时才暴露**（同族 #59「数字偏小不报错」、#63「月单不降反平」）。

63. **`SUM(CASE WHEN type='reversal' THEN -quantity ELSE quantity END)` + `status` 过滤 = 退款单被排除后又被加回**（M4-2 盘出 · **真缺陷，已修**）:`monthOrdersOf`（C2 晋级的月度单量判据）曾用 `SUM(CASE WHEN type='reversal' THEN -quantity ELSE quantity END)` 配合 `WHERE status IN (...)` 计算「本月完成份数」。问题在于**符号补偿与状态过滤写在两个地方**：`ab_commission.type='reversal'` 的行 `quantity` **本身已经是负数**，`CASE` 再取一次负 → **翻成正**；而它的 `status` 又恰好**不在** `('pending','settled')` 里 → **先被 `WHERE` 排除、又被 `CASE` 无条件加回**。净效果：**退款对本月的月单量几乎没有任何影响**。后果不是「数字难看」，而是**晋级审计可被刷**：退款是**免费**的（钱全额退回），于是「先下单冲单量 → 退掉」就能把 `month_orders` 推高，凭退款拿到 C2 晋级（正式 / 金牌 / 首席费率更高）。**修法**：只数 `type='normal' AND status IN ('pending','settled')` —— 把「哪些行算数」收进**一个**判据表达式，不再用 `CASE` 做符号补偿。⭐ **判据（可复用）**：① 一张表里**行本身带符号**时，**永远不要**在聚合里再补一次符号 —— 两种写法选一种：要么行是正的、聚合按 `type` 减，要么行带符号、聚合直接 `SUM`；② **过滤条件与符号补偿分散在两处**（`WHERE` + `CASE`）时，只要两者的作用域不一致就会**互相抵消**，而 SQL 不会因此报错 —— 把「算哪些行」写成**一个**判据。（同族 #43「凡『一变须两变』的字段对，两侧都要断言」、#36「写不变量而非当时那次数字」：**两个真相**在聚合层的形态。）

64. **跑批的「目标日期」写成 `today`，会每天漏核一段 —— 而每天的结论都「看起来是对的」**（M4-2 改正 · **设计口径错误**）:`reconciliation.task` 的 `dateKind` 原写 `today`（文档与声明表**同步写错**，故不会有任何不一致告警）。每日 04:00 跑批若核「今日」，核到的只是 `00:00–04:00` 这 **4 小时切片**；而 T 日下单窗口是 `[T-1 14:00, T-1 23:00)` —— 昨日 23:00 前后的流水要等到**次日**才会被覆盖到。于是**每一天都有一段时间从未被对过**，但每天的输出都是「核过了、平的」。⚠️ 这类缺陷的伪装性在于：**它不制造错误数字，它制造缺失覆盖** —— 对账的每一行输出都正确，只是永远有一块盲区；等到某天与真实银行流水对不上时，盲区已累积几个月、无从追查。**修法**：`dateKind` 改 `yesterday`（在 `TASK_SCHEDULES` **一处**改，任务体不写日期计算），核**完整自然日**，且此时 T 日的流水已闭合齐全。⭐ **判据（可复用）**：跑批任务的「目标日期」**不能靠「触发时刻看起来像」来定** —— 要问「**在这个时刻，我要核的那个数据源到底长完了没有**」；核「一段完整区间」的任务，目标日期应当是**已经结束的那一天**，而不是「今天到目前为止」。（同族 #55：对账的「完成」二字含义比名字小，必须在返回体里显式标注 —— 本条是它的**时间轴版本**。）

65. **`git commit` 会在提交瞬间改写文件 —— 「已验收的代码」可能从来不是「已提交的代码」**（M4-2 收尾复核 · **防御性纪律，本次未实际发生**）:本项目 husky + lint-staged 会在 pre-commit 阶段对**暂存文件**跑 `prettier --write`（输出里的 `[STARTED] *.{json,md,scss,css}` / `Applying modifications from tasks...` 就是它在**改内容**）。于是链路变成：工作区 A → 跑门禁验 A（15/15 绿）→ `git add` → commit 时 prettier 把 A 改成 A′ → **提交进去的是 A′**。若被改的是 `*.{ts,vue}`，那么 **lint / typecheck / build / e2e 从未跑过 A′** —— 门禁的 15/15 是**关于 A 的**，不是关于仓库里那份代码的。⚠️ 这与 #42「批量改文件要原子脚本」是**同一族**：都是「**你验的和实际生效的不是同一个东西**」，只是这里动手的是钩子而不是脚本。**本次实测**：`chore(baseline)` 提交时 lint-staged 报 `*.{ts,vue} — 0 files`（因为 `feat` 那笔已把格式化做尽），且**提交后对 HEAD 复跑 `gate.mjs all verify` 同样 15/15**、`verify-manifest` 仍 219/219 —— 即本次**已提交内容 = 已验收内容**（这条是**机制上的隐患**，不是本轮已发生的缺陷，如实标注）。⭐ **判据（可复用）**：① **提交后**对 HEAD 复跑一次门禁（或至少 `git status --porcelain` 必须为空 + 复跑 `verify-manifest`）；② 看 commit 输出里 lint-staged 有没有 `Applying modifications` 与**非 0 文件数** —— 有就说明它改了东西，**改了就必须重验**；③ 最省事的规避：**提交前先 `gate.mjs format:write`**，让工作区本身就是格式化终态 → lint-staged 无可改（本次正是这条在起作用）。⚠️ 反例边界：格式化只影响空白 / 换行时，语义风险低但**字节风险真实存在** —— 项目里 `verify-manifest` 是**字节 + SHA-256** 比对（#34），一个空行差异就是 219 行里的失败项。（同族 #34「清单按字节校验」、#42「原子脚本带期望命中数」：**证据必须与产物对齐，对齐不了就等于没有证据**。）
66. **「编译期全绿」不等于「服务能起来」—— DI 解析发生在运行时，`tsc`/`eslint`/`build` 全查不出**（M4-3 收尾盘出 · **真缺陷，已修**）:M4-3 给 `RefundService` 加了「退款重试入队失败」的操作日志，于是构造函数多了一个 `@InjectRepository(OperationLog)`。`typecheck:api` / `lint` / `build:api` **全部通过**，但服务**启动即崩**：`Nest can't resolve dependencies of the RefundService (DataSource, OrderRepository, RefundRepository, ReversalService, Symbol(WX_PAY_PROVIDER), MessageService, QueueService, ?). Please make sure that the argument "OperationLogRepository" at index [7] is available in the FinanceModule context.` 根因是 `FinanceModule` 的 `TypeOrmModule.forFeature([...])` **没注册** `OperationLog`（只注册了 Commission / SupplierShare / Balance / … / SupplierDishDaily 十四个）。⚠️ **当时的第一反应是错的**：「`CommonModule` 是 `@Global()` 且已经 `forFeature([TeamLeader, OperationLog])`，所以 `OperationLogRepository` 应该全局可见」—— **这个假设不成立**。⭐ **`@Global()` 只让该模块 `exports` 的东西全局可见**：`CommonModule` 的 `exports` 是 `[KvService, QueueService, BizConfigService, LeaderGuard, AdminGuard]`，**没有** `TypeOrmModule` —— 从别处 `import` 进来的 provider **不会二次导出**，那两个仓储只在 `CommonModule` **自己的上下文**（`QueueService` / `OperationLogInterceptor` 的构造注入）可用。**修法**：把 `OperationLog` 加进 `FinanceModule` 的 `forFeature`（与 `tasks.module.ts` / `admin.module.ts` 的既有做法一致 —— **谁注入谁注册**）。⚠️ 这条缺陷的**真正代价不在修法**，而在它**藏了整整一轮**：`typecheck` 与 `build` 绿得毫无破绽，唯一能发现它的是**真起一次服务**；而当时恰好没有在改完代码后立刻跑 e2e，于是「门禁 15/15 全绿」被当成了「可以提交」。⭐ **判据（可复用）**：① **依赖注入是运行时行为**，静态检查（`tsc --noEmit` / ESLint / `nest build`）**在原理上就不可能发现**它 —— 任何「新增构造注入」的改动，**必须在同一轮内真起一次服务**（哪怕只跑一个起服务 + `/health` 的探针），否则「门禁全绿」这句话只是关于**编译**的，不是关于**可运行**的；② 看到 `Nest can't resolve dependencies ... at index [N]` 时，**先数构造函数的第 N 个参数**（`?` 就是缺的那个），再去**声明它的模块**看 `forFeature` 清单 —— 不要顺着「应该是全局的」往下猜；③ 项目纪律「派生值不落库」的对偶版：**能力不会因为你以为它是全局的就真的全局** —— `@Global()` 的语义边界（只对 `exports` 生效）写进本节，别在下一个批次重新假设一遍。（同族 #65：**机制上的隐患**；本条是它在**依赖注入**层的实例 —— 都是「你验的和实际生效的不是同一个东西」。）

67. **跨端字符串契约（页面路由 / 模板 ID）没有任何校验点 —— 写错了「微信照收、服务端照发、用户点开落到空白页」，四处都不报错**（M4-3 盘出 · **真缺陷，已修 + 已加机械对账**）:退款结果订阅消息的落地页在 `refund.service.ts` 里硬编码成 `'pages/order/detail'`，而 `apps/miniprogram/src/pages.json` 里的**真实路由**是 `pages/order-detail/order-detail`（目录名带连字符、且是 `order-detail/order-detail` 这种「目录 = 文件名」的小程序写法）。后果是一种**极其安静的失效**：`notify()` 返回 `delivered=true`、`ab_message` 落一条 `status=success`、服务端日志写「已投递」、**微信也照发**（它只负责把 `page` 塞进通知，**不校验页面是否存在**）—— 只有用户点开通知时才会看到一个空白/报错页，而**没有任何人会收到这个反馈**（用户只会觉得「这 App 有毛病」）。⚠️ **为什么这类缺陷特别危险**：它同时满足「所有机械证据都是绿的」与「真实体验是坏的」，因此**不可能靠跑门禁发现** —— 只有把它**变成一条断言**才行。**修法（两步，缺一不可）**：① 把落地页集中到 `message-template.specs.ts` 的 `NOTIFY_PAGES` **单一常量**（`orderDetail` / `leaderCommission` / `leaderWorkbench`），消灭「同一个路由在服务端有第二份写法」；② ⭐ **在 e2e §30 加一条机械对账** —— 从 `message-template.specs.ts` 抽出 `NOTIFY_PAGES` 的所有值，逐个断言 ∈ `pages.json` 的 `pages[].path`（`pages=3 dangling=无`）。**只做第①步只是把风险挪了个地方**（常量内仍可能写错），第②步才把它**关掉**。⭐ **判据（可复用）**：① 任何**跨端 / 跨系统**的字面量（页面路由、微信模板 ID、回调地址、枚举名），都要问「**如果它写错了，谁会报错**」—— 答「没有人」时，它就必须有一条**机械对账**，而且要拿**消费端真正的声明文件**（`pages.json`）当 oracle，不是拿另一份文档；② 「收敛到单一常量」是**必要条件而非充分条件** —— 常量只是把「多处可能写错」变成「一处可能写错」，**校验才是防线**；③ 这条与 M3-12 的「模板 ID 由服务端下发、端上不硬编码」是**同一条纪律的两端**：**所有跨端标识都必须有一个唯一的权威来源 + 一处机械校验**。（同族 #63 的「两个真相」、#65 的「机制隐患」，但增益在于：**这一类失效不会以任何错误形式出现**。）

68. **消息载荷里没有收件人 = 「通知成功」其实什么都没发生**（M4-3 设计阶段盘出 · **设计缺陷，已修**）:`settle-orders` 队列的载荷原本是**整批聚合**形态 —— `{ mealDate, settledCount, totalFen }`（「今天共 X 笔、合计 ¥Y 已入账」）。这在「入队成功」这个层面完全说得通：跑批算完一批，入队一条汇总。但**订阅消息必须指定收件人**（`userId` → openid → 微信 `touser`）—— **聚合载荷里根本没有收件人**。于是消费者唯一能做的事就是**写一条日志**：任务正常结束、队列计数 `completed +1`、接口返回成功、`failed=0`，**而数十位团长一条通知都没收到**。⚠️ 这类缺陷的特征是「**每一层都成功**」：跑批 `settled>0` ✅、入队 ✅、消费完成 ✅、无死信 ✅ —— 只有「用户到底收到没有」这一层是空的，而它**恰恰没有任何计数在观察**。**修法**：载荷改为**按团长逐条**（`{ mealDate, leaderId, settledCount, amountFen }`），`settlePending` 在事务内**收集**、事务提交后**逐条入队**（单条失败不影响整批 + ERROR 日志），消费者按 `leaderId` 查团长 → `notify()`。收益不止「能发出去」：**独立重试**（一个团长查库失败不会连累其余 19 个）、**死信粒度到人**（运维看到的是「谁的那条卡住了」而不是「一批里有问题」）、**幂等可重跑**（e2e §30 钉死重跑 `notifyQueued=0`，不会把同一句「你的佣金已入账」给同一人发第二遍）。⭐ **判据（可复用）**：① 设计队列 / 事件 / 消息的载荷时，**先问「这条消息最终要投给谁」** —— 要投给「某个人」的，载荷里**必须有能定位到那个人的键**；聚合形态只适用于**给系统自己消费**（统计、对账、告警），一旦下游是「通知人」，聚合就是错的；② 「**任务成功**」与「**业务结果发生**」是两件事：本条的 `completed+1` 只证明「消费函数跑完了」，不证明「通知到了」——**验收断言必须落在业务事实上**（e2e 断言的是 `notifyQueued` 与「未启用时不投递」，而不是「任务没报错」）；③ 同族 #66 / #67：**别让系统看起来比实际更可靠**（#55 的第三次重现），但本条的特殊之处是**它连一条错误日志都不会产生**。

69. **`ab_team_leader` 上的三个金额列是「假真源」—— 全仓零写点，却被三个出参当真值下发**（M4-4 盘出 · **真缺口，已修**）:`ab_team_leader` 挂着三列看起来像「钱」的字段：`balance`（注释*可用余额*）、`pending_amount`（待入账）、`withdrawn_amount`（已提现）。它们**只在种子里被赋过值，全仓没有任何写点**，而 `balance` 恰好被**登录 / 资料 / 退出**三个出参当作「可用余额」下发。后果是团长**在同一时刻看到两个不同的余额**：小程序「我的」页显示的是**种子里写死的数字**（示例数据 ¥575.86），而「余额明细」页走 L11（`ab_balance`）显示的是**真值** —— 两者都不报错。更硬的后果是他去提现时被 `50004 可提现余额不足` 挡下（真值可能是 0），而页面上明明写着有几百块 —— 这是**必然会产生客服工单**的一类错。⚠️ 最讽刺的一点：`ABox一盒MVP` 的两个前端文件里**早已写明**「`ab_team_leader.balance` 仅为快照，勿用；展示可用余额请走 L11 `balanceFen`」（`api/leader-finance.ts` / `api/leader.ts`）—— **明知有坑，服务端出参自己还在踩**；而前端的这条注释正是「口径只写在文档/注释里、没有机械校验」的产物（同 #67）。**修法**：新增 `LeaderMoneyService`（注册在 `CommonModule` 并 `exports`，任何模块直接注入），四项**全部派生**、**不读不写那三列**（改历史字段，与 M4-0 `ab_supplier.type` / `ab_distribution_center.supplier_id` 同一模式，见 **#58**）：`balanceFen`←`ab_balance.balance`、`frozenFen`←`ab_balance.frozen`、`pendingCommissionFen`←`ab_commission(status='pending' ∧ type='normal')`、`withdrawnFen`←`ab_withdraw(status='success')` 的 **`actual_amount`** 合计。⭐ `withdrawnFen` 取 `actual_amount` 而非 `amount`：平台代扣的个税**没到团长手里**，把申请额当「已提现」会让他看到一笔自己没收到的钱。⭐ `pendingCommissionFen` 必须再排除 `type='reversal'`（负额行），否则退款冲销会把「待入账」算小甚至算成负数（同 **#63**）。⚠️ **为什么不「顺手把这三列写起来」** —— 让每个写点（下单抵扣 / 退款回退 / D39 调账 / 提现冻结 …）都同步更新一遍，就是**第二份真相**：漏掉任一个，快照与真源就悄悄分叉，表现只是「某个页面显示旧数字」，**不报错、无告警**。⭐ **判据（可复用）**：① 看到「余额 / 金额 / 累计」这类字段，先 `grep` 它的**写入点**，**零写点 = 假真源**（#59 的同族，本条是它在**金额列**上的实例）；② 修它的正确姿势是「**不再读**」而不是「**多写一处**」—— 多写一处就把一份真相变成两份；③ 出参字段名与真源不一致时（`balance` vs `balanceFen`，`amount` vs `actual_amount`），先问「**这个出参到底该读哪张表**」，别顺着字段名猜。

70. **共享枚举写成小写、而全链路都是大写 —— 因为「全仓零消费点」而一直没炸**（M4-4 盘出 · **真缺陷，已修**）:`PayoutChannel` 的枚举值原写成小写（`'flex_manual'` / `'flex_api'` / `'wechat_transfer'`），而**真实链路上全是大写**：`ab_withdraw.payout_channel` 的**列默认值**、`BizConfigService.payoutChannel()` 的**缺省值**、e2e-m2 的**断言**，全是 `'FLEX_MANUAL'`。之所以一直没炸，是因为该枚举**全仓零 import（零消费点）** —— 没有任何一处代码用它做比较，也就没有任何机会暴露不一致。⚠️ 但「零消费点」不是安全，是**定时炸弹**：一旦有人照它写 `row.payoutChannel === PayoutChannel.FLEX_MANUAL`，比较会**恒为 false 且不报错** —— 表现是「已到账的提现单被判成非灵活用工通道」这类**不报错的错**，最难查。**修法**：枚举值改成**真实取值**（大写），并在文件头写明原因与登记号，让「照枚举写」与「照库写」指向同一个字符串。⭐ **判据（可复用）**：① 新增共享枚举（尤其**字符串枚举**）时，值必须**逐字取自「已经落库 / 已经在下发」的那一份**（DB 列默认值 / 迁移文件 / 既有断言），**不是**自己新造一套命名风格 —— 命名风格是审美，落库值是契约；② **「没人用的类型」比「用错的类型」更危险**：用错的地方至少跑一次就炸，没人用的那一份连**运行期**都碰不到它；本条正是 **#15**（共享包枚举值必须与 DB / 接口契约逐字一致）的**未被消费版本** —— #15 里 `LeaderLevel` 写 `regular` 而 DB 是 `formal`，后果是 `LEADER_LEVEL_META` 查表 miss、`label` 直接崩（**响了**）；而这个枚举连「查表 miss 崩一下」这条最后的报警都没有（**一声不吭**）。③ 同族 **#67**：**跨端 / 跨系统的字面量，写错了没人会报错 → 它就必须有一条机械对账**（本项目对落地页已做，枚举值的对账仍在「靠人读」阶段，属可改进项）。

71. **`enableShutdownHooks()` 没开 —— 所有 `onModuleDestroy()` 都是死代码，容器停不下来**（M5-0 盘出 · **真缺陷，已修**）:`main.ts` 里 `NestFactory.create()` 之后**从未调用** `app.enableShutdownHooks()` —— 而 Nest **默认不注册进程信号监听**。于是项目里已经写好的两处 `onModuleDestroy()`（队列 / 连接池收尾）**一次都没有执行过**。后果分三层：① 编排器 `docker stop` 发 SIGTERM 后应用**不等在途请求跑完**就被杀 → 正在执行的写事务半途中断（正是「支付回调处理到一半」这类场景）；② 队列消费者不 `close()` → BullMQ 里的 active 任务被丢在 Redis 上，要等 `stalledInterval` 超时才被重新认领（表现为「消息卡住一阵才重试」，而**没有任何地方报错**）；③ DB 连接池不 `destroy()`。⚠️ **为什么长期没暴露**：e2e 收尾走 `taskkill /T /F`（**强杀**），**从来没有走过优雅关闭这条路**；人在本地 Ctrl+C 时终端看起来「也退出了」→ 「写了 `onModuleDestroy`」被当成了「优雅关闭已实现」。**修法**：`main.ts` 在 `NestFactory.create()` 后立即 `app.enableShutdownHooks()`，并让 bootstrap 日志回显版本与环境（灰度 / 回滚的判据）。**验收**（M5-0）：Windows 上 `process.kill(pid,'SIGTERM')` 走 `TerminateProcess`、**handler 不跑**，不能用它验 —— 改为进程内 `process.emit('SIGTERM')` 等价触发，并用**跨进程子脚本**在钩子执行瞬间 `writeSync(1,…)` 落标记、父进程读（实测 5/5）。⚠️ 配套硬约束：容器必须用 **exec 形式 CMD**（`["node","dist/main.js"]`）—— `sh -c` 会让 PID 1 变成 sh，**信号到不了 node**，`enableShutdownHooks` 开了也白开（见 **#74** 第 ⑤ 条）。⭐ **判据（可复用）**：① 「写了生命周期钩子」≠「钩子会被调用」—— 钩子的**注册**与**触发**是两件事，和 **#66**（DI 是运行时行为）一样，**静态检查在原理上看不见**；② 凡声称「优雅关闭 / 优雅退出」的能力，验收必须**真发一次信号 + 断言钩子里的副作用发生了**（「进程退出了」不算证据 —— 强杀也会退出）；③ 同族 **#65 / #66 / #67**：**机制上的隐患** —— 都是「你以为它生效了，其实那条路径从未被走到」。

72. **迁移 glob 只匹配 `*.ts` —— 生产（`dist/*.js`）下「一条迁移都没找到」，而 TypeORM 只打印一行就继续**（M5-0 盘出 · **真缺陷，已修**）:`data-source.ts` 的 `migrations: [join(__dirname,'migrations/*.ts')]` 在 dev（ts-node 直跑 `src/`）工作正常，但生产跑的是 `dist/`、产物是 `*.js` → glob **命中 0 个文件**。⚠️ **最危险的是它的失败形态**：TypeORM 对「没找到迁移」**不报错**，只打印 `No migrations are found`，然后 `migration:run` **正常退出 0** —— 于是「迁移」这一步在部署流水线里显示 **✅ 成功**，而**所有 DDL 从未应用**。后续症状伪装成完全无关的样子：服务能起（表不存在要等到第一次查询才炸），或更糟 —— 炸在读某张新表时被当成「代码把列名写错了」。⚠️ 与 #67「跨端字面量写错没人报错」同族，但**证据面更硬**：它连一条错误日志都不产生，只有一个**退出码 0 的成功**。**修法**：glob 改 `*.{ts,js}` **双匹配**（dev 命中 `.ts`、prod 命中 `.js`），并补 `db:migrate:dist` / `db:migrate:dist:revert` 指向 `dist/database/data-source.js`。**验证**：`typeorm migration:show -d dist/database/data-source.js` 必须**列出** `[ ] Init1700000000000`（实测通过）—— 即「glob 真的命中了编译产物」。⭐ **判据（可复用）**：① 任何**按路径模式搜集文件**的机制（迁移 / 种子 / 路由自动注册 / 测试 glob），都要问「**在生产的产物目录里，这个模式还匹配得到吗**」—— dev 与 prod 的**目录形态不同**（`src/*.ts` vs `dist/*.js`），只写一种就必然有一种是坏的；② **「零命中」必须被当成失败**：这类机制要自己断言「找到了 N>0 个」，别指望框架替你喊（TypeORM 不喊）；③ 同族 **#59**（字段没写点）、**#69**（金额列假真源）—— 本条是「**机制没命中点**」，三者都是「你以为它在工作、它其实什么都没做」。

74. **骨架 Dockerfile 有五处「生产不可用」—— 而它看起来完全正常**（M5-0 盘出 · **真缺陷，已修**）:`apps/api-server/Dockerfile` 早已存在，是脚手架风格的骨架，五处硬伤：① `pnpm install --frozen-lockfile=false` —— 关掉锁文件冻结，构建**不可复现**（今天与明天装出不同依赖树，而镜像 tag 相同）；② **没有 `build:shared`** —— 本仓 `packages/*` 必须预构建，否则 `@abox/shared-*` 解析不到（**#4** TS6059 家族）；③ **以 root 运行**；④ **无 `tzdata` + 无 `TZ`** —— 容器 UTC；⭐ 本项目 `@Cron` 全带 `timeZone`、DB 连接用 `timezone:'+08:00'`，故**触发时刻是对的**，但容器内 `date` / 日志时间戳 / 任何未显式带时区的格式化都会偏移 8 小时；⑤ **无 `HEALTHCHECK`，且 CMD 是 shell 形式**（PID 1 变 sh → **吞 SIGTERM**，配合 **#71** 就是「优雅关闭彻底不可能」）。**修法**：多阶段重写 —— builder（`--frozen-lockfile` → `build:shared` → `api build`）；runner（`node:22-alpine` + tzdata + `ARG APP_VERSION` → `ENV`、**非 root 用户**、`HEALTHCHECK` 打 `/health`、`CMD ["node","--enable-source-maps","apps/api-server/dist/main.js"]` **exec 形式**）。⚠️ **另补一处静默失效**：compose 里传了 `build.args.APP_VERSION`，而 Dockerfile **没有 `ARG` 声明** → 版本注入**默认值而非构建版本**（探针回显永远 `.dev`，而灰度 / 回滚判据正要靠它）。⭐ **判据（可复用）**：① 骨架文件（Dockerfile / CI / compose）**必须逐条对照「生产要什么」审一遍**，别因为「它在那儿」就当成资产（与 **#73** 同源）；② `--frozen-lockfile=false` 出现在**生产** Dockerfile 里是明确信号：**这个文件不是为生产写的**；③ 交叉核对**参数的送达链**：调用方传了 A，被调用方**声明了吗**（`ARG` / `ENV`）？「传了但没声明」是一类**不报错的静默失效**（同 #67）。

75. **`/health` 只证「进程会应答」，却被当「可以接流量」用 —— 探针不分级，等于没有探针**（M5-0 盘出 · **真缺陷，已修**）:原 `GET /health` 返回 `{status:'ok',service:'abox-api',ts}`，只回答「进程还活着」，**完全不检依赖**；而它被同时赋予了两个**互相矛盾**的角色：① 三个 e2e 套件的 `waitHealthy()` 拿它判「服务已起」（此处只想知道进程活了，**不检依赖是对的**）；② 生产编排器拿它判「能不能接流量」（此处**必须检依赖**，否则 DB 断了它照样回 200、流量被继续打进来，每一个请求都失败）。⚠️ 这两个角色**必须拆成两个端点**，混用的两种后果都是灾难：若把 liveness 也做成「检 DB」，则 DB 一抖动 → 探针全红 → 编排器**重启所有容器** → 重启期间没人服务、DB 压力更大 → **重启风暴**（而 DB 挂了重启应用根本治不好）；若只保留「不检依赖」的版本当 readiness，则**摘不掉流量**。**修法**：新增 `GET /health/ready`（检 DB `SELECT 1` + 队列 3 个消费者是否齐备），失败时**显式** `BizException(SERVICE_UNAVAILABLE, …, HttpStatus.SERVICE_UNAVAILABLE, body)`；`GET /health` 出参**一字不改**（`waitHealthy` 依赖 `code===0`）。⚠️ 两处必须**显式**而不能靠默认：① `ErrorCode.SERVICE_UNAVAILABLE=90002` **不在** `HTTP_STATUS_OVERRIDE` 表里 —— 本项目业务失败默认 HTTP 200，**不显式传 503 就退化成 200**，而编排器只看状态码 → 「不可用」被判成健康，**探针形同虚设**；② 探针**免鉴权**（编排器要打，公网可达），故出参必须按「**会被人看见**」设计 —— 失败原因（DB 主机 / 端口 / 账号 / 连接串）**只进服务端日志**，HTTP 出参给固定文案「数据库探测失败（原因见服务端日志）」。⭐ 为什么 readiness **检「消费者齐不齐」而不是「Redis 通不通」**：Redis / DB 连通性在**启动期已 fail-closed 验过**（连不上即拒绝启动）；而「消费者有没有注册上」是**启动期验不到、失败后完全静默**的一类故障 —— 注册丢失时入队照常成功、`GET /admin/queue` 计数照常显示，但任务**永远无人消费**（同 **#68**「每一层都成功」）。⭐ **判据（可复用）**：① 探针**必须分级**：liveness =「要不要重启我」（**不检依赖**）、readiness =「要不要给我流量」（**检依赖**）—— 一条探针兼两用必然在某一侧错，而**错的那一侧会把故障放大**；② 探针出参是**契约**：`/health` 已被三个套件依赖，改它 = 全红，新增能力一律走新端点；③ **探针自身不能成为故障点**：`PROBE_TIMEOUT_MS`（1.5s —— 依赖「半死」时不挂住、不堆积请求）+ 探测结果走 `logger`；④ 免鉴权端点 = **公网可见端点**，出参按「会被人看见」设计（**#55**「别让系统看起来比实际更可靠」的**安全版**：这里是**别让它说得太多**）。

**门禁自带自证能力（本次最有价值的一处设计）**：每次运行**人为制造一个缺口**（从源A 深拷贝里删掉一列）**并确认能报出该列**，否则**自身失败** —— 「**恒绿的检查比没有检查更糟**」。⚠️ **这条自检当场抓出了自身一个 bug**：计数器原在循环外模块级累加，第二支迁移文件拿本文件条数去比累计值 → 误报「CREATE TABLE 源码 2 / 解析 27」。⑤ **不写成已验**：本批验的是「**迁移推演 ≡ 实体**」这件**结构事实**，**不是**「MySQL 上执行成功」这件**运行事实**（本机无 Docker / 无 MySQL）。
   ⭐ **补一条判据**：**「两支迁移合并推演才等于实体」这件事本身也要被门禁表达出来** —— 否则下一个人单看 `init` 就会得出「迁移只有 25 张表」的错误结论，然后再去「修」一次。检查器对**全部迁移文件**做推演，天然具备这个性质；**文档侧同步在 init 头注释与目录结构登记里写明**。

77. **`refundBalancePart` 是无条件 `+=`：退款的两道闸门都是「先读后写」，真并发下同一单会被退两次 —— 而且修好佣金那一半之后它更隐蔽了**（M5-6 收口阶段探针盘出 · **真缺口，未修：本地不可复现，挂账待真机 MySQL 验证**）:退款是全流程**唯一会让钱流出去**的地方，它有**两道各自独立**的闸门 —— ① 退款单闸门 `approveByAdmin` 里 `refund.status !== APPLYING`；② 订单闸门 `order.status !== REFUND_APPLYING`。两道都是 **`findOne` → 判定 → 写**，没有任何数据库级判定。P1-1 只把**佣金**那一半换成了原子占位（`UPDATE ab_commission SET status='cancelled' WHERE id=? AND status=?`，以 `affected` 判归属），而**余额**那一半的等价物仍然缺失：`ReversalService.refundBalancePart()` 是**无条件**的 `UPDATE ab_balance SET balance = balance + ?` + 写一条流水，它自己不会发现「这笔已经退过」。⚠️ **最反直觉的一点**：修掉 P1-1 **反而把这处缺口从「有报错」变成「没报错」** —— 改动前，第二次执行会撞 `uk_commission_order_type` 唯一索引**抛错**，于是整个事务回滚，**顺带**把多退的那次余额一起回滚（钱没多退，但靠的是错误发生的时机）；改动后原子占位让第二次执行**干净地早返回**，事务**正常提交** → 余额真的被退两次，**且从日志到状态位全都看不出异常**。即「一处并发缺陷被修好，另一处从『靠报错兜底』退化成『连报错都没有』」。**复现条件**：两次执行各自通过自己那道闸门（同一张单的两张 `applying` 退款单；或 D11 `forceRefund` 与 D41 `approveByAdmin` 并发）。**本地复现不了**：`better-sqlite3` 是**单连接同步**驱动，两次事务被**串行化**，第二次一定读到第一次已提交的状态 → 被订单闸门挡在 `40013`（探针 `tests/_probe-refund-concurrency.mjs` 实证：A=`201/0`、B=`200/40013`、余额只增一次）—— 故**必须有真机 MySQL 才能验证**，本地任何"绿"都不构成证据。**建议修法（下批）**：在 `settleRefundDb` 入口对**退款单行本身**做一次原子占位（`UPDATE ab_refund SET status='refunding' WHERE id=? AND status='approved'`，`affected===0` 即早返回），把「这张单的账务效果归我」交给数据库判定 —— **一处占位同时覆盖余额退回 / 佣金冲销 / 通道三段**，比逐段加守卫更不容易漏（逐段加守卫的失败模式正是本缺陷：修了佣金忘了余额）。⚠️ 注意 `approved` 是中间态，占位后事务回滚须让它回到 `approved`（同一事务内自然回滚，不要写成事务外）。

78. **`app.use()` 注册在 `await app.init()` **之后** = 中间件一次都不执行 —— 编译过、启动无告警、日志无异常**（M5-6 盘出 · **真缺陷，已修**）:限流中间件原先在 `main.ts` 写成 `await app.init(); app.use(createRateLimitMiddleware(app.get(KvService)))`。`NestApplication.init()` 的内部顺序是 **① `registerParserMiddleware()` → ② `registerModules()`（跑 `configure()`）→ ③ `registerRouter()`**；而 `app.use()` 只是把中间件**追加到 Express 栈尾**。于是两个位置**都不对**：**早于 `init()`** → 排在 body-parser **前** → `req.body` 恒为 `undefined` → **账号维度静默失效**（IP 维度照常工作，外部看不出异常）；**晚于 `init()`** → 排在**路由之后** → 请求已被控制器处理完毕，中间件**永远轮不到**（比前一种更隐蔽：连一条日志都不会有）。⚠️ 实测踩坑过程值得记：e2e 首次断言红时第一反应是「**账号维度**失效」（因为 IP 上限 10、理论上第 11 次才该红，而断言在第 6 次），直到写探针连打 12 次**全非 429** 才定位到「**根本没跑**」—— **断言失败的现象与真实原因隔了两层，靠读代码永远看不出来**。**正解**：`AppModule implements NestModule` + `configure(consumer: MiddlewareConsumer){ consumer.apply(createRateLimitMiddleware(this.kv)).forRoutes('*'); }` —— `configure()` 在 ② 被调用，天然夹在 body-parser 与路由之间，是唯一同时满足「拿得到请求体」与「挡得住请求」的注册点。⭐ 顺带两条实测结论：`forRoutes('*')` 经 `RouteInfoPathExtractor` 展开成 **`/api/v1$` + `/api/v1/*`**（**会**带上全局前缀，不必自己拼）；函数式中间件（非 `@Injectable` 类）能被 `consumer.apply()` 正确包装 —— `isMiddlewareClass()` 的判定要求函数名**首字母大写**且 `prototype.use` 是函数，普通小写函数名不会误判成 class。**判据**：探针 `tests/_probe-ratelimit.mjs`（IP 第 11 次 / 账号第 6 次各 429）+ `e2e-m3.mjs` §34。⭐ **配套纪律（限流阈值与自伤）**：e2e 主线套件一轮会打 **54 次 `POST /auth/admin-login`**（`finance` / `sanweiwu` 等同一账号各被复用近 10 次），**远高于**按「一栋办公楼共用 NAT 出口」定的生产阈值（IP 10/分 · 账号 5/分）→ 套件会被**自己的防护**打成 429。对策**不是**把阈值调大（那等于拿测试阈值换掉生产阈值），而是**把两件事分开**：e2e 启动器默认给子进程 `ABOX_RATE_LIMIT=off`，**限流自身的验收另起一台实例**（§34 真开）走真实 HTTP 断言。⚠️ 该开关照 `ABOX_SHIFT_TO_HOUR` 的范式：**`NODE_ENV=production` 时无条件忽略**（写 off 也无效，只打 WARN）。⚠️ **还要防自己被自己的默认值静默覆盖**：`lib/e2e-server.mjs` 的 `buildEnv()` 若把 `ABOX_RATE_LIMIT` 写成**不可覆盖的常量** `'off'`，则 `local-test.mjs` 按本文件既有习惯「先设 `process.env` 再起服务」的写法会**静默失效** → 故默认值必须让位：优先级 **`off` 默认 < `process.env.ABOX_RATE_LIMIT` < `extra`**（面向手工测试的 `local-test.mjs` 有意覆盖回 `on`，与生产一致）。

## 三、e2e 门禁纪律

### M5-10 批次三附带纪律：**L16 `mine.level` 与 L11/L14 `level` 同名不同义**（#94）

- **现象**（2026-09-18 M5-10 批次三实装 P16/P20 时实测）：`dev:1001` 是**首席**团长，
  `GET /leader/balance` 与 `GET /leader/profile` 都回 `level:'chief'` / `levelLabel:'首席'` / `rate:0.12`；
  **同一次会话**里 `GET /leader/level-rules` 却回
  `mine:{level:'trainee', monthOrders:7, invitedFormalCount:6, nextLevel:'formal', progress:0.23}`
  —— 于是 P16 大卡显示「首席 · 12%」，**同一屏**的体系表把「见习」标成「← 当前」；
  P20 更直接：头部「首席团长」+ 晋升进度条「见习 → 正式 23%」。
- ⭐ **判据：这不是代码 bug，是两个不同的东西共用了 `level` 这个名字。**
  - `ab_team_leader.level`（L11/L14 出参）= **实际生效等级**，由平台按晋级审计写入；
  - `LeaderLevelService.resolve()`（L15 `mine.level`）= **按本月业绩反推的「应处等级」**
    （`resolveLevel(monthOrders, invites)`，C2 双条件），它是**晋级审计的输入**，**根本不看当前等级**。
  - 故「首席但这个月只做了 7 单」必然同时命中 `chief` 与 `trainee` —— 两个值都"对"，只是语义不同。
    **同名不同义比"两个名字同一义"更危险**：编译器与类型系统都拦不住，肉眼看两个字段名一样还会以为是同源。
- ⭐ **端上纪律**：
  - **「我的等级 / 当前分佣比例」一律取 L11/L14**（`leader.level`，与 L15 的 `effectiveLevel` **同值**）；
  - **「下一级 / 进度」一律取 L15 出参**（服务端已把「谁比谁高」与门槛判定锁定为单一真相）；
  - ⚠️ **M5-11 前的老写法（端上自算）已废弃**：当时端上取 L15 `levels[]` 出参顺序排阶梯、
    取 `shared-types` 的 `LEADER_LEVEL_META` 当门槛再自己算进度 —— **等价于在每个读侧复刻一份推导**，
    正是本缺陷要根除的东西。现已收回服务端（见上方「契约层已收口」）；
  - **已达最高等级 → 进度恒 100%**（对齐原型 P20「已达首席（最高等级）」+ 满格）。
- ⚠️ **反向的坑：为什么长期没人发现** —— 原型 P16/P20 的演示数据是「首席 + 本月 186 单 + 推荐 5 名」
  （**业绩达标**），两个 `level` 恰好相等，**原型自己看不出这个矛盾**；换一套不达标的演示数据
  （如本仓种子 `dev:1001`）**立刻暴露**。⭐ **教训：原型演示数据"自洽"不代表口径自洽 ——
  演示数据必须至少有一组落在**边界/不达标**侧，否则版式对齐会掩盖语义缺陷。**
- ✅ **契约层已收口（2026-09-18 M5-11）**——两个建议**都做了**，且比原建议更彻底：
  `LeaderLevelService.progress()` 签名由 `(monthOrders, invitedFormalCount)` 改为
  **`(effectiveLevel, monthOrders, invitedFormalCount)`**，返回 `{ derivedLevel, nextLevel, progress }`
  —— L15 `mine` 出参里那个含义模糊的 `level` **删掉**，拆成两个自解释字段：
  · `effectiveLevel` = 实际生效等级（= L11/L14 的 `level`，**只作对照，不由本接口决定**）
  · `derivedLevel` = 按业绩反推的「应处等级」（原 `resolveLevel()` 输出，晋级审计的输入）
  · `nextLevel` / `progress` = **服务端按生效等级在阶梯上推导**（原来这段推导在每个读侧各写一份）。
  ⇒ **端上不再复刻阶梯与门槛**：`commission.vue` / `profile.vue` 删掉 `ladder` computed 与
  `LEADER_LEVEL_META` 引用，直接读 L15 出参；`e2e-m2.mjs` L16 断言同步改为
  `derivedLevel === 'trainee' && nextLevel === 'formal' && effectiveLevel === 'trainee'`
  并**显式断言旧字段 `mine.level === undefined`**（防止悄悄回退）；《接口规范》§4.6 补三字段语义表。
- ⚠️ **`effectiveLevel` 传入非法值**时 `progress()` 记 warn 并兜底 index 0 —— 否则 `indexOf` 返回 `-1`
  会被下游误读成「已达最高级」（又一个不报错的错）。
- **另注（留痕备查 · 非功能缺陷）**：种子把 `dev:1001` 的 `level` 设为 `chief` 而 `monthOrders` 仅 7，
  与 `resolveLevel()` 的判定不一致 —— 若晋级审计真机跑起来会把它降到见习。这是
  **演示数据与审计规则的口径差**，属"演示数据失真"，不是代码缺陷。

### M5-12 附带纪律（2026-09-18 · 运维与门禁类待办清理 · 零 DDL · 零错误码）

#### ① ⭐ 代理陷阱：`http_proxy` 会让「探测本机」变成「探测代理」（**与「服务真挂」同形**）

- **现象**：`ops-daily.sh` 首版探 `127.0.0.1:3000`，**恒报服务不可用**，拿回 `502 upstream connect failed`。
- **根因**：本机 shell 里 `http_proxy=http://127.0.0.1:1907` 已设，而 **curl 默认尊重它** ——
  「探测 `127.0.0.1`」的请求实际被送到了**代理**上，代理连不上上游就回 502。
- ⭐ **为什么这条比普通 bug 危险**：它**长得和「本机服务真的挂了」一模一样**（同样的退出码、同样的连接失败）。
  若走进日巡检，它会**每天**报「服务不可用」而服务一直是好的 —— 最后把人训练成**忽略告警**，
  那等于巡检不存在。
- **对策**：探测子进程显式清代理 ——
  `env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY -u all_proxy curl …`
- ⚠️ **刻意不改 `healthcheck.sh`**：它也可能被用来探**外网网关域名**（那里代理可能是需要的）。
  「探针不许过代理」是**本巡检**的判据，由 `ops-daily.sh` 自己承担。
- ⭐ **通用判据**：**任何「探本机端口」的脚本都要先假设环境里设了代理**；报错信息相同不代表根因相同。

#### ② ⭐ 监控脚本的判据，初版**三条全部恒过**（= 等于没检查）

> 「**恒红的检查等于没有检查**」是上一批的结论；本批补上它的孪生兄弟 ——
> **恒过的检查同样等于没有检查，而且更难发现**（恒红至少会被人看见并去修）。

| 判据 | 初版写法（恒过 / 无鉴别力） | 改后 | 为什么初版没用 |
| --- | --- | --- | --- |
| 磁盘可用 | 固定 MB 阈值 | **`df -Pk` 算百分比** `free*100/total` | 固定阈值在 **40G 盘恒过**、**100G 盘恒红** —— 两种都等于没检查 |
| 备份新鲜度 | `find -newermt "-26 hours"` | `find -mmin -N` + **`<1024` 字节判空导出** | `-newermt` 在 busybox 上行为不一致；且「文件在、时间新、**大小 0**」在年龄判据下完全看不出，**要到恢复那天才知道是空的** |
| 探针 | 直连 curl | **显式清代理**（见 ①） | 见 ① |

- ⭐ **另修一处「脚本自身的错」**：`install-cron.sh` 的 `cmd | grep -q` 配 `set -o pipefail`
  —— `grep -q` 命中即退出 → 上游收 **SIGPIPE** → 管道整体判失败 → **「装上了却报错」**。
  改成 `CUR="$(crontab -l 2>/dev/null || true)"` + `case` 匹配。
- ⭐ **标记行必须从模板 `grep` 取，不能硬编码**：硬编码会让「模板改了标记、安装器没改」表现为
  **旧块删不掉**；而重复的 cron **不会报错**，只表现为「磁盘莫名涨得快」。
- ⭐ **`strip_block` 用 awk 而非 `sed /r1/,/r2/d`**：范围删除在「有起无终」时会**删到文件尾**。
- ⭐ **渲染后若仍含未替换占位符即 `die`**：crontab 会**原样接受语法错误的命令行并每天定时执行它**，
  表现为「cron 什么都没干」而 `crontab -l` 完全正常。

#### ③ ⭐ 黑盒机械对账的两条硬约束（`e2e-m3` §36）

- ⭐⭐ **出厂口径必须在断言里写死复刻，刻意不 `import` 服务端常量**。
  否则就是**「拿实现验实现」**：实现改错了断言跟着一起错，**两边互相担保而恒绿**。
  只有**两条独立路径**（实现一份、断言一份）才能互相证伪。⭐ #49 的「结构性派生」只保证
  「同一份源」，**不保证「外部看到的就是它」**（写进 `ab_config` → 热重载 → 读回来，这条链
  从来没有人黑盒走通过）。
- ⭐⭐ **必须有「反证」组**：只验正例会漏掉「时刻表压根没读配置」这种情况。

  若有人把 `TIMELINE_CONFIG_KEYS` 扩到全部时刻，它会红。
- ⭐ **节首归一 + 节末复原并断言复原**：本节**真改过配置**，不还原会把「被改过的时刻表」留给
  后续节与重跑，症状是**「其它节偶发红」**（因果关系极难建立）。同 §34/§35 的夹具纪律。
- ⭐ 另两条**双向**断言值得复用：「偏离出厂值的任务集 **恰好等于** 被覆写的配置键对应任务集」
  （少了 = 配置没接上；**多了 = 存在第二个写入点**，那才是漂移的真形态）；
  「送达时刻在时刻表上**不留任何一行**」（映射表里显式 `null`，让「配了 5 项、只动了 4 项」有一个写在断言里的解释）。

# 附录 C · 单文件工具外壳与共享源件（2026-09-25 迁入）

> 本附录只讲 `_tmp/` 下**单文件工具**（P0 五系统 + P1 各件）自己的两类缺陷，与产品代码无关。

## C1. ⭐ `position: sticky` 侧栏高于视口可用高度时，**底部被钉住、够不到**

**症状**：侧栏（`.side`）比视口可用高度还高时，`sticky` 把它钉在 `top: 62px`，
**底部永远在视口外** —— 滚页面带不上来（滚到**整页最底**才脱离，用户不会那么干）。

**实测（1440 宽 · 末控件底 px）**：R1 928 · 驾驶舱 952 · S2 990 · **G1 1646** · **G2 1310** · **F3 1631**；
1440×1080 下 G1/G2/F3 **仍够不到**。

**修法**（共享 `_tmp/p0/_shared/shell.css` · 一处改六件受益）：
```css
.side { position: sticky; top: 62px;              /* 62px = .top 实际高度，改一处要一起改 */
        max-height: calc(100vh - 62px - var(--sp-3));
        overflow-y: auto; overscroll-behavior: contain; }
```
窄屏媒体查询里**必须解除**（`position: static; max-height: none; overflow-y: visible`）——
否则手机上出现一个 **1/4 屏高的小滚动盒**。

⚠️ **手写外壳各有各的副本**：E3 内容工厂的 `.fc-side` 不引 shell.css，需**单独对齐**
（它原本已有 `max-height + overflow:auto`，但少了 `- var(--sp-3)` 底部呼吸位 ⇒ 底边**贴死视口折线**，
实测 900→900）。**这类分叉没有编译期判据能拦** ⇒ 靠常驻探针 `_probe_side.mjs`。

**常驻探针**：`_tmp/qa-env/uisim/_probe_side.mjs`（7 件共享壳工具 × 2 视口 × 4 条 + 窄屏 + 2 件无侧栏确认 = **65/65**）。
两条**探针自身**的坑（改它时别退回去）：
- **必须先滚页面让 sticky 真的钉住，再量**；只滚侧栏自身 ⇒ 量到 hero 之下的自然位置 ⇒ **假红**。
- 自证口径别写死 `top == sticky`：**视口越高、整页可滚区间越小**，E3 在 1080 下滚动区间 = 0
  ⇒ 永远钉不到而它自然位置已完整可见 ⇒ 应判「**顶边不高于 sticky 线 ∨ 页面无可滚区间**」。

## C2. ⭐⭐ 共享源件「**被引用**但**没被追踪**」⇒ 改与不改都能过闸门（恒绿）

`build_lib.finish()` 与 `selftest_common.run()` 的新鲜度判据**只覆盖各自 `src/` 的源件**；
共享件要靠 `shared_files` 显式传。实测：六件引用 `shell.css` 的产物里，
**只有 G2 / F3 传了**（G2 还只传了 `income.js`）⇒ 改共享 `shell.css` 时
**R1 / G1 / M1 / S2 四件用新旧任何版本都能过闸门**。

**要查三处，少一处就是漏**：
1. `build.py` 的常量 `SHARED_FILES` + `B.finish(..., shared_files=…, shared_dir=…)`
2. `selftest.py` 的 `selftest_common.run(..., shared_files=…)`
3. ⚠️ **手写版 selftest**（R1 就是）—— 它不走 `selftest_common`，得**单独给 ④ 加分支**

**负控自证（必须做）**：往共享件追加一行注释 ⇒ ④ 须**真变红**（`源件 ['_shared/shell.css'] 改了但没重生成`）；
原件恢复后 **sha256 逐字一致**。没有这一步，「补上追踪」与「没补」在观感上完全一样。

## C3. 探针判据的**作用域**：断言「红的集合怎么变」，而不是「红了几项」

F3 探针 4 条红曾同时出现，根因只有一个：⑦/⑧ 两块（讲**别的功能**）把自己架在了
被 ⑥ 处置流**污染**的状态上 —— 那里有一处**合法红**（⑩：策略从 1 小时改回 48 小时后，
此前合法处置被按**新**策略判「提前 36 小时」），而 ⑦/⑧ 硬写 `bad === 1` / `probRows === 1`。

**修法（比原判据更强、且与前置状态无关）**：
```js
const badSet = () => …;                                   // 红的行号集合
const setDiff = (a, b) => ({ added: b.filter(i => !a.includes(i)),
                             removed: a.filter(i => !b.includes(i)) });
// 要求「新增**恰好**是目标那一项」且 removed 为空 ⇒ 误伤别的判据照样报红
```
筛选类判据同理：**在全量视图里数「真有标记的行数」**，再与筛选后的行数比
（在筛选之后再取数 = 同义反复/恒真）。

## C4. 补丁脚本的新坑：「旧串是否已消失」不能写 `old in text`

`count(old) - exp + count(new 里的 old)`。详见《工程纪律》**C18**。

## C5. ⭐⭐ 「环境故障伪装成测试失败」—— 本机 `stdio:'pipe'` 一律 EBUSY（2026-09-25 实测）

**症状**：`node scripts/gate.mjs seed` / `e2e:m3` / 几乎所有门禁 **`exit=null (2ms)` 且无任何输出**，
看起来像断言失败，实为**子进程根本没起来** ⇒ 属「恒红 / 恒绿同罪」之外的**第 4 种假象**。

**实测（逐项隔离；关沙箱后**同样** EBUSY ⇒ 与 WorkBuddy 沙箱无关，是机器级限制）**：

| 调用 | 结果 |
|---|---|
| `spawnSync(exe, ['-v'], {stdio:'pipe'})` | `status=null` · `EBUSY` |
| `spawnSync(exe, ['-v'], {encoding:'utf8'})`（**不写 stdio**）| `status=null` · `EBUSY` |
| `stdio:'inherit'` / `'ignore'` | `status=0` |
| `stdio:['ignore', fd_out, fd_err]`（**文件 fd**）| `status=0` 且**能取回输出** ✅ |

**对策** = `_tmp/gatepipe/pipefix.cjs` 垫片（位置 / 用法 / 继承规则见《工程纪律》**C19**）。

**两条判据（本轮各踩一次）**：
1. ⭐⭐ **「垫片生效了」≠「垫片覆盖了该调用形态」**：只认**显式** `stdio:'pipe'` 的垫片，
   遇到 `spawnSync(cmd, args, { encoding })`（**缺省 stdio 即 pipe**）会**原样透传** ⇒
   `scripts/check-gate-parity.mjs:81` 的 `loadTruth()`（跑在**孙进程**里）永远 EBUSY。
   症状最费解：**垫片已装载、自证 14/14 全绿，却仍红** ⇒ 必须为「缺省分支」**单列一段**自证。
2. ⚠️ **探针本身必须覆盖目标形态**：诊断探针若也写成 `{ encoding:'utf8' }`（不传 stdio），
   它就**根本没走到被改写的那条路**，却给出「`isPatched` 已是新函数、却仍 EBUSY」的**自相矛盾**结果
   ⇒ 那是**探针没覆盖目标形态**造的假象，**不是垫片的问题**。

## D8. ⭐⭐ 日期「双平移」：`+8h` 之后再读**本地分量**，16:00 后会把今天算成明天（2026-11-03 实测修掉）
- 错误写法（AI 编排 M/N/O/K 四处 + 4 个生成脚本都有）：
  ```js
  const bj = new Date(Date.now() + 8 * 3600 * 1000);
  `${bj.getFullYear()}-${bj.getMonth() + 1}-${bj.getDate()}`   // ← 本地分量
  ```
- 病因：容器 `TZ=Asia/Shanghai`，`getFullYear/getMonth/getDate` **本来就按东八区**取，
  再手动 `+8h` 就是**平移两次**。UTC 机器上碰巧对，东八区机器上 16:00 后直接跨日。
- 自证（已跑）：`2026-11-03T16:27+08:00` ⇒ 该写法得 **`2026-11-04`**；`toISOString().slice(0,10)` 得 `2026-11-03`。
- 后果不是报错，是**静默查空**：拿「明天」的日期去查统计/对账，接口返回空，报告照常生成，
  读起来像「今天没生意」。⚠️ 每天 09:00 的 cron 恰好不踩（+8h 后仍在当天）⇒ **只有下午手动触发才中招**，
  所以长期没被发现。
- 正确写法（三选一，全部 TZ 无关）：
  - 服务端：`todayBj(now)`（`common/utils/time.ts`，内部走 `toISOString`）、`bjYmdPlus(now, -1)`（走 UTC 分量）、`addDays(ymd, n)`；
  - 脚本：`new Date(Date.now() + 8 * 3600 * 1000).toISOString().slice(0, 10)`；
  - 通用：任何 `toLocaleDateString('sv-SE', { timeZone: 'Asia/Shanghai' })`。
- ⇒ 判据：**凡出现 `+ 8 * 3600 * 1000`，禁止配套使用 `getFullYear/getMonth/getDate/getHours`**；
  只允许配 `getUTC*` 或 `toISOString`。
- 附带一条：`.mjs` 的**模板字符串里写 markdown 反引号**（如 `` `#` ``）会截断字面量，
  `node --check` 报 `SyntaxError: Invalid or unexpected token` ⇒ prompt 里要提「# 号标题」就直接写文字。

## C11. 🔴 「展示上限截断」把唯一有信息量的那条挤掉（2026-11-04 生产实测）

- **形状**：一个 `string[]` 同时装了两类东西 —— ① **模板化文案**（每个对象一条，数量随对象数增长）；
  ② **唯一解释原因的那句话**（通常只有一条）。再对数组做 `slice(0, N)`，N 又刚好等于模板化文案的数量
  ⇒ 原因那条被**静默**挤掉，页面只剩「AI 未给」「无数据」这类空话。
- **本次实例**：开团草稿 `needsNewTemplate`。5 个楼群各生成一条「楼群 X 未排到套餐（AI 未给或全部越界）」，
  LLM 自报的那句「提案全是零食、模板全是正餐，建议新增零食模板」排在**第 6 位**，被服务层 `slice(0,5)` 切掉。
  表面：`ok:true, mode:'llm', rows:0`，看起来像「AI 没干活」；真相：AI 判断完全正确，是我们没让它说出口。
- **为什么难发现**：① `ok:true` + 空数组是**合法**返回，没有异常、没有报错日志；
  ② 脚本真调了模型（`mode:'llm'` 如实反映），所以连「退化成占位」的提示都不会出现；
  ③ 两条信息在同一个字段里，截断处不报错。
- **判据（可直接照抄成检查）**：
  > 凡是 `slice(0, N)` 作用在「混合来源的字符串数组」上，先问：**这 N 够不够装下最坏情况？**
  > 更稳的做法是**优先保留稀缺信息**（LLM/异常自报的那条），把可枚举的模板化文案放到末尾或另一个字段。
- **本次修法**：脚本侧改为「LLM 自报优先、覆盖度随后」+ 服务层上限 5→8 + **透传 `dropped`**
  （越界剔除原因此前被整段丢弃，导致「AI 给了但 ID 不在白名单」与「AI 没给」不可区分 —— 同一种静默）。
- **同类判据**：任何「把失败原因塞进给用户看的提示列表」的地方，都要保证**失败原因不会被截断**。
  失败的说明必须是**必现项**，不是「列表里的一条」。
- ⚠️ 查证手法（有效，可复用）：容器内 `docker exec -u root` 给脚本临时注入一行
  `writeFileSync('/tmp/dbg.json', JSON.stringify({input, rawDraft}))`，跑一次真实端点，
  读 `/tmp/dbg.json` 看**模型到底返回了什么**，然后 `cp` 备份还原。
  注意容器以非 root 用户跑、`/app` 非 root 不可写、`/tmp` 可能属别的用户 —— 备份放 `/app/scripts/.bak`。
  **别用 `docker exec node -e` 里的嵌套模板字符串**（`${}` 会被外层 shell/JS 提前展开）。

## C12. 🔴 新 DTO 类漏了 `export` ⇒ 企微侧退化成「你自己拼 JSON」，且无人报错（2026-11-04）

### 症状链（三层，只有第三层能看见）
1. 控制器里写 `class DecideInsightDto { ... }`（无 `export`），接口与后台页面**完全正常**；
2. `gen-wecom-catalog.mjs::parseDtoClass` 用 `/^export\s+class\s+(\w+)\b/` 找类
   ⇒ **找不到** ⇒ 该端点在目录里入参标成 `*`（只能收一整段 JSON）；
3. `check-wecom-param-hints.mjs` 把带 `*` 的端点**整段跳过**并打印 —— 于是它既不会被判红，
   也不会出现在「受检 N 个必填参数」里。**跳过不等于没问题。**

真人后果：同事在企微被问「还要填什么」时，机器人只能干巴巴回一句「你自己拼 JSON」，
而这类端点的参数往往正是最需要引导的（如 `status` 只能填 `open/adopted/dismissed`）。
**`tsc` / `eslint` / e2e / 后台页面，全都不会报。**

### 判据与修法
- 新写后台 DTO：**`export class XxxDto`**，一个字都不能省。
- 自检：`node scripts/gen-wecom-catalog.mjs` 输出里看 `入参未解析 N`——
  **这个数涨了就是新端点没解析出字段**（本批从 4 降到 1）。
- 另一种成因是 `@Body() dto: { a?: string }` 内联对象类型（`op-blocklist` 一处）。
  它两个字段全可选、无必填参数可引导 ⇒ 判定可接受，**不要为它硬造 DTO**。
  两种成因症状一样，故 `check-wecom-param-hints.mjs` 的跳过提示已改成同时列出两者 + 分辨方法。

## C13. 🔴 自证取样撞上「被跳过的对象」⇒ 自证恒假红，且报错指向完全错误（2026-11-04）

`check-wecom-param-hints.mjs` 的自证要证明「抹掉 hint 会报」。它取
`findFirstRequired()` = 目录里**第一个**带中文 hint 的必填参数。

而 `scan()` 会**整段跳过**入参含 `*` 的端点。两者判据不一致时：
取样命中了一个「会被跳过」的端点 ⇒ 抹掉 hint 后 scan 直接跳过 ⇒ 不报 ⇒
输出「把 hint 抹掉竟然没报 —— 这条检查抓不到『问得看不懂』」。

**这个报错是骗人的**：检查器本身是好的，坏的是取样。追错方向会去改判据、把好判据改坏。

- 修法：`findFirstRequired()` 里加**与 `scan()` 逐字相同**的跳过条件
  （`params.some(p => p.name === '*')`）。两份判据必须同源，改一处必须改另一处。
- ⭐ 通用法则：**凡「注入缺陷做自证」的检查器，取样必须先套用与主扫描一致的过滤**。
  否则样本落在扫描范围外，自证证明的是一件没发生的事。
- 补充：本批是 `C12` 的连带效应触发的（新端点带 `*` 且恰好排第一）——
  **一个真缺陷常会连带暴露一个检查器的假红**，两个都要修，别只修让人眼红的那个。

## C14. 🔴 admin-web 里硬编码色值会被 `design:spec` 拦（2026-11-04）

SFC 的 `<style>` 若写成 `<style scoped>`（无 `lang="scss"`），就用不了 `tokens.scss` 的变量，
很自然会写出 `#909399` / `#faf8f4` 这类值 —— 然后 `design:spec` 报 `命中=4` 转红。

- 写 `<style lang="scss" scoped>`；`vite.config.ts` 已 `additionalData: '@use "@/styles/tokens.scss" as *;'`
  自动注入，变量直接可用、无需 import。
- 常用映射：`#909399 次级文字 → $c-text-weak`；`#f6f0e5 米色底 → $c-bg`；
  `卡片面 → $c-surface-2`；`边框 → $c-border`；字号 `$fs-caption/$fs-micro`；间距 `$space-1..5`。
- `font-family: inherit` 也要换成 `$font-family-base`（`inherit` 在 `<pre>` 上会掉到浏览器默认等宽）。
