### 关键设计：`cancel_source` 才是核心字段，不是 `cancel_reason`
三条取消路径过去都只置 `cancelled`，看不出谁取消的。**「忘付款被系统清掉」量通常更大**，
混进用户主动放弃的统计会把流失结论带偏 ⇒ 统计**必须先按 `cancel_source` 分层**。
`cancel_reason` 各域保留原语义（团长侧沿用既有 `RefundReasonType`，**不强行合并** ——
那是给财务/供应商追责用的，语义更重）。

### 实现（第 5 支迁移 · 打破「零 DDL」，理由要能 GROUP BY 就必须加列）
- `ab_order` 加三列：`cancel_reason`(varchar32) / `cancel_note`(varchar128) / `cancel_source`(varchar16)，全 nullable
- 迁移 `1700000000004-cancel-reason.ts`：⚠️ MySQL `ALTER TABLE ADD COLUMN` **不支持 IF NOT EXISTS**，
  故先查 `information_schema.COLUMNS` 判存（服务器 `git archive` 覆盖后重跑是常态，必须可重入）
- 三处写入：用户自助 `source=user` · 截单跑批 `source=system + reason=timeout_unpaid` · 团长代退 `source=leader`
- ⭐ **团长代退是「申请」路径**：申请时写 source、`reasonType` 进 cancel_reason；
  **驳回时必须三列一起清**（`refund.service` reject 处）—— 否则订单回到 paid 却带着「已取消」标记
- 前端：`order-cancel.vue` 加选项 chip（再点一次取消选择）+ 选「其他」出输入框；
  按钮文案随状态变（未选=「不说明，直接取消」）

### ⚠️⚠️ 同轮追加：推翻我自己上一节写下的两条结论（用户追问「A 是不是得时刻盯着」引出）
1. ❌ 旧结论「第三方 SaaS 客服因需公网 HTTPS 而**全部排除**」—— **错**。
   **回调 URL 由第三方提供，我们只是授权小程序，不需要我们自己的服务器** ⇒ 技术上可行，
   代价是付费 + AppID/AppSecret 授权第三方（数据出域）+ 多一个供应商 ⇒ 改列为 **C 方案（保底）**。
2. ❌ 旧结论默认「A 打底再换 B」—— **低估了 A 的短板**。A 的「服务通知」提醒**不可靠**
   （开放社区长期反馈：收不到/不弹/网页端要刷新/需手动在线/绑多小程序只推一个）
   ⇒ **A 的真实成本是人力盯梢，且盯了还可能漏** ⇒ 推荐改为**直接办 B**，A 只能当过渡。

**教训（复用）**：出技术方案时，「客服能不能及时收到提醒」这类**人力侧可用性**必须单独列为选型维度，
不能只看「技术上能不能接通」—— 用户一句「是不是得时刻留意」就问出了我方案里最大的漏洞。
另一条：**「我们没有 X ⇒ 方案不可行」这类推论要先想清楚「X 由谁提供」**，第三方方案往往自带 X。
