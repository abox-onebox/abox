### 从源件读出的真实部署事实（手册据此写，勿凭印象改）

- **`deploy.sh` 七阶段**：1/7 预检 → 2/7 备份 → 3/7 起依赖(mysql/redis) → 4/7 构建(api+admin)
  → 5/7 迁移 → 6/7 起应用 → 7/7 健康验证(轮询 `/api/v1/health/ready`，默认 90s) → 写 `.deploy-state`。
  ⚠️ 2/7 首次部署报「备份失败」**属正常**（库还是空的），脚本 warn 后继续。
- **迁移命令**（真实形态）：`compose run --rm --no-deps --entrypoint sh api -c
  'node node_modules/typeorm/cli.js migration:run -d apps/api-server/dist/database/data-source.js'`
- **对外端口只有一个**：`${ADMIN_PORT:-8080}:80`；mysql/redis **不映射宿主端口**。
  ⇒ **8080 只给宿主机 nginx 内部反代，绝不开公网**（手册列为第 2 步硬禁忌）。
- **compose 硬失败项只有一个**：`MYSQL_ROOT_PASSWORD`（`${VAR:?msg}` 语法）；
  其余多为 `${VAR:-默认}` 有兜底 ⇒ 「能启动」≠「配对了」。
- **`.env.prod` 三项必改**（`.env.example` 顶部明文警告）：
  ① `PROVIDER_MODE` 必须**显式写 real** —— 留 `mock` 的后果是**任意 code 免密登录任意身份
  + 支付自动置为已支付**，且服务照常起、零报错；`main.ts` 的 `REQUIRED_IN_PROD` 只防**漏配**、
  **防不了"配成 mock"**。② `JWT_SECRET` 否则任何人可自签超管 token。③ 两个 MySQL 密码。
- **宿主机 nginx 两个必须保留的细节**（容器内的 nginx 已配好，宿主机那层容易漏）：
  `client_max_body_size 20m`（否则传图 413）+ `proxy_request_buffering off`
  （微信支付 V3 回调要**原始报文**验签，缓冲会导致"支付成功但验签不过"）。
- **api 容器刻意没有 healthcheck**（避免依赖故障引发重启风暴）⇒ **不能用"是否 healthy"判 API 好坏**，
  只能看 `/health/ready`；`ps` 里它只显示 `Up` 是正常的。
- **4C8G 不可省**：要在机上**构建两个 Node 镜像**，构建峰值吃内存；OOM 的表现是
  `Killed` 且**无其它报错**，极难归因 ⇒ 手册加了 2G swap 一步。
- Dockerfile 带 `--enable-source-maps` ⇒ 线上堆栈可直接对应 **TS 行号**（排查时别只看 dist）。
  `COPY .npmrc` 必须在 `pnpm install` 之前（`shamefully-hoist` 决定 `node_modules/typeorm` 是否存在，
  而迁移命令正依赖该路径）。
