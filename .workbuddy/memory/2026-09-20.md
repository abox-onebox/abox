### ① 身份切换：症状成因已精确定位（三条真缺陷 + 两条非缺陷）

**用户观察到的现象**：「我的」仍显示**李明**，但「跟随团长」变成**新注册团长的名字**。

**成因链（全部已核实）**：

1. **昵称恒为「李明」是因为登录的确实就是李明** —— 不是缓存过期：
   `env.ts:12` 前端登录码**硬编码 `dev:1001`**；`mock-wx-mini.provider.ts:52-53` `/^dev:(.+)$/`
   → `mock_openid_1001` ⇒ **恒定 user#1001**；`auth.service.ts:71-85` **只在建号分支写 nickname**
   ⇒ 昵称永远「李明」。⚠️ 我一开始误判为"mock 固定映射"，**实际 provider 是解析 code 后缀的**（支持 `dev:1002`），
   是**前端 env 写死**导致换不了人。
2. **用户所谓的"重新注册其他用户名"= 团长申请表单里的姓名**（仓库**无注册页/注册接口**，
   `ab_user` 写点仅 `auth.service.ts:72` 与种子）⇒ 只写 `ab_leader.real_name`（`team-leader.service.ts:112,121-123`），**不碰 `ab_user.nickname`**。
3. ⭐ **「跟随团长」显示新名字的直接来源 = `auth.service.ts:202-207,224` 的"自我回退"**：
   `effectiveLeaderId = user.teamLeaderId ?? leader?.id ?? null` —— 退出团长只置 `team_leader_id=null`
   （`team-leader.service.ts:312`），**`ab_leader` 记录仍存在（status=2 停职）** ⇒ 回退到**自己** ⇒
   `leaderName = 自己 leader.realName` = 申请时新填的名字。
   ⚠️ 注释(`:194-201`)说明该回退是为让团长本人在 P8 不显示"未绑定办公楼"，但 **`buildingId` 已有独立回退(`:209`)**，
   `leaderName` 跟着回退 ⇒ 语义错误：**停职团长不该"跟随自己"**。

## 20:10 小程序首页三条需求 · 只读排查（未改代码）

用户提三条：① 首页最下面的「往日这盒」暂时不要，别让首页太复杂；② 每道菜的「来自：X」应该可点、点了能跳第三方外卖（类似供应商页点商家）；③ 无团长用户下单时是否有页面提醒必须先注册/选择团长；没点下单前能否在首页选团长。

### 查证结论（全部读代码确认，非推测）

1. **「往日这盒」= U2 `/home/history`（M01-02）**，**不在原型 P1 里**（原型无「往日」字样），是 M5-10 明确「保留在页尾」的**原型外既有验收点**；端上**唯一消费点**就是 `pages/index/index.vue`（另 `api/meal.ts` 一个薄封装）⇒ 删 UI 后 **U2 变成零消费点端点**，需决定「保留接口 / 一并退役」。注意 **P6 订单列表已覆盖「我下过什么」**，所以页面层面不损失能力。同时「往日这盒」**没有出现在《内部测试操作清单》**里，删除不影响测试步骤。

2. **菜品可点需要后端补数据**：U1 出参 `dishes[]` 目前**只有 `supplierName`**（`meal.service.ts:266`），**没有 supplierId、没有外卖链接**。P38 的跳转逻辑（`wx.navigateToMiniProgram` + appId 白名单降级为复制店名）**已实装在 `pages/traceability/traceability.vue` 内**（`openLink` 一带）—— 但它是**页面内私有实现**，首页要用就必须**抽成共享 util/组件**，否则立刻变成「同一件事两份表述」。U5 出参的 `supplier` 视图也**没有 id**（只有 name/qualifications/recommended/takeoutLinks）⇒ 想「从首页定位到某一家」要么补 id，要么按 name 匹配（有同名风险）。
   ⚠️ **一期 appId 白名单未取得** ⇒ 「点击跳第三方」真机**做不到真跳**，只能「能跳则跳、不能跳则复制店名 + 引导」——这条必须在设计阶段就说清，否则又是「假装能跳」。

3. **⭐ 最重要：用户的前提不成立**。`canOrder` **只看套餐状态与下单时间窗**，与「有没有团长」**无关**；下单侧 `OrderService.resolveLeader` 有**两级回落**：① 已绑定且**在职** → 用他；② 否则取**本办公楼的「第一位在营团长」**（`order: {id:'ASC'}`）；③ 两者都没有才抛 **30007**。
   ⇒ 所以「普通用户不走邀请也能下单」在**大多数情况是成立的**，只是**佣金静默归给了该楼第一位在营团长**，而**用户看不到这个归属**。
   ⇒ **P3 下单页没有任何团长闸门**，取餐信息卡还写着 `daily.leader?.name ?? '本楼团长'` —— **无团长时显示「本楼团长」，看起来像有团长**（误导性兜底）。
   ⇒ 真正需要「提醒选团长」的场景比用户想的小得多：**仅「该办公楼一个在营团长都没有」**时才必须拦。

4. ⭐ **顺带查出一处真缺陷（已记入 ref/缺陷与陷阱 ⑫）**：U1 的第一级**不校验在职**，U6 校验。
   ⇒ 团长被停职后，**首页显示的「跟随团长」是 A，下单佣金实际记给 B**，两边都不报错（错位的是钱）。

### 建议方向（待需求方裁定后落码）

- ② 推荐**原地开弹层**（复用 P38 的平台弹层，抽成共享组件），**不建议首页一键跳第三方**：首页是下单页，一键把人送出去（且一期只能复制店名）会直接损失下单转化。
- ③ 推荐**明示归属**（首页写清「这单佣金归 X」）而不是**强制先绑定**：因为系统当前是「自动挂靠」语义，改成强制会让大量本可下单的用户被拦住；是否改属**业务口径**问题，不是 UI 细节。
