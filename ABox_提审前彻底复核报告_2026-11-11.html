结论先行：备案与代码质量都没问题，但有 3 项会让审核员实测失败
技术 11-11 出的《提审前自检清单》结论是「全部就绪，仅等隐私指引审核」。我把每个环节按审核员真机视角重跑了一遍， 发现清单里一处自相矛盾的假设：A3 写「正式包 demoMode:!1（false）」，但「审核体验路径」写的是 「打开即自动登录 dev:1001 首席团长」「点确认支付约 1 秒自动成功、不产生真实扣款」—— 后者只可能在 demoMode=true 的 development 包里发生。
按当前磁盘上的 production 包实测，审核员会遇到：全新无楼宇用户 → 明日未开团 → 看不到商品；点支付 → 假签名参数调起收银台失败。 另外，正在审核的《用户隐私保护指引》漏声明了「读取你的剪切板」，且补充文档写了与代码相反的陈述。

一、P0-1　隐私指引漏声明「读取你的剪切板」（正对着你正在审的那份）

证据内容
官方清单微信《小程序用户隐私保护指引内容介绍》原文：「读取你的剪切板」对应接口 wx.setClipboardData、wx.getClipboardData（写入也算）。官方社区运营专员答复： 只使用 setClipboardData 仍需声明，隐私弹窗为微信强制要求，无法规避；未声明则接口被禁用。
端上实扫带自证的扫描器扫 src/ 79 个文件：唯一需声明项 = 读取你的剪切板，10 处 uni.setClipboardData。分布在：订单详情、账号注销、团长订单导出、团长分享（4 处）、推荐页、客服页、团长邀请等。
构建产物产物里是 e.index.setClipboardData（uni 代理）10 处， 字面 wx.setClipboardData = 0。这正是漏判原因：按字面串扫确实「无调用」， 但 uni 在 mp-weixin 平台运行时映射到 wx，隐私管控是接口级运行时拦截，不是只扫字面量。
技术底稿《填报底稿》§99：「位置 / 地址 / 发票 / 麦克风 / 摄像头 / 蓝牙 / 传感器 / 剪切板等｜保持未选，全包无调用」；《补充文档》txt 第 79 行：「本小程序待提审版本的代码中， 未调用以下微信隐私接口或组件：…剪切板」。⇒ 与代码事实相反。

后果有两层：① 指引未声明 ⇒ 10 处复制功能（订单号、邀请码、分享链接、客服微信号、订单导出） 在真机上会被隐私管控拦掉；② 补充文档里「未调用剪切板」属与事实不符的陈述，审核员核实即是硬伤。
修法（成本很低）：在「开发者处理的信息」补勾「读取你的剪切板」，用途写 「用于复制订单号、邀请码、分享链接及客服微信号等文本」；同步把补充文档 txt 第 79 行的「剪切板」删掉； 端内《隐私政策》v1.1 补一句剪贴板说明。多声明一项不会导致驳回，少声明会让接口失效，宁可多勾。

操作窗口（结合你当前状态）：入口1 现网指引正「审核中、不可修改」—— 不要重复提交。等审核结果出来后点「去更新」补这一项并重新提交；或按官方运营口径， 直接在入口2「版本管理 → 提交代码审核 → 信息填写页」按平台识别结果补齐（入口2 的修改不影响现网版）。 官方明确：提审被隐私拦截时必须在入口2 改，回入口1 改无效。同时提审页别勾「未采集隐私」。

顺带肯定技术做对的三点（我已回官方文档核实）：wx.login 不属该指引限制的隐私接口； open-type="contact" 客服按钮不在清单；2023-10-17 后 __usePrivacyCheck__ 已废弃、隐私检查默认强制， 且未注册自管回调时微信会自动弹官方隐私框 ⇒ 端上不写隐私授权代码反而是对的，不要为此补代码。

二、P0-2　支付模式冲突：production 包 + 线上 mock = 点支付必失败

环节实测
线上配置.env.prod：NODE_ENV=production、PROVIDER_MODE=mock； 只配了 WX_MINI_APPID / WX_MINI_SECRET，没有商户号
正式包constants/env.js → demoMode:!1（false = production 构建）； apiBaseUrl 已是 https://api.xunlizhinian.cn/api/v1
支付分支use-wechat-pay.ts：demoMode 为 false ⇒ await requestPayment(prepay)（真实微信收银台）；mockPaid() 兜底只在 true 时走
服务端参数mock-wx-pay.provider.ts 头注原文：「createPrepay 返回假 prepay_id 与假 payParams （小程序端会调起失败，属预期）」
结果假参数调真实收银台 ⇒ requestPayment reject ⇒ 直接抛出， 连 pollResult() 都不会执行。即便 800ms 后 mock 自动把订单置为 paid，端上仍显示支付失败。

两条路都不通，必须由你和技术拍板，不能维持现状：

  • 提交 production 包（当前磁盘这个） → 审核员点「确认支付」报错，大概率驳回。
  • 改提交 development 包（demoMode=true） → 走 mockPaid 自动「支付成功」，不弹收银台、 不扣钱。审核员可能判定支付功能不真实；更严重的是发布后用户付款不实际扣款。
  • 提审前切 PROVIDER_MODE=real → 需配齐商户号与证书，且 dev: 账号全部失效； 但审核员用自己微信可以自助登录（见下一节），并需准备真实支付闭环。

技术《提审说明》§3.3 定的顺序是「① 提审（MOCK）→ ② 审核通过+发布 → ③ 才切 real」，理由是切 real 后 dev: 账号失效、审核员进不去。这个顾虑成立，但它默认了「提审用的是体验版」—— 而提交审核上传的是开发版代码包，不是体验版。请先确认「本次到底上传哪个目录、用什么 mode 构建」， 再把 A3 与体验路径改成一致。
