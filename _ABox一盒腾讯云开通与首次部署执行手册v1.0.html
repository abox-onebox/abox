01结论先行：腾讯云选得对不对

选得对，但别指望它帮你省时间

腾讯云合适。但决定你什么时候能上线的，不是云厂商，是备案接入和资质。

三家境内云都能过微信审核。纠结"选哪家"最多影响一两天的操作手感，不影响上线日期。

真实好处只有三条

① 微信、微信支付、腾讯云备案、COS、CDN、SSL 同账号体系，少一轮跨厂商资料往返。

② 轻量应用服务器便宜且够用。

③ 备案主体与小程序主体一致性核验更顺。

最该担心的是这条

ICP 备案与接入商绑定。你的域名如果原备案不在腾讯云，换过来必须办接入备案（1–20 工作日）；不办，域名解析到腾讯云服务器会被阻断访问。

好消息 项目侧的部署基座已经是完整的。仓库里已有两个 Dockerfile、docker-compose.prod.yml、nginx 站点配置、五支运维脚本、cron 声明模板、两级探针、回滚与备份恢复流程。 这一轮要做的不是"开发部署能力"，而是"把它第一次真正跑起来"。
边界 本手册不重复《部署运维手册》的运维内容（探针语义、禁发窗口、应急预案、日巡检）。它只管两件事：云厂商侧怎么开通、第一次上机怎么验证。

02三个坑（只有查了才敢说的）

坑 1 · 备案接入商绑定 —— 最容易卡住，也最容易没人想到

备案信息必须与实际接入服务商关联。这是规则原文的意思：主体在某家接入商完成备案，只表示"可以在该接入商的服务范围内开展网站内容服务"。

你域名的现状会发生什么要做什么
原备案接入商 = 腾讯云 直接可用；若是新域名需走"新增服务" 新增服务即可
原备案接入商 ≠ 腾讯云 必须办接入备案。腾讯云初审 → 管局终审，1–20 工作日；审核期间网站需保持可访问供核验 接入备案
原备案已失效（取消接入后长期无新接入商） 会被管局注销，需重新备案 重新备案

⚠️ 《账号资源与密钥清单 v1.0》里 R4 只记了「域名（已备案）✅」，没记接入商是谁、域名是什么。这是本轮要补的第一个空。

坑 2 · 轻量应用服务器要"够格"才能用于备案

要求项具体条件
地域必须中国境内节点。中国香港地区及境外节点不能用于备案
计费模式仅包年包月。按量计费、试用期、竞价实例均不支持
购买时长≥ 3 个月（含续费），且备案期间剩余有效期 ≥ 1 个月
公网 IP需绑定腾讯云中国境内公网 IP，且带宽不能为 0；不支持绑 EIP 备案
备案额度企业账号：同一轻量实例最多备案 5 个网站/APP，另可生成 2 个备案授权码
账号实名生成备案授权码要求账号实名类型为企业。个人实名账号不能生成授权码

⇒ 一句话落地：买的时候选「境内地域 + 包年包月 ≥ 3 个月 + 带公网带宽」。为了省几百块买按量计费，后面要返工。

坑 3 · HTTPS 不在编排文件里，要你在宿主机补一层

docker-compose.prod.yml 里 admin 只对外开 HTTP 8080（ADMIN_PORT），注释写着"上线时前置 HTTPS"。项目文档给了两条路：宿主机 nginx/Caddy 反代，或云负载均衡。

只能选一条 结合遗留风险 R10，实际只有"宿主机 nginx + 证书"这一条路可走。 走云负载均衡会引入"第二个 API 实例"的形态 —— 而 currentTimeline() 是进程级单例，多实例会出现「A 实例已按新截单时刻拒单、B 实例还按旧时刻放行」，两边都不报错，只表现为"同一分钟下单，一台过一台不过"。在改成 Redis 发布订阅广播（并写出黑盒断言）之前，多实例属于未验证形态。

3.2 明确不买的（每条都写明理由，防止后面有人"顺手加购"）

不买理由
云数据库 MySQL / 腾讯云 Redis 生产编排已自托管 mysql:8.0 + redis:7-alpine，且依赖不暴露宿主端口。27 张表 / 单楼 500 单/日的体量下自托管完全够。一年省几千，且少一层网络延迟与白名单配置
负载均衡 CLB R10：一期只允许一个 API 实例。见 §2 坑 3
K8s / TKE 同上；且单楼灰度的体量用不上编排能力
对象存储 COS 可以推迟。STORAGE_DRIVER=local 已支持，nginx 已配好 /static/ 反代。等图片量起来再切 COS —— 四驱动开关意味着代码零改动

#动作判据 / 命令
A1 确认腾讯云账号实名主体 = 北京巡礼之年科技有限公司（企业实名） 控制台 → 账号信息 → 实名认证类型显示"企业"。⚠️ 个人实名账号不能生成备案授权码，也不能改回个人
A2 购买轻量应用服务器：境内 / 包年包月 ≥ 3 个月 / 4C8G / 带公网带宽 到期时间 ≥ 3 个月之后；计费模式显示"包年包月"
A3 系统镜像选 Ubuntu 22.04 LTS 纯系统镜像 ⚠️ 不要选 WordPress / 宝塔 / Docker 应用镜像 —— 与项目脚本假设不符，且会引入不受控的默认配置
A4 防火墙只放行：22（限来源 IP）/ 80 / 443 ⚠️ 不要放行 3306 / 6379 / 3000 / 8080。与《账号资源与密钥清单》§5.2 一致
A5 SSH 密钥登录，禁用密码登录 ssh -i <key> root@<IP>
A6 安装 Docker 20.10+ 与 Compose V2 docker compose version 有输出（注意是 docker compose 不是 docker-compose）
A7 固定服务器时区为 Asia/Shanghai timedatectl → Time zone: Asia/Shanghai (CST, +0800)
A8 查原域名备案的"接入商"是谁 工信部备案系统 / 原服务商控制台 → 拿到：备案号、接入商名称、备案状态
A9 若接入商 ≠ 腾讯云 → 提交接入备案 拿到受理号。这一步 1–20 工作日，是唯一可能拖长关键路径的动作
A7 为什么是硬要求 业务口径是 Asia/Shanghai；deploy/cron/abox-ops.cron 用宿主机本地时区，而且项目刻意不设 CRON_TZ（设了就成第三个时区来源）。宿主机时区不对 ⇒ 备份与巡检按错误时刻执行， 而这是不报错的：容器里的 @Cron(timeZone) 能兜住跑批触发时刻，但 Docker 之外的 cron 与日志时间戳兜不住。

05阶段 B · 首次部署（1 天，本质是"兑现 R1 / R2 / R11"）

先定性 把这一次当成"联调"，不是一次例行发布。两个 Dockerfile、docker-compose.prod.yml、nginx.conf、五支运维脚本、cron 模板 —— 从未在真机执行过（R1 / R11）；生产库从未执行过迁移（R2）。 第一次跑挂掉是预期内的；怕的是"看起来跑通了"而 DDL 从未应用。
#动作命令 / 判据
B1 宿主机装 nginx + certbot nginx -v · certbot --version
B2 签发证书 certbot --nginx -d api.<域名>
B3 宿主机 nginx 反代：443 → 127.0.0.1:8080；80 全量跳 443 curl -I https://api.<域名>/ → 返回 HTTP 状态码（而不是超时）
B4 拉代码，cp .env.example .env.prod，按《部署运维手册》§4.2 逐项填 启动不应报「缺少 MYSQL_ROOT_PASSWORD」（compose 用 ${VAR:?}，缺值即拒绝启动）
B5 只构建镜像 ./scripts/deploy.sh --build-only ← 这一步最先可能失败（pnpm workspace + alpine 依赖解析）
B6 正式部署（脚本自动：预检 → 备份 → 起依赖 → 构建 → 迁移 → up → 健康验证） ./scripts/deploy.sh
B7 核对两支迁移都 applied npx typeorm migration:show -d dist/database/data-source.js
→ Init1700000000000 和 ParityFix1700000000001 都必须是 [X]
B8 探针（readiness） ./scripts/healthcheck.sh → [结果] 通过；出参里 queue.consumers = 3/3
B9 备份可用 ./scripts/backup-db.sh → 产出非空 .gz（空导出会给出"备份成功"的假象）
B10 回滚演练（M5 验收标准 #4：10 分钟内可回退） 发一版 → ./scripts/rollback.sh → 再发回来。⚠️ 永远不要在生产机执行 docker image prune -a —— 那会把回滚能力一起删掉
B11 cron：先 --dry-run → 手工跑一次 ops-daily.sh 核对输出 → 最后才装 ./scripts/install-cron.sh --dry-run → ./scripts/ops-daily.sh → ./scripts/install-cron.sh → --list 有 2 条
B12 后台可访问 https://api.<域名>/ 打开运营后台登录页

B7 为什么单独拎出来讲

这是本项目里最典型的"显示成功但什么都没发生"一类缺陷，有两个具体陷阱：

  1. 迁移 glob 必须双匹配 *.{ts,js}。只写 *.ts：dev 用 ts-node 直跑 src/ 能命中，生产 dist/*.js 下零命中。
  2. TypeORM 对"没找到迁移"不报错，只打印 No migrations are found，然后 migration:run 正常退出 0。

⇒ 部署流水线里"迁移"这一步会显示 成功，而所有 DDL 从未应用。后续症状会伪装成完全无关的样子（"代码把列名写错了"）。

所以判据只能是 migration:show 列出两支且都为 [X]，不能只看"那一步绿了"。跑完再复跑一次 node scripts/gate.mjs schema:parity 确认结构一致。

顺序纪律 B11 的三步顺序不能颠倒：--dry-run → 手工跑一次核对输出 → 才交给 cron。原因是 crontab 会原样接受一条语法错误的命令行然后每天定时执行它 —— 表现为"cron 什么都没干"，而 crontab -l 看上去完全正常。

06阶段 C · 域名与小程序（并行 · 长周期，不占 A/B 的关键路径）

关键认识：服务器部署 ≠ 小程序上线。服务器这条线今天就能全做完，不需要等任何资质；小程序这条线卡在资质与备案上，两条应该并行。

#动作依赖时效
C1 小程序备案（工信部，经微信公众平台提交，免费） 微信认证已完成（¥300/年） 平台初审 1–2 + 管局终审 1–20 工作日
C2 服务类目审核 《食品经营许可证》（热食类制售）或《预包装食品销售备案凭证》 3–7 工作日
C3 小程序后台配 服务器域名（request / uploadFile / downloadFile） 阶段 B 的 HTTPS 域名 + C1 即时生效
C4 上传体验版，走真机 C3 无需审核，上传后可给体验者扫码
C5 提审 → 灰度放量（单楼 3 天） C1 + C2 审核 0.5–1 工作日
C1 两个时间陷阱 ① 备案有每日提交配额，额度耗尽当日无法提交（次日刷新）—— 别卡在最后一天。
② 平台初审通过后会给 12381 短信，24 小时内必须核验，超时需重新排队。
C4 待实测确认 体验版无需提交审核即可给体验者扫码使用，这一点是确定的；但体验版能否正常调起微信支付，公开资料说法不一致（有说受限、有说正常）。请以真机实测为准，不要照抄任何一方的结论。
好消息：项目内部测试走 PROVIDER_MODE=mock（MOCK_PAY_AUTO_SUCCESS 可自动发支付成功事件），这条链路的验证不依赖真实支付能力。

09需你确认的三件事

#要确认什么为什么它决定路径
1 域名的原备案接入商是谁？备案状态是否正常？ 决定要不要走 1–20 工作日的接入备案。这是本轮唯一可能拖长关键路径的动作
2 是否用"新注册"的腾讯云账号买？ 新用户首单约省 ¥1,000+，但新账号需先完成企业实名（1–2 天）才能生成备案授权码
3 部署由谁执行？要不要我把阶段 A + B 展开成"逐条命令 + 失败排查"的粘贴版清单？ 决定我是出文档，还是派运维专家按这份手册在真机上逐步执行并留痕每条判据的实测输出
说明 本轮是判断与方案，没有召集开发团队 —— 这是个判断题而不是产出物题，召集人反而绕弯。
等你确认上面三件事，我会按标准路径推进：架构师锁定云资源与网络口径 → 运维（卜宕机）真机执行阶段 A/B → QA 复验 B7/B8/B10 三条判据，并把每条实测输出留痕。
