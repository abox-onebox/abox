三、P1「能看不能买」根因修复 —— 终验（本轮核心）

第三轮发现的 P1：存量用户绑在无在职团长的楼上，首页 canOrder=true 但下单必抛 30007。根因是「能不能下单」的判据散落在首页与下单两处、下单侧不查团长。

修复（2026-11-11 19:20 提交，19:43 部署）：新增纯函数 orderability.ts#evaluateAvailability 把 hasActiveLeader 并进唯一判据，由 OrderAvailabilityService 统一装载；order.service.ts 显式拦截 leader_unavailable → 30007 + 唯一出口文案。

三重证据

  • 源码 本地 orderability.ts 第 124 行 if (!i.hasActiveLeader) return { canOrder:false, reason:'leader_unavailable' }；编排层第 126–130 行装载 hasActiveLeader。
  • 生产 容器内 /app/apps/api-server/dist/ 编译产物含 leader_unavailable 字符串 → 线上已是新逻辑。
  • 单元 gate all 的 jest 共 818 测试全过，含 orderability 全序判定用例（结构层 fail-closed、leader_unavailable 位置不可调换）。

五、支付闭环（新用户路径，本轮补验）

第三轮仅实证了既有用户支付闭环；本轮以全新账号走完整两步模型，确认对所有人一致：

  1. POST /orders 建单（Idempotency-Key 头）→ code=0，返回 orderNo（pending_pay）。
  2. POST /orders/{orderNo}/pay（createPrepay，幂等键 idem:pay:*）→ code=0，返回 paySign=mock_pay_sign。
  3. 轮询 GET /orders/{orderNo}/pay-result：mock 模式 ~1s 内由后端自动置 paid（U8 实证 orderNo=AB2026111165695925）。

注意：真实支付回调 /pay/notify 在 real 模式下由 RealWxPayProvider 验签；/pay/mock/paid 仅 mock 模式可用、生产 nginx 已拦。审核阶段走 mock 闭环即可，真实微信支付需在正式公开发布前切 PROVIDER_MODE=real 并配置商户号（见 §十）。
