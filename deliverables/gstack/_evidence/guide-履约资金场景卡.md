### 6.7 ⭐ 昨天的 P1（取消两层幂等缺失）为什么本机测不出来？

> **机理**（**结论：本机测不出，因为 SQLite 写串行 + 单实例把并发窗口消灭了**）：
> 1. 本机开发库是 **SQLite**，写操作**串行化** ⇒ 两个「取消」请求在 DB 层被排成先后，第二个进来时第一个已提交、状态已变 ⇒ 观察不到「同时读到旧快照」。
> 2. 一期**只允许单实例**（R10），无跨进程并发。
> 3. 缺陷的触发条件是**「两个请求都先读到 `pending_pay`/`paid` 快照，再各自无条件 update」**；串行化后这个「同时读到旧快照」窗口不存在。
> 4. 故「e2e 全绿」**不能**反驳此缺陷（`pr-逻辑审查发现.md:169` 原话：「本项目为一期单实例、开发环境用 SQLite（写串行）⇒ 本地实测极可能测不出来，需 MySQL + 真并发才现形」）。
>
> ⚠️ **但——当前 HEAD 已修**（见文首更正 + §9）：`order.service.ts:497-513` 已用**事务内原子占位**（`WHERE id=? AND status=?` + `affected===0` 抛错）把两层补齐。所以这一节的性质**从「复现缺陷」改为「验证修复是否真的生效」**——但**验证方式仍需真机 MySQL + 并发**，因为 SQLite 下「修好」和「没修」表现一样（都测不出差别）。

**真机复现 / 回归验证步骤**（需真机 MySQL + 能并发）：
```
# 前置：真机 MySQL（非 SQLite）· 一期单实例 · 关掉前端「提交即禁用按钮」的自动重试保护
# 1. 造一单 paid（走真实支付或 Mock 回调），记下 paymentNo / balanceUsed
# 2. 用两个 shell 同时发取消请求（两个不同幂等键，模拟「断网重试换键」/ 双端同点）：
#    A: curl -X POST .../orders/{orderNo}/cancel -H 'Idempotency-Key: <key-A>'
#    B: curl -X POST .../orders/{orderNo}/cancel -H 'Idempotency-Key: <key-B>'
# 3. 断言（任一不满足即 P1）：
#    · ab_balance_log 中该 orderNo 的「解冻/退回」流水**只能有 1 笔**（出现 2 笔 = 退两次）
#    · ab_refund 中该 orderNo 的退款单**只能有 1 张**（出现 2 张且 out_refund_no 不同 = 微信都受理）
#    · 第二个请求应返回 ORDER_STATUS_ILLEGAL（订单状态已变更），且**不得**给出「取消成功」假回执
# 4. 若用同一幂等键重放：应返回 code:10006 + 首次结果（KV 层拦截）
```
- **判定**：流水 1 笔 / 退款单 1 张 / 第二请求报「状态已变更」= **修复生效（绿）**；否则 **P1**。
- **依据**：`order.service.ts:497-513`（原子占位 + `affected` 抛错）+ `order.controller.ts:59-85`（两层覆盖不同情况，注释明写）+ `pr-逻辑审查发现.md:169`（为何本机测不出）。

## 8. 易漏点清单（每条一句话 + 为什么容易漏）

1. **「提交成功」≠「链路成功」** —— 出餐确认提交成功，但订单可能仍停 `cut_off`（K47）；易只验前半句。 → 见 SC-S-08/SC-F-01
2. **「跳过」不是「失败」** —— 重复提交出 `skipped=1` 是正确行为（K44）；易当异常上报。
3. **「空」不等于「坏」** —— 结算页默认今天为空（K43）、登录第一眼空白（K41）；易误报 P0。
4. **「实送 — 与 0」是两回事** —— `—` = 未申报（视为足额）、`0` = 申报零份；易混同。 → SC-S-05/SC-S-19
5. **工作台份数不是结算依据** —— 工作台是计划量、结算是实收量；易拿工作台 45 去对结算。 → SC-S-06/SC-S-15
6. **单价「冻结快照 vs 现值」** —— 结算用出餐日冻结价，改价不影响；不先改价试不出来。 → SC-S-15
7. **配送单状态链 ≠ 订单状态链** —— 两条链只在 T8/T9 接上；易把配送单状态当订单状态。 → SC-F-03
8. **`called` 推了订单却不动** —— 只有 `en_route` 才动订单；易以为「推了就该动」。
9. **「取餐通知没到」不是缺陷** —— 一期走微信群人工发；易误报。
10. **计佣（14:00）≠ 入账（次日 02:00）** —— 两段式；易把「已计佣」当「已到账」（K11）。
11. **佣金费率改动最隐蔽** —— 测完不还原，之后所有人佣金按错费率算且看不出谁改的（K-7 附注）。
12. **跳级「不报错但订单不动」比报错更危险** —— 要同时看返回码和订单状态。 → SC-F-05
13. **跑批顺序颠倒才是 OBS-7 的复现路径** —— 先出餐确认再生成配送单；正常顺序测不出。 → SC-F-02
14. **`ab_team_leader` 三列是死列** —— `balance/pending_amount/withdrawn_amount` 无写点，读它们会看到旧数字（K16 根因）。 → SC-M-03
15. **「门禁全绿 ≠ 状态可达」** —— #79 是 19 门禁 + 969 e2e 全绿却零写入点；要到可达性审计。 → SC-F-07/§6.5
16. **N3「替他人确认」业务测试人点不出来** —— 必须工程用接口验；最易在手工清单整条漏掉。 → SC-S-20
17. **无归属单（`orphanConfirmed`）不猜团长、不计佣** —— 归属为空的边界态最易漏。 → SC-F-06
18. **一期只允许单实例（R10）** —— 多实例会「A 按新时刻、B 按旧时刻，两边都不报错」。 → §6.6
19. **运维脚本从未真机跑过（R11）** —— 「本机绿」不代表真机绿。
20. **测完必须复原截单时刻与金牌费率** —— 不复原会污染后面所有人看到的数据（K-7 附注）。

## 9. P1（取消两层幂等）专项

### 9.1 现状更正（重要）

team-lead 派发口径称「`POST /orders/{orderNo}/cancel`（U11 自助取消）**两层幂等同时缺失**」。**经逐行核对当前代码，此缺陷已修**：

| 层 | 现状 | 证据 |
|---|---|---|
| 控制器层（KV 幂等） | **已加** | `order.controller.ts:72-74`：`@Post(':orderNo/cancel')` + `@UseInterceptors(IdempotentInterceptor)` + `@Idempotent({ scope: 'order-cancel', required: false })` |
| 服务层（事务内原子占位） | **已加** | `order.service.ts:497-513`：`UPDATE ... WHERE id = :id AND status = :from` + `if ((claim.affected ?? 0) === 0) throw`（fail-closed 抛 `ORDER_STATUS_ILLEGAL`） |

代码注释自称「**外部测试报告 PR-01 · 2026-09-21 收口**」，并解释了「为什么 `required: false`」（不破坏既有端上调用方，收益已由服务层覆盖）。⇒ **本项性质 = 已修项的回归验证点**。

> ⚠️ 派发口径中引用的行号（`order.controller.ts:59` / `order.service.ts:493-500`）是**修复前**的位置；当前实际位置为控制器 `:59-85`（取消块含注释）、服务层 `:497-513`（原子占位）。

### 9.2 为什么本机测不出（机理，仍成立）

见 §6.7。核心：**SQLite 写串行 + 单实例把并发窗口消灭了**；修复前后在 SQLite 下**表现一样**，故本地「修好」也证不出、本地「没修」也测不出。

### 9.3 真机回归验证步骤

见 §6.7 的 shell 步骤。**要点**：
1. 必须 **真机 MySQL**（非 SQLite）+ 能**并发**发两个取消请求（两个不同幂等键，模拟「断网重试换键」/ 双端同点）。
2. 断言：`ab_balance_log` 对该 `orderNo` 的解冻/退回流水 **1 笔**；`ab_refund` 退款单 **1 张**；第二请求报「订单状态已变更」。
3. 若用**同一**幂等键重放：应返回 `code:10006` + 首次结果。
4. 任一不满足 → **P1**。

### 9.4 判定与记录

- 绿：1 笔流水 / 1 张退款单 / 第二请求被拒。
- P1：出现 2 笔或 2 张（退两次 = 账实不符）。
- ⚠️ **本机环境无论如何测不出差异** —— 报告里必须**显式点名「本机测不了，需真机 MySQL + 并发」**，不得用「e2e 全绿」作证。
