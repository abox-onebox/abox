### SC-A-01 登录与账号（登录 / 401 / 限流 / 改角色即刻失效） [对应清单 A1]

| 项 | 内容 |
|---|---|
| **测试目标** | 证明「后台登录链路正确、错凭据不泄权限、失败有上限、改角色/停用后旧 token 立刻作废」。 |
| **身份 / 角色** | `admin` / `finance` / `supplier` / 新建账号 |
| **前置条件** | 环境已起（`node scripts/local-test.mjs --seed --build`）；**只有 3 个后台账号**：`admin/admin123`（super_admin）· `finance/finance123`（finance）· `sanweiwu/supplier123`（supplier）——依据 `seed.ts:1051-1071`、`auth.controller.ts:41`。 |
| **操作步骤** | 1. 后台地址 `:5173` 填 `admin/admin123` 登录。 **→ 见预期 ①**<br>2. 右上角看账号与角色。 **→ 见预期 ②**<br>3. 另开无痕窗口，用**错密码**连试 6 次（同一账号）。 **→ 见预期 ③**<br>4. 不带 token 直接请求 `GET :3000/api/v1/admin/dashboard/todos`。 **→ 见预期 ④**<br>5. 用 `admin` 登录后到 **系统 → 账号管理**，把 `finance` 改成 `operator`（或停用），**不刷新**原来的 finance 窗口，用旧窗口点任一财务接口。 **→ 见预期 ⑤**|
| **测试内容** | 登录成功落点、角色标签、限流、未登录 401、**旧 token 吊销**、`ROLE_LABEL` 中文名。 |
| **预期结果** | ① 登录后进入侧边栏并落到**第一个可见菜单**（`admin` = `/dashboard`，依据 `stores/permission.ts:61-63`）。② 角色中文名 = 「超级管理员 / 管理员 / 运营专员 / 财务 / 只读观察者 / 供应商」（`admin-role.ts:161-168`）。③ **同账号 1 分钟内失败 5 次 → `429`（`code=10005`）**，属**预期**（`接口口径.md` M5-6-B #4：`auth:admin-login` 账号 5/分、IP 10/分；启动横幅已注明）。④ 无 token → **`401`（`10002`）**（`error-code.ts:33,414`）。⑤ 改角色/停用后旧 token 立刻失效 → **`401` 且提示「账号权限已变更，请重新登录」**（`admin.guard.ts:44-47` + `admin-user.service.ts:193-197` 写 `adminRevokeKey`）。 |
| **边界情况** | 失败 4 次（应不锁）vs 5 次（应锁）；IP 与账号**双维度**限流（换账号可能被 IP 拦）；`rt=true` 刷新令牌不得用于业务接口（`jwt-auth.guard.ts:67-69`）。 |
| **异常场景** | 用 supplier token 打 `/admin/*` → `10003`；用用户端 token 打 `/admin/*` → `10003`/`10002`（`jwt-auth.guard.ts:76-77`）。 |
| **易漏点** | **「改角色后要等 12h」是错觉**——`adminRevokeKey` 把窗口压到 0，但**只有「改角色/停用/重置密码」才写标记**，只改姓名手机号**不踢人**（`admin-role.ts:181-189` 注释）。测「即时失效」必须**改角色或停用**，改姓名测不出来。 |
| **判定与记录** | 未登录能进后台/旧 token 仍可用 ⇒ **P0**（安全）。限流阈值不符 ⇒ P2。记法：「步骤+账号+实际 HTTP 码+`code`」。 |

### SC-A-02 权限矩阵与越权（绕菜单直输 URL / 低权限调高权限接口） [对应清单 §五末注]

| 项 | 内容 |
|---|---|
| **测试目标** | 证明「菜单遗漏 ≠ 能越权」：真正拦人的是服务端两级闸门，前端只做体验层。 |
| **身份 / 角色** | 先用 `admin` 建出 `operator` 与 `viewer`（见 SC-A-28），再逐个角色测。 |
| **前置条件** | **`operator` / `viewer` 没有现成账号**——必须先在 **账号管理** 新建（角色下拉选「运营专员 / 只读观察者」）。 |
| **操作步骤** | 1. 用 `finance` 登录，**手输** `http://<IP>:5173/system/schedule`（菜单里没有）。<br>2. 用 `viewer` 手输 `/finance/withdrawal`。<br>3. 用 `operator` 打开 `/finance/withdrawal`（菜单在），点「通过 / 驳回 / 已打款 / 失败」任一。<br>4. 用 `viewer` 打开 `/finance/overview`（菜单不在）后，直接改地址栏地址试。<br>5. 抓一个 `/admin/*` 请求，把 `Authorization` 换成另一角色的 token 重放。 |
| **测试内容** | 三条闸门的层次：`JwtAuthGuard`（主体 typ）→ `AdminGuard`（吊销 + `@Roles`）→ 前端 `canAccessPath`。 |
| **预期结果** | ① 手输无菜单页 → **跳 `/403`**（`guards.ts:63-65`；`/403` 是白名单页，`guards.ts:11`）。② `operator` 点提现审批动作 → **`10003`/403 且提示「无权限访问该资源」**（`finance-admin.controller.ts:290/318/346/376` 用的是 `FUND_ACTION_ROLES` = 不含 operator；文案 `error-code.ts:333`）。③ `viewer` 的手输 `/finance/*` → 接口 `10003`（`finance-admin.controller.ts:85` 类级 `FINANCE_VIEW_ROLES` 不含 viewer）。④ 换 token 重放 → 仍按**新 token 的角色**判定（服务端只信 token 里的 `payload.role`，`admin.guard.ts:56`）。 |
| **边界情况** | `@Roles()` **空注解**的端点 = 默认对所有后台角色开放（`admin.guard.ts:17,23` 注明「有意」）——如 A5 `/auth/profile`，**不要**把「某角色能进 A5」记成越权。 |
| **异常场景** | 手改 localStorage 的 `menus` 绕过前端 → **接口照样 403**（`stores/permission.ts:39-40`）。 |
| **易漏点** | ⭐ **`operator` 有财务「读」权限但不该有「写」权限** —— 逐条测 `GET` 通、`POST` 403，才算证明两级白名单。只测「菜单看不看得到」证明不了任何越权边界。 |
| **判定与记录** | 低权限账号**成功调通**了资金动作 ⇒ **P0**。菜单可见但点了必报 `10003` ⇒ **P1**（项目明文列为须消灭形态，`finance.constants.ts:8-11`）。 |
