四、发现的问题（按处置优先级）

P0 · 服务器出现随机性接口故障

现象：订单相关 GET 接口（订单详情、支付结果、订单列表）随机返回异常：

{"code":10001,"message":"Unexpected token '\"', \"\"eyJhbGciO\"... is not valid JSON"}

服务端在尝试把一段 JWT 字符串当作 JSON 解析。

实测经过：

  • 15:41 起，同一订单连调 10 次 pay-result，10/10 全部异常；订单详情同为 10/10 异常
  • 全新注册用户、从未调用过任何异常接口的干净订单，同样异常 —— 排除「我的账号被污染」
  • 同一时段内用 curl 请求全新用户，结果完全正常（code=0）
  • 15:48 起连续采样 16 次（46 秒），0 次异常，已自愈
  • 期间健康检查始终正常（db 1ms、queue ok），服务未重启（uptime 持续增长）

最可能的解释：后端有多个容器实例，其中某一个进入了坏状态，请求负载均衡到谁就决定成败。这也能解释「同一时刻有人正常、有人异常」。

为什么这条最严重：它不可预测、能自愈、健康检查发现不了。若明天上线期间某个实例再次进入此状态，用户会随机遇到「订单打不开」，而监控上看一切正常。

建议交给技术的动作：拉取 15:33–15:48 期间各实例日志，检索错误关键词 JSON／eyJhbGci；确认 docker-compose 中 api 服务副本数；将 GET /orders/:orderNo 与 pay-result 纳入拨测，按每分钟粒度监控。

P1 · nginx 对模拟支付接口的封锁可被大小写绕过

测试服务器上 nginx 精确封锁了小写 /api/v1/pay/mock/paid（返回 nginx 404 HTML，非应用错误）。这本是安全加固，方向正确。

但我实测发现：NestJS 路由大小写不敏感，仅仅改变大小写即可绕过并真实执行：

POST /api/v1/pay/mock/paid     ->  HTTP 404（nginx 拦截）
POST /api/v1/pay/MOCK/paid     ->  HTTP 201，body: {"code":0,"message":"ok"}   ← 真实执行成功

补充边界实测：pay/mock/paid/（尾斜杠）也能绕过返回 200；pay/mock/paidd、pay/mock/notify 正常。

影响：本环境 PROVIDER_MODE=mock、mockEscaped=true，该接口的作用是「免鉴权把订单改成已支付」。若上线环境沿用同形态，这道封锁等于没有。

建议：① nginx 规则改为不区分大小写（正则加 (?i)）或同时匹配尾斜杠；② 更彻底的做法是在应用层由 prod-mock-gate 关闭该路由（现已有该机制，建议线上彻底关闭 ALLOW_MOCK_IN_PROD）。

P2 · 并发下可生成多笔待支付订单（需业务确认）

实测：同一用户用不同幂等键并发下单 5 次，成功生成 5 笔订单（AB20261027... 五笔）。

这与 S8 不同——S8 是「同一意图被重复执行」，已被幂等拦住；这里是「五个独立意图」，接口按正常业务处理。

但存在业务风险：目前只有单笔份数上限（order.max_quantity=20），未见同一用户同一出餐日的订单笔数上限。若用户连点或网络重试产生多笔待支付订单，会造成履约混乱与重复配送。

建议：确认是否需要「同一用户同一出餐日未支付订单上限」，或由端上做「有待支付订单时禁止再下」。请先确认业务口径，再决定是否落码。

P2 · 两项安全扫描 WARN（可顺手处理）

mock-wx-mini.provider.ts:32/42 的 debug 日志打印了 openid 与示例手机号。仅在 mock 路径，非生产，建议把 openid 截断后再打印，消除扫描噪音。

六、交给技术前建议你先确认的三件事

  1. 本次是否按计划上线：第四节 P0 的随机性故障如果能自愈，多数情况下会被忽略；但它若出现在上线当天，影响面不可控。建议至少确认技术已看过那段时间日志。
  2. 线上形态：健康检查实读 providerMode: "mock"、mockEscaped: true。这是「任意 code 免密登录任意身份 + 免鉴权改支付状态」的形态。测试环境可接受，正式环境必须为 real。这是 main.ts 注释里自己写明的后果。
  3. 后台账号：我刻意没有尝试管理员密码（5 次失败锁 900 秒）。若要我把停售／停用／提现这三项也实测掉，请提供一组专用管理员账号。
