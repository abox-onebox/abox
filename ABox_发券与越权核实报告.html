ABox 一盒 · 发券风险与越权核实报告

核实日期 2026-10-26 ｜ 第二批（紧接资金类四条）｜ 方法：真实代码走查 + 反向验证 ｜ 结论先行：越权防线做得比我预想扎实；发券有一条真缺口但我把等级估高了一档

先说这轮最重要的一条更正：我上一轮说 F10 是「一次输错就是百万级事故」，这个表述夸大了。
核实后发现单笔抵扣有两道数学兜底（Math.min(面额, 订单额) 和 Math.max(0, …)）， 一张天价券最多只能免掉一单的钱（¥25.80），撑不到百万级。真正残留的风险是「无面额上限 + 可绕开总量限制无限发」， 性质从「资金爆雷」降为「内控缺失」，等级由 P0 降 P2。
越权（V1/V2）这轮是反向结论：我原本准备提的几条，代码里基本都堵住了，下面是实证。

F10 · 代金券：无面额上限，且能绕开总量限制无限发

等级 P0 → P2 ｜ 性质：内控缺失，不是资金爆雷 ｜ 定级理由见文末「我为什么降级」
① 真缺口 A：面额只有下限、没有上限
  • modules/coupon/dto/coupon.dto.ts:37-41 —— 创建券种定义：@IsInt() @Min(1)，无 @Max
  • modules/coupon/dto/coupon.dto.ts:133-137 —— 手动发券：@IsInt() @Min(1)，无 @Max

这意味着面额字段技术上接受任意正整数。把 500（¥5）误输成 500000（¥5000）时，校验层不会拦。

② 真缺口 B：手动发券可以完全绕开「发行总量上限」
  • modules/coupon/dto/coupon.dto.ts:120-125 —— couponDefId 标了 @IsOptional()，注释写「纯补偿券可空」
  • modules/coupon/coupon.service.ts:136-140 —— 全部限量校验写在 if (input.couponDefId) { … } 里头
这条是实打实的绕过路径：只要发券时不传 couponDefId，totalLimit 的「券种已达发行上限」判断（coupon.service.ts:148-153）整段被跳过， 且末尾的总量回写（issuedCount 自增，coupon.service.ts:192-197）也不执行 —— 系统连计数都没有。
后果：运营可以脱离券种定义，不停调用 POST /admin/coupon/grant 发放任意张数、任意面额的券，无熔断、无二次审批、无额度告警。 唯一的痕迹是 @OperationLog（coupon-admin.controller.ts:75）写进 ab_operation_log —— 那是事后留痕，不是事中阻断。
③ 但以下三点是被防住的，别按上面两条去问责：
  • 券不能被别人用 —— coupon.service.ts:262-263：if (uc.userId !== userId) throw …'该券不属于当前用户'。这条比我预想的好，关联的定义校验之外，逐张校验了持有人。
  • 抵扣不会超过订单额 —— coupon.service.ts:71-74：discountOf() 返回 Math.min(面额, 订单额)，注释写「面额不应超过订单额；双保险」。
  • 支付金额不会成负数 —— order.service.ts:332：payAmountFen = Math.max(0, 总额 − 余额 − 券)，券与余额双抵扣也有兜底。
我为什么把等级从 P0 降下来：
因为有上面这两道数学兜底，单笔交易的损失上限就是一份饭钱（¥25.80）。要做到显著金额，必须「发 N 张 × 每张各用一单」—— 那是一条慢性的内控漏洞，不是「一次输错炸掉全年利润」的爆雷。性质不同，处置优先级就该不同。
但它仍然要改，理由是事后无法对账：一旦有人手滑或有内鬼，事后只能靠翻操作日志逐条比对，没有任何一道闸门拦得住。
建议的修改（三处，都很小）：
  • coupon.dto.ts 两处 faceValueFen 补 @Max(…)，推荐取单份套餐价 ¥25.80 = 2580 分为上限（超过这个数在业务上没有意义）
  • coupon.service.ts:136：couponDefId 为空时，改为必须填发券理由并要求二次确认字段，或干脆强制关联券种定义（让所有发券都走总量口径）
  • 加一条「单日发放总额」围栏（例如单日累计超过 ¥500 直接拒绝）—— 这条能兜住前两条都失守的情况

V1 · 水平越权（IDOR）：结论是「系统性防住」，建议保留现状

原本担心的问题：登录后把请求里的 userId / openid 换成别人的，能不能读写他人数据
结论：这条防线是按「漏写即沦陷」的思路设计的，不是靠每个开发者记得加注解。四条实证：
① 全局默认要登录（fail-closed）
  • src/common/common.module.ts:86 —— { provide: APP_GUARD, useClass: JwtAuthGuard }
  • 全仓 34 个 controller，免鉴权（@Public()）只有 10 处，且每一处都有注释写明理由（登录 / 支付回调 / 企微回调 / 匿名埋点 / 溯源只读）

我一开始按「UseGuards 计数为 0 = 没鉴权」去筛，差点又犯上一轮「探针不完整就下结论」的错 —— 这些「0」是走全局守卫，反而更安全。

② 身份一律从令牌取，没有任何端点从请求体取 userId
  • 全仓 grep @Body() / @Query() / @Param() 中的身份字段：只出现在 3 个后台控制器（leader-admin / user-admin / coupon-admin 的补偿券），全部挂在 AdminGuard + Roles 之下，是正常的管理功能
  • 用户侧一律 @CurrentUser() user.sub：order.controller.ts:48/54/60/94、coupon.controller.ts:20/29、payment.controller.ts:35/41、meal.controller.ts:22/28 等，写法完全一致
③ 前后台账号体系强制隔离（防止「后台账号调用户接口」）
  • common/guards/jwt-auth.guard.ts —— 按路径前缀（/admin/*、/supplier/*）判定主体，admin 类路径只收 typ='admin' 的令牌，反之亦然
  • 源码注释里写明了这么设计的理由：「漏写即越权」 —— 按路径自动覆盖新控制器，不依赖任何人记得加注解。这是有经验的写法。
  • 额外：rt=true 的刷新令牌不能当访问令牌用；失效注销用户之类的边界也有处理
④ 团长身份不信任令牌里的标记，每次都回查库
  • common/guards/leader.guard.ts 头注：「禁止仅凭 JWT 内的 isLeader 放行」，理由是令牌有效期 7 天，期间团长可能已被停职
  • 实际实现二次查询 ab_team_leader 确认在职；「从来不是团长」与「已停职」分开报错（不同引导话术）

V2 · 团长跨团操作：主防线已堵住，留一条「脚手架没拆」的建议

这是本批我最想查的一条 —— 因为它直接连着佣金：团长能不能把不是自己团的单推进「已送达」从而计佣
① 团长的操作范围是被强制收窄的，不是靠前端过滤
  • modules/order/leader-order.service.ts:413-419 —— applyScope() 统一给查询加上归属条件
  • buildPickupQuery()（同文件 :401-410）在取餐确认时也调用它，注释明确写着「避免把别团长的 delivering 单算进来（IDOR）」
  • 「一键分发」还做了逐单条件更新（:319-330）：只把真正更新成功的单计佣，并发被抢走的单不计佣且写告警日志

结论：团长 A 确认团长 B 的单这条路径，代码里已经想到了并堵上了。

② 后台推进配送状态确实不校验楼群 —— 但那是设计意图，不是漏洞
  • modules/delivery/delivery.service.ts:639-648 —— advanceStatus(id, dto, operatorId) 只按 id 查配送单，没有 operator 与楼群的绑定校验
  • 但调用入口是 modules/delivery/delivery.controller.ts，路径 admin/deliveries，挂 AdminGuard + Roles('super_admin','admin','operator') 且有 @OperationLog

也就是说这是后台运营作业（调度全城配送必然要能推进任意楼群），鉴权与留痕都在。不算越权。唯一可提的：operator 角色拥有推进任意楼群履约状态的权力，若将来 operator 账号外发给第三方（比如外包调度），需要额外收紧。

③ 唯一建议：一条已经不可达的「兜底」分支，建议尽快清掉
applyScope() 的范围是：
o.teamLeaderId = :leaderId OR (o.teamLeaderId IS NULL AND o.buildingId = :buildingId)

第二个分支的含义是「历史未绑团长时按楼栋兜底」。但我核到建单路径（order.service.ts:1602-1620 resolveLeader()）：
订单创建时团长一定非空 —— 三个来源都拿不到就直接 throw LEADER_NOT_FOUND「未绑定团长，请通过团长邀请链接进入」，然后 order.service.ts:337 无条件写 teamLeaderId: leader.id。

所以这个 IS NULL 分支对新订单永远不成立，目前是死代码。危险不在今天，在明天：这是一种「同一栋楼内任意团长都能操作任何单」的后门口径，一旦将来有人改建单逻辑让 teamLeaderId 可空，边界会瞬间从「只认自己的单」放大到「认整栋楼」，而改动的人多半不会想到有人在 applyScope 里留了这句话。
建议：确认生产库 ab_order.team_leader_id IS NULL 的行数为 0 后，删掉第二个分支（或加断言），让边界定义只有一处。

X1 · 走查中新发现：换绑办公楼会清空团长归属，且注释说要「重算」但没有实现

核前未预设 ｜ 触发概率低，但一旦发生会把佣金算给别人 ｜ 建议先观察
现象
  • modules/user/user.service.ts:141-145 —— 用户自助绑定/更换办公楼时：update({ buildingId, teamLeaderId: null })
  • 紧随其后的日志自己写着：「已清空 team_leader_id 待重算」
  • 但我在全仓没有找到对应的「重算」实现
会发生什么

该用户下一单走 resolveLeader()（order.service.ts:1607-1618），三级 fallback：
① 专属链接 leaderCode → ② 用户表绑定的团长 → ③ 都没有时，按楼栋取 order: { id: 'ASC' } 的第一个在职团长。

②被清空且用户没走专属链接时，这单就落到 ③ —— 佣金给了楼里最早注册的团长，而不是用户实际认识的那位。

我为什么把它定为低优先级
因为触发条件窄：代码里 const changed = 原buildingId !== dto.buildingId，只有真的换了楼才清空（重绑同一栋楼不动）。 而换楼之后，原团长本来也服务不到，把归属交给新楼的团长是合理的默认行为。
真正值得改的只有一点：「归给谁」不够聪明（取 id 最小而非最近的），以及「待重算」这几个字是句空话 —— 注释承诺了系统做不到的事，属于会误导后来人的那种。
